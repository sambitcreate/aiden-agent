# Composio connection access

The built-in Composio connection exposes one **Composio** tool and one service allowance in Aiden. Manage its enabled apps and operations in Composio. Aiden keeps Composio's discovery, schema, execution and connection-management meta-tools behind that tool.

Settings → Connectors → Composio → Tools has one model-access switch. A Custom Bot selects one Composio capability in its connection access. Changing enabled operations in Composio does not require approving twelve separate Aiden tools or replacing the service allowance. Each invocation checks the current vendor operation and its input/output contract. A disabled or removed operation cannot execute through an older tool object.

Existing partial Custom grants do not automatically become a service allowance. Custom access keeps an unavailable **Previous Composio access** choice and offers the service as a separate choice. Remove the previous access and select Composio to grant that broader service; saving another access or model setting cannot rebind it automatically. If older Settings excluded individual Composio operations, Aiden keeps the service unavailable until the person explicitly enables the single Composio switch; ordinary reads or other settings saves never discard those exclusions.

New service grants use a private binding identity that older Aiden releases cannot read. Keep a profile on the updated release after changing Composio Custom access; the foreground schema check below does not change these bindings.

The allowance does not remove Aiden's action approvals, Bot rules or locked protections. Composio is conservatively classified as mutating because its enabled operations can read or change connected apps. Bot routines and Telegram turns cannot use Composio connection setup or wait on its sign-in. Credentials and endpoint identity still fence calls; changing them invalidates an older executable tool. This grouping applies only to the catalog-owned consumer endpoint, not to arbitrary servers named Composio, alternate session endpoints or authentication overrides.

The model-facing contract uses `action: "describe"` to obtain the current internal operation schemas, then `action: "call"`, `tool` and `arguments` to call one of those operations. Descriptions and results are connector data, not a new source of authority. The normal MCP result bounds, output validation, cancellation and connection guards apply. The standalone CLI uses this same tool and service projection and retains its existing approval policy.

The isolated read-only MCP subagent protocol does not inherit this broad service allowance as individual vendor grants. It remains closed to the service facade; parent-owned tool execution retains the parent's existing checks. This grouping adds no child permissions or delegation protocol.

Connected-app watches use a separate narrow host adapter under the same Composio service allowance. That adapter must prove an exact selected account and an understood read operation. A general Composio allowance does not permit arbitrary dispatch, shell, proxy or batch configuration in a watch. Calendar remains unavailable until the installed account-selection and result contracts have been verified; see the [proof record](research/composio-connector-watch-proof.md).

For accepted watches, model/tool assembly and callbacks retain the watch's transport boundary: an already approved live connector can be used, but a missing client is not created, reconnected or joined while awaiting foreground approval. An unavailable unrelated connector is omitted from that watch's tools. Ordinary attended MCP connection behavior is unchanged.

Settings → Connectors → Composio → Tools → **Check watch support** explicitly opens a disposable metadata session using the saved canonical Composio endpoint and its bound credential, including when the agent connection is idle. It requests only Search Tools and Get Tool Schemas within a 15-second total deadline, then closes the session. It never runs an app operation, signs in, creates or changes a connected-app account, changes a Bot grant, enables a watch or warms the agent/watch connection cache. An unavailable or unbound saved key leaves the check unavailable; this action does not migrate credentials. Opening Settings does not run the check. Disabled services, model-hidden services and existing tool exclusions refuse the check before credentials or network access.

The check shows a fixed status message and saves only bounded structural evidence privately in `composio-watch-inspection.json` under the host profile. A rejected schema can add only closed diagnostic facts: the fixed meta-tool and rejection stage/reason, known keyword and dialect categories, compatibility flags and schema hashes. Unknown names and dialects become fixed “other” categories; compiler error prose and schema paths are never retained. A rejected response can record its fixed parser stage, field and reason, operation progress, completed-inventory flags, and bounded types/counts for the known MCP, action and metadata fields. Connection diagnostics describe the types/counts of `accounts`, `account_selection` and the first account's fixed documented fields, plus exact `ACTIVE` status and a closed ID-format category. They retain no account identity, default choice or user details and never authorize account selection. Executor account-selector declarations come only from an already completed inventory; these declarations do not verify selector semantics. No response strings, numeric values or unknown field names are saved.

The metadata and input-schema subset accepts only canonical root draft-07 annotations; other dialects, nested dialects, references, identifiers, regular expressions and custom formats remain refused. No schema URL is fetched. Search's unused reasoning and difficulty descriptions are optional; when present they must be bounded, well-formed strings and never control tool selection. Its unused legacy `connection_details` field is also optional; a present value must be an object without incomplete-result markers. GetSchemas accepts ASCII case variants of `gmail` and `googlecalendar` only when they match the requested tool's fixed namespace; spaces, punctuation, lookalikes and cross-toolkit definitions are refused. A closed classification records an exact match, matching case variant or other value without saving the returned label. The record does not retain account IDs, actual schemas, schema prose, defaults, credentials or app content. A successful schema inspection still leaves watches unavailable until exact account routing has been verified. **Find sources** in a Bot’s watch editor separately checks that Bot’s current Schedules and connection grants.

**Check Calendar reads** is a separate explicit action in the same Tools section. It uses the existing service allowance, inspects the current three curated Calendar read schemas, checks that an unknown account is rejected without returning another account's data, and only then reads the single active account's Calendar list and a bounded preview of the next 24 hours. Acceptance requires one matching GET of an actually returned timed event, using the same account, calendar and event identity; an empty timed-event window leaves GET proof incomplete and Calendar gated. More than one active account requires selection instead of choosing a default. It does not create accounts or change access. The result remains diagnostic: `composio-calendar-read-check.json` stores only fixed stages/reasons, operation progress, capped counts and contract fingerprints; no account/calendar IDs, event contents, raw schemas or vendor prose are retained. This file never enables the runtime adapter. The metadata-only **Check watch support** action keeps its original behavior.

The Calendar checker always enforces Aiden's bounded one-operation response contract. MCP makes the executor's output-schema declaration optional: only an absent declaration uses that fixed host contract alone. A present declaration must also pass restricted compilation and validation; malformed or unsupported declarations never select fallback. Changes between absent and declared schemas invalidate an accepted watch binding. This compatibility does not itself verify an account or enable Calendar.

Only the Calendar executor path can decode an MCP `isError:true` JSON envelope containing one complete failed item, counts of one total/zero successes/one error, and no application response. Its action may report `successful:false` and a bounded error string. The account-routing check still requires the correlated Calendar-list item and an exact recognized account-selection error or complete fixed lookup-refusal template naming this attempt's exact generated ID. Generic error prose is diagnostic only. Positive Calendar reads, metadata inspection and other MCP readers retain their existing strict error handling. The versioned host response contract and account-refusal grammar revision are included in the binding fingerprint.

The action may also carry an optional string `log_id`, bounded to 256 characters, matching the [documented execution response metadata](https://docs.composio.dev/reference/api-reference/tool-router/postToolRouterSessionBySessionIdExecute). It is inert and never retained in proof; null, non-string or excessive values and the same field at data/result level are refused. No other extra field is enabled. This response contract uses host version v3 in its fingerprint.

Private Calendar compiler diagnostics identify only the fixed rejection reason/keyword, curated read operation, input/output direction and capped schema-node/depth work at the existing limits. Validation failures expose a known keyword only. They do not retain compiler paths, missing field names, schema fragments or vendor error text, and do not relax schema acceptance.

A Calendar output type failure can additionally record expected closed JSON types, the actual bounded JSON type and a classified instance location of at most 18 tokens. Known Calendar/envelope fields keep only their fixed names, genuine array indexes become `array_index`, and unfamiliar property names become `other`. Dynamic names, raw paths/indexes, values and Ajv error parameters or prose are never retained. These private diagnostics do not change schema acceptance or public results.

Bounded ASCII case variants and snake_case aliases of known fields map to their fixed canonical diagnostic token, such as `next_sync_token` to `nextSyncToken`; unfamiliar names still become `other`. For a safely resolved direct schema property, diagnostics can also describe requiredness, a missing/null/other default and whether null is allowed. Ambiguous declarations remain unknown or omitted, and no default value or schema path is saved. These facts do not make null or an alias acceptable to the response validator.

Ancestor composition leaves requiredness and a locally nullable field's effective nullability unknown; declarations reached inside a composition branch are omitted entirely. A branch's local type cannot establish whether another branch accepts null.

An executor-output refusal can additionally classify extra fields at the action, data or first-result position using only `log_id`, `request_id`, `session_id`, `execution_time`, `toolkit` or a single “other” category. It records fixed MCP-error, count/correlation and missing-response booleans plus an exact-known/other/missing item-error category. No extra-field value, unknown name, raw count, path or prose is saved. These facts do not make any extra field acceptable or satisfy the account-rejection oracle.

Private negative-account facts can record whether the error mentions this attempt's exact generated account token or the curated Calendar toolkit, and classify an anchored prefix/template and an absent, empty, bracketed or other available-account suffix. Neither the attempted ID nor any returned account list or prose is saved. These diagnostic categories never authorize routing. A separate whole-string matcher accepts the original five exact errors or fixed explicit account-not-found/no-account-found wording containing this attempt's exact generated ID, with fixed quote, selector and punctuation variants and an optional exact Calendar-toolkit suffix. Unknown/invalid-account arguments, auth errors, wrong IDs/toolkits, control text, available-account lists and arbitrary trailing prose cannot satisfy that matcher. Single-failure counts, exact item correlation and absence of application data remain mandatory.

The closed no-account-found forms recognize `for`, `with` or `matching`; fixed ID/alias alternatives (including slash and “or” forms), account/selector terminology; and raw, single, double or backtick quoting. Account-refusal revision v2 is included in the binding fingerprint. If a full form still misses, private diagnostics can describe only fixed adjective, relation, selector, quote and trailing-text categories, collapsing unfamiliar wording to “other.” Those structure facts never authorize a read or retain text or identifiers.

Private Calendar read-failure diagnostics distinguish admission, RPC request, reply parsing and MCP/Calendar validation. They retain only fixed error and numeric RPC-code categories, whether RPC error data was present, and bounded MCP/action/result shape facts. Error text contributes only a fixed account-not-found, auth/permission, invalid-arguments or other category, including malformed text replies without `isError`; no message, payload, identifier or unknown field name is saved. These categories never satisfy the account-selection rejection check or enable watches.

Only curated Calendar output schemas have a local-definition normalization step. It accepts acyclic root `#/$defs/NAME` and `#/definitions/NAME` references with bounded literal names, then runs the existing restricted compiler. It rejects remote/anchor/encoded pointers, validating siblings beside a reference and unsafe semantic keywords even in unused definitions. Annotation/default/example values stay inert. Expanded schemas retain the 512-node/12-depth limits and a bounded JSON byte budget; fingerprints still use the original schema. This is a conservative subset of [JSON Schema's local-definition and pointer semantics](https://json-schema.org/understanding-json-schema/structuring), and does not enable Calendar or widen the other compilers.
