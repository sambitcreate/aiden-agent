# Direct native development browser — source review, 2026-09-09

Use a native browser pointed at `http://<paired Mac Tailscale IP>:<user port>`. This is an ordinary tailnet TCP service, independent of Aiden's authenticated API transport. The API supplies only an optional bare developmentHost hint derived from the running node's Self record. Never inject Aiden credentials, API TLS exceptions, DOM bridges, or desktop browser sessions into the page.

The devserver must bind to its Tailscale interface address or all interfaces; a localhost-only listener cannot receive remote packets. For Vite, `--host 0.0.0.0` enables nonloopback listening; IP hosts are accepted by default. A MagicDNS name may need an exact allowedHosts entry. WebSocket/HMR must target the reached Mac address and actual listening port, not a hardcoded localhost endpoint. Source: [Vite server options](https://vite.dev/config/server-options). These recommendations are conditional on the app's Vite version; current docs deprecate HMR transport fields in favor of server.ws.

HTTP does not require provisioning a page TLS certificate. The Mac-to-mobile tailnet hop uses WireGuard encryption for direct and relay connections ([Tailscale connection types](https://tailscale.com/docs/reference/connection-types)). This does not make HTTP a browser secure context: features such as service workers can still require HTTPS ([W3C Secure Contexts](https://www.w3.org/TR/secure-contexts/)). Tailnet ACLs and host firewall determine reachability; Aiden pairing is not a replacement for that policy.

For localhost-only servers, the agent can now use `tailscale_serve` to configure a private HTTP Serve reverse proxy. Ordinary direct Browser navigation still changes no Serve routes and requires no Serve/HTTPS. MagicDNS supplies per-device DNS names ([MagicDNS](https://tailscale.com/docs/features/magicdns)); the hint accepts only the current Mac's validated self name, not peers or arbitrary DNS input.

Implementation: main/services/aiden-remote-tailscale.ts now exposes node-only developmentHost() and optional connection-status developmentHost. Require Running, reject explicit offline, prefer self canonical IPv4 in100.64/10, fallback to bounded syntactically valid machine.tail.ts.net. No serving configuration or peer inventory is changed. Tailscale tests34/34pass; scoped lint passes.

For the requested Next.js example, start the project's development command with `--hostname 0.0.0.0 --port 3000` (for example `npm run dev -- --hostname 0.0.0.0 --port 3000` when the script runs `next dev`). Open `http://<Mac Tailscale IPv4>:3000` in the native pane. See the [Next.js CLI](https://nextjs.org/docs/app/api-reference/cli/next). If the project's development-origin policy blocks the reached host or HMR requests, configure the specific host under [allowedDevOrigins](https://nextjs.org/docs/pages/api-reference/config/next-config-js/allowedDevOrigins); do not disable origin checking globally. A server may print localhost in its startup message even though it listens on all interfaces; use the actual Mac address on the device.

Final independent source review accepted both native implementations after correcting keyed WebView selection, retained address input, canonical host parsing and iOS website-session cleanup across pairing contexts. Desktop Remote Access lifecycle E2E passed on the final direct-browser build. Android instrumentation verified HTTP, WebSocket messages and retained DOM state; physical iOS/tailnet acceptance remains pending.

## Optional agent HTTP forwarding tool

Use `tailscale_serve` with `{"action":"open","localPort":3000}` after the development server starts. An optional `exposedPort` selects a different tailnet port. The tool probes localhost HTTP, verifies the host’s Tailscale self identity, then creates the equivalent of `tailscale serve --yes --bg --http=3000 --set-path=/ http://127.0.0.1:3000`. It returns an owned id and `http://<Mac DNS name>.ts.net:3000/`. This is a private HTTP proxy; it does not enable Funnel or require a page TLS certificate. Command behavior follows the [official Serve CLI reference](https://tailscale.com/docs/reference/tailscale-cli/serve).

`{"action":"list"}` inspects only the current workspace’s owned forwards. `{"action":"stop","id":"<returned id>"}` removes an unchanged owned forward. The agent presents the returned address as a Markdown link; explicit user taps on canonical Tailscale HTTP links route to the native Browser. Browser tabs and forms remain client-local. Raw tool results never trigger navigation.

The tool is available to ordinary foreground workspace chats, including mobile generations, with Ask or Full access. Ask uses existing native/desktop tool approval. Read-only, assistants, bots, subagents and scheduled generations do not receive the tool. Generation cancellation and workspace permission/root identity are rechecked before effects. Mutations are never replayed automatically after an interruption.

Both ports must be integers in 1024–65535. Targets are fixed to HTTP 127.0.0.1; Aiden internal API listeners are excluded. Existing HTTP/TCP/Funnel/foreground listeners on the requested exposed port are conflicts. An ownership journal under the active profile’s userData/tailscale-previews/routes.json is atomically persisted before the CLI operation. A shared cross-process lock coordinates Aiden’s API routes and preview changes. Unrelated configuration is compared before/after; changed or uncertain routes are never broadly reset or rolled back. A noncooperating external Tailscale operator can still race the CLI between final inspection and mutation; the CLI does not offer an atomic conditional update here.

`status: active` verifies configured route ownership and current Tailscale identity, not end-to-end client reachability or continuing backend health. Forwarding persists across Aiden/Tailscale restarts until stopped. The journal allows an interrupted operation to be inspected and an unchanged owned route stopped after restart. A stopped development process can leave a configured forward, so stop the forward when finished. Host firewall, tailnet access policy, DNS, framework origin settings and WebSocket URLs still determine actual page/HMR behavior. Physical iOS/tailnet/Next.js acceptance remains pending; no live tailnet routes were modified during implementation tests.
