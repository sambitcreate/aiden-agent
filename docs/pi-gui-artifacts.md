# Pi GUI artifacts

Aiden can present structured, tool-produced artifacts in an attended desktop chat without asking a model to emit Markdown paths.

## Current image path

1. `prepareGeneration` contributes `aiden.gui.display-image` only to an attended workspace chat with non-`none` access.
2. The Pi-native `display_image({ path })` tool accepts a workspace-relative raster path. Main verifies the pinned workspace root, lexical containment, file identity, regular-file status, raster structure, compressed bytes, decoded dimensions, and pixel count. APNG plus animated or out-of-bounds GIF/WebP payloads are refused for now.
3. Before the tool reports success, main stages the normalized image bytes in an app-owned durable store keyed by chat, generation, and tool call. It then emits a `ChatArtifactEventV1` `present` event. The tool result returned to Pi is a short text acknowledgement and never contains image bytes.
4. The renderer validates the event before retaining it, renders the image immediately, falls back to a file card on browser decode failure, and deduplicates it against the terminal chat snapshot. Automatic provider retries retain completed, non-replayable image effects.
5. Main persists the normalized image on the assistant message through Aiden's existing bounded attachment contract and clears its staged copy. While a staged response is unresolved, the main-owned chat-read status keeps the composer blocked across navigation, and further sends, copies, and exports for that chat are refused. Startup recovery deduplicates a crash-left stage against ChatStore or restores each interrupted generation as an image-only assistant message with a fixed interrupted-response marker, so reopening, copying, and exporting do not depend on the source file still existing.

**Placement and size.** Each image renders right after the activity row of the call that produced it (`display_image`, `share_image` or `generate_image`), live and after the reply is saved, so later text streams in below it. Adjacent media calls at the same text offset keep their own rows: images, visuals, extracted values and browser recordings follow call order rather than being collected by media type. Image, visual and recording calls reserve that boundary before their output arrives, including failed calls. The live `present` event carries the call's public `toolCallId`, and the message stores `imagePlacements: [{ attachmentId, toolCallId }]`. Replies saved before every image recorded its call are paired in order with their completed `share_image` or `display_image` calls when each source matches its calls one for one; shown images are not paired while any `generate_image` call has no placed image (`renderer/shared/image-placements.ts`). Anything else trails the reply. Paired desktops retain the attachment's projected `toolCallId` as a message image placement; malformed optional placements are dropped without dropping the image. Phones get the same placement as each assistant image attachment's `toolCallId` (Remote contract revision 44) and draw the image beneath that step. On the desktop an assistant image is message-sized, like a photo in Messages: its natural shape within 22.5rem by 20rem at the start of the column, with its name and hover icon actions (Expand, Copy, Save) below; Bot chats use the same image view. The generate_image placeholder uses the same box.

Each image is capped at 20 million decoded pixels. A response is capped at 8 MB and 40 million decoded pixels; a chat is capped at 32 MB, 64 million decoded pixels, and 100 assistant-displayed images. Durable in-flight stages share the same 32 MB and 64-million-pixel process-wide ceilings.

No raw local path, `file://` URL, SVG, or model-authored remote URL crosses into image rendering.

## Current HTML path

Design and roadmap: [Inline Generative UI](superpowers/specs/2026-10-08-inline-generative-ui-design.md). Phase 1 (desktop inline HTML) is described here.

1. **Availability.** `prepareGeneration` contributes `aiden.gui.generative-ui` to every attended desktop chat, with or without a workspace, subject to Settings → Appearance → **Inline visuals**:
   - **Automatic** (default): the tools are always registered.
   - **Only when I ask**: registered only on `/visualize` turns.
   - **Off**: never registered.

   The mode travels as `GenerationParams.inlineVisuals`. Telegram, Assistant, Bots, scheduled runs, and child agents do not inherit the extension. Reading a workspace `.html` file (`path`) still requires a workspace with file access.
2. **Tools.**
   - `render_artifact({ title, html } | { title, path }, layout?)` validates UTF-8 HTML (512 KiB), rejects remote scripts, frames, `<base>`, `<link>`, refresh `<meta>`, a remote `src`, and `javascript:` / `data:text/html` URLs where a browser would load or run them. The check (`main/services/generative-ui-html-scan.ts`) reads the markup with parse5, the HTML parser the browser follows, so comments, `<textarea>`/`<title>` text, `<style>`/`<script>` bodies and SVG or MathML content (where `<style>` and `<script>` hold markup) count exactly as the browser sees them: a tag inside a comment or a code sample is inert, and one inside SVG `<style>` or a `<template>` is real. Each start tag is also checked as the tokenizer reads it, so a tag parse5 drops inside a `<select>` but Chromium builds there (an `<img onerror>` or an `<iframe>` in a customizable select) is refused, and an `<svg>`, `<math>` or `<style>` inside a `<select>` is built by parse5's in-body rules, as Chromium builds it, so what it holds is read as SVG, MathML or CSS: an option with an icon or a select with a style sheet is admitted, while a script, link, `<set>` or `url()` inside is refused. Inside an `<svg>` or `<math>` in a `<select>` only SVG and MathML are admitted, since Chromium reads any other tag there by its in-body rules where parse5 reads it by the select's: an HTML start tag parse5 does not read as SVG or MathML (a `<div>` in a `<desc>`, an `<img>` in a `<foreignObject>` or MathML text, a `<b>` that leaves the `<svg>`) is refused, and so is an end tag that closes no SVG or MathML element there (`<option><svg></option>`, `</p>`, a `</select>` inside a `<foreignObject>`), with advice to keep only SVG or MathML there and close each with its own end tag; an icon closed with its own `</svg>` is admitted, and the host's closing markup after a visual does not refuse what its streamed draft admitted. Outside a `<select>`, an end tag that names an SVG or MathML element around an open HTML element (`<svg><title><b>x</title>`, `<math><mtext><span>x</mtext>`) is refused, since parse5 matches it by name and closes the HTML with it where Chromium ignores it and stays in the HTML; a `<title>` or `<mtext>` whose HTML is closed first is admitted. An `<xmp>`, `<title>`, `<noembed>`, `<noframes>`, `<noscript>`, `<plaintext>` or `<textarea>` in a `<select>`, also inside an SVG `<foreignObject>` or MathML text there, is refused with advice to move it out of the select, since Chromium reads its content as text where parse5 reads markup and comments. It looks at each element the parser creates, the `href`, `src`, `action`, `formaction`, `xlink:href` or `data` attribute (as the URL parser reads it), CSS `url()`, an SVG `<set>`/`<animate>` of `href` under any prefix (`xlink:href`, or `q:href` in XML a script parses, where any prefix can name XLink), and JavaScript in `<script>` or an `on*` handler that sends such a URL to `open`, `location`, `assign`, `replace`, `navigation.navigate`, `setAttribute("href"/"src", …)`, `.href`/`.src` or `href.baseVal`, sets an `on*` attribute (through `setAttribute`, `setAttributeNS`, or an attribute node's `value`, `nodeValue` or `textContent`, as in `attributes.onclick.value`, `attributes["onclick"].value`, `getAttributeNode("onclick").value`, `getAttributeNodeNS` or `getNamedItemNS`, or an `Object.assign` onto such a node) to a handler that does so, or writes such markup through `innerHTML` (a bare `innerHTML =` inside `with` included), `outerHTML`, `srcdoc`, `insertAdjacentHTML`, `document.write`, `execCommand("insertHTML", …)` or `DOMParser`'s `parseFromString`. An `Object.assign` key is a sink too, named or computed (`{["innerHTML"]: …}`), and so is a `location` key (`Object.assign(window, {location: …})`). `parseFromString` reads its string as HTML when the type is `text/html`. The XML types it parses (`text/xml`, `application/xml`, `application/xhtml+xml` and `image/svg+xml`) are checked only if the XML names the XHTML, SVG or MathML namespace (an RSS or Atom feed that declares the XHTML namespace, as `xmlns:xhtml` does, is checked too, so its channel `<link>` is read as an HTML link and a CDATA section holding a `<p>` is refused, as an Atom feed's XHTML `<link>` is), and then as HTML with element prefixes of any characters dropped (so `<x:iframe>` and `<x.y:iframe>` are iframes) and each prefixed URL attribute (`q:href`) read as well; XML with a DTD internal subset (a `[` in the DOCTYPE outside its quoted IDs, so a `<` or `>` in a system or public ID does not hide one after it, in every XML type including `application/xhtml+xml`), an `<!ENTITY>` or an `<!ATTLIST>` declaration is refused, and so is namespaced XML that HTML would read partly as text where XML reads markup (a self-closed or markup-holding `<style>`, `<script>`, `<textarea>` or `<title>`, a character reference in a `<style>` or `<script>`, or a CDATA section that holds `<` or `&`), with advice naming what to remove. A well-formed XML comment is dropped before that reading, so what it names (`<!-- icons never use <script> -->`, `<!--TODO:link-->`) is not read; a malformed one (holding `--`, or unterminated), `<!-->` and `<!--->`, which HTML ends at once, stay as text and are read. A processing instruction or DOCTYPE is kept whole, so a `<!--` inside starts no comment, and one that holds `<` or `>` before its XML end is refused, since HTML ends it at the first `>` and reads what follows as markup (`<?xml?>`, `<?xml-stylesheet?>` and an external DOCTYPE are admitted); one with no end stops the reading there, and the rest stays as text and is read. A type that is computed, or that a spread argument may supply, is read both as HTML and as XML; any other type throws and is not read. The literal is followed however the call is written: an optional call (`write?.(…)`), a method named in brackets (`el["setAttribute"](…)`), a parenthesized callee (`(el.setAttribute)(…)`, `(0, open)(…)`), a bound one (`el.setAttribute.bind(el)(…)`) or the sink's `.call` (`el.setAttribute.call(el, …)`, `document.write.call(document, …)`), with the arguments shifted to match, a spread array argument (`el.setAttribute(...["onclick", …])`, where an empty spread array is no argument and a trailing comma no element), a tagged template (also read raw, as `String.raw` passes it), a literal wrapped in a trivial expression (`(…)`, `(0, …)`, `a || …`, `a ? … : …`, an array or a template substitution), or strings joined with `+`, which are checked one by one and joined, also after a value (`"<p>" + name + "</p><ifr" + x + "ame …>"`, `"java" + ["script:…"]`), and the literals written to one URL sink are joined across the brackets and `+` between them (`'java' + ('script') + ':…'`), while one after a value (`base + 'javascript:…'`) is not read as where the URL starts; a line break after `await` does not end the statement, as it does not in the browser. An `on*` attribute node made with `createAttribute` or `createAttributeNS` is refused outright. Not followed: names and values computed at run time, variables, destructuring targets, an SVG `<set>` whose `to` is set with `setAttribute`, `.apply` and `Reflect.apply`; the guest CSP below is the backstop there. Markup or a handler a script writes is checked the same way, three levels deep, and one nested deeper is refused as too complex to check rather than admitted unread (string escapes (legacy octal ones such as `\74` and braced code points such as `\u{0003c}` included), names spelled with `\u` escapes and joined strings are read as the engine reads them, and a `/` right after an `if`, `while`, `for` or `with` head starts a regular expression, as it does in the browser, so a quote inside one cannot hide the code after it (a keyword read as a property, as in `o.if()` or `[1, 2].with(0, 3)`, is a method call, so the `/` after it divides); `<!--` anywhere and `-->` at the start of a line begin a line comment, as in a classic script; and where a `/` could either divide or start a regular expression (after `}`, a `)` that closes no head, a `++` or `--`, or a name such as `of`, `yield` or `await`), the script is read both ways and refused if either reading sends such a URL or markup to a sink, while a script with too many such places to read both ways is refused as too complex to check). Markup nested more than 512 elements deep, a tag with more than 512 attributes, more than 262,144 elements, or more than 16,384 pieces of content the parser moves out of a table (foster parenting) is refused as too complex to check, so the check stays fast at the 512 KiB cap. A complete document (`<!doctype>`, `<html>`, `<head>`, `<body>`) is unwrapped to its body plus the head's inline `<style>` and `<script>` elements. The check reads the bytes that render, where they render: the unwrapped fragment and the markup as written (what a streaming draft showed), each placed after the guest head's `<body>` and before the wrapper's closing tags (and, when the markup has a `<noscript>`, read a second time with scripting off, as a viewer or exported page with scripts turned off reads it), so a `<body>` inside a comment, `<textarea>`, `<title>`, script string, style comment or attribute value cannot carry markup past it. The stage, the store, the wrapper (preview, snapshot, phone viewer) and export all take that verdict, and the last few verdicts are cached so the same visual is read once. That step, the check and a streaming draft's check all run in linear time, so any input under the cap is handled in well under a second. A draft reads a start tag that is still being written on every chunk while it is under 1 KiB, and after that each time it has doubled, so an unsafe unfinished tag still stops the draft early without a long one being reread per chunk; the browser shows no element for a tag until it ends, and the finished tag is always read in full. While a tag, comment, script or word is unfinished, a draft holds the short chunks it is sent (the parser would recopy everything since the last finished piece for each one) until it has 8 KiB or as many characters as are unfinished, then checks them together; it shows only text it has checked, and the rest when the call ends. A label such as "JavaScript: 41%" (in text, `aria-label`, an `<option>` or `textContent`), `i<base && i>0` in a script, or `const src = "https://…"` passes. A refusal quotes the refused markup in its error (a CSS `url()` up to the end of its declaration), and says so when a script joins that markup from strings, since the source never spells it in one piece. The tool stages accepted bytes in `generative-ui-artifacts.json` (`0600`), and emits a `kind: "html"` `ChatArtifactEventV1` with an opaque `mediaId`. Its tool result is text only.
   - `visualize_guide({ modules })` returns design, HTML, chart, and interactivity guidance on demand (`main/services/generative-ui-guide.ts`), which keeps the system prompt short.

   Replay is `"never"` for both tools.
3. **Placement.** Each visual renders right after the activity row of the `render_artifact` call that produced it.
   - The message stores `htmlArtifactPlacements: [{ mediaId, toolCallId, layout? }]` beside `htmlArtifacts`, never inside it, because older builds drop the whole artifact list on an unknown key. The placement parser ignores unknown keys, so later fields never drop a placement.
   - Placement ids are the timeline's public `call-N` ids. `generative-ui-placements.ts` translates Pi's raw ids.
   - Artifacts with no placement or no matching step trail the response.
   - The live `present` event carries `toolCallId`.
   - **Width.** `layout` is `column` (default: the reading column, about 690px) or `wide`. A wide visual spans the chat pane inside a 1.5rem gutter, up to 80rem, and follows the window. It measures the pane through a size container on the transcript's scroll content, and stays in the column beside a docked Quick View card. Only `layout: "wide"` is stored. A same-title revision keeps its first position but takes the latest layout. Drafts follow the layout as soon as the streamed arguments name it.
4. **Preview.**
   - The renderer loads a **main-built** preview over `chats:htmlArtifactSrcdoc`. Main wraps the HTML and serves it from `aiden-genui://preview/<64-hex-token>` (`generative-ui-preview-store.ts`), with the guest CSP as a **response header**.
   - The iframe uses `src` (not `srcDoc`) and `sandbox="allow-scripts"` only. Parent `script-src` is not widened, and parent `frame-src` is `'self' aiden-genui:`.
   - Guest CSP sets `connect-src 'none'` and allowlists only the exact host-library URLs.
   - The frame is borderless and as tall as its content (64–1600px). The title, Expand and Export sit in a caption row below it. A neutral focus ring shows when focus arrives in the guest by Tab; a click into a visual draws none (the host cannot see focus moves inside a cross-origin guest).
5. **Guest bridge.** A host script injected before any model code:
   - reports content height;
   - relays Escape;
   - announces `ready` so the host can send the theme before the document loads;
   - applies live theme messages from the parent, which send allowlisted, sanitized semantic tokens (`renderer/shared/generative-ui-theme.ts`);
   - exposes a frozen `window.aiden` with `sendPrompt`, `theme` and `series`.

   The host accepts only the closed message schema in `generative-ui-bridge.ts`, and only from that frame's window. `sendPrompt` never sends by itself. A visual can never send as the user. Browser signals cannot prove which frame the user acted in: a sandboxed guest can `focus()` itself, `navigator.userActivation` is page-wide, and out-of-process frames hide hover from the page (three review rounds broke heuristics built on them, including in Electron). So an admitted request (at most 2,000 characters, one per 3 s per visual, `admitGuestPrompt`) only shows an Aiden-drawn confirmation chip under the visual quoting the text, with **Send** and **Dismiss**. The user's click on that app UI sends a normal visible turn through the composer's send path. While a run is starting, running, detached, or queued, the action reads **Add to draft** and puts the text in the composer instead. A newer request replaces the pending one.
6. **Kit.** Main serves `aiden-genui://aiden-ui.css`, a generated class kit that mirrors the shared components (`generative-ui-kit.ts`). When no renderer theme is supplied (export), the light default tokens are emitted.
7. **Streaming drafts.** While `render_artifact` arguments stream (and only when the tool is registered for the turn), main writes the partial HTML into a single-use draft preview whose CSP allows only the bridge's nonce. Partial markup renders progressively, and model scripts wait for the final artifact. The `draft` and `draft_end` events carry only the preview URL; draft HTML never reaches the renderer as a string. The presented artifact replaces the draft in the same row: the `present` event carries a ready preview URL (`src`), and the final frame starts at the draft's last height.
8. **Libraries.** Host Chart.js, Plotly, and KaTeX load from the `aiden-genui:` protocol (exact library names). Export inlines those libraries and the kit into one offline `.html` file and fails if a library is missing. There is no CDN.
9. **Persistence and clients.** Persistence stores metadata, the `mediaId`, and placements on the assistant message. Pending HTML stages share the existing image-recovery composer gate. Since Remote contract revision 28, paired devices show each visual as its snapshot image (see "Snapshots and paired devices" below); a client without the snapshot still shows the title plus “Can't view on this device. View in Aiden Agent.”

Limits: 4 HTML artifacts per response, 40 per chat, 8 MiB staged HTML per chat, titles 1–120 characters without controls.

## Native visuals (`render_ui`)

The model composes a visual from Aiden's own component catalog instead of writing HTML. The guide and system prompt tell it to prefer `render_ui` and keep `render_artifact` for custom drawing or scripting.

1. **Markup.** `render_ui({ title, layout?, markup })` takes Aiden UI Markup (AUM): JSX-like catalog elements, `{expressions}` over `<Data name="…">{json}</Data>` and `<Visual state={{…}}>`, and actions (`sendPrompt`, `setState`, `openUrl`, `copy`). The catalog (`renderer/shared/aiden-ui/catalog.ts`) is the single source of truth. The `visualize_guide` `catalog` module is generated from it, including the shape of one item for each list prop (a `Checklist` item is `{label, done}`, a `Sparkline` takes numbers), and a test keeps the guide's example compiling cleanly.
2. **Compiler.** `renderer/shared/aiden-ui/` holds the shared pure TypeScript used by main, the renderer and the CLI:
   - **Parser (`parse.ts`).** Tolerant: auto-closes elements at a stream cut, drops an unfinished attribute, and treats `Data`, `Code`, `Math` and `Markdown` bodies as raw text.
   - **Expressions (`expression.ts`).** Expressions become a JSON AST and never JS. There is no `-`, `*`, `/`, method call or arrow function.
   - **Compile (`compile.ts`).** Unknown elements are dropped but their content kept; bad props are dropped. Every repair becomes a diagnostic returned to the model in the tool result. After the visual is drawn, `render_ui` also runs the artifact page check (`main/services/workspace-artifacts/check.ts`) against the visual's own data and state, and adds each read that draws empty (a misspelt field, a list read as an object, an unknown `$name`, a list prop whose items are text or lack the fields the component draws) under a "Visual check" heading, so a blank chart is not reported as a plain success. A second `render_ui` call in the same reply with the same title replaces that visual in place, and its result says so. That call may send `edits` instead of `markup`: up to 32 `{ old, new }` replacements applied in order to the markup the visual was last drawn from in this reply, all or nothing (an `old` that is missing or matches more than one place draws nothing, and the error names that edit). The markup is held only by that reply's tool, so a visual from an earlier reply is redrawn with whole markup.
   - **Evaluator (`evaluate.ts`).** Pure, own-properties only, prototype keys blocked, with a step budget and a 10,000-item list cap. Its semantics are pinned by `fixtures/expressions.json`, which the Swift and Kotlin ports will reuse.
   - **Fallback text (`fallback-text.ts`).** Renders the visual's initial state as Markdown-ish text for memory, the CLI and clients without a renderer.
3. **Contract.** `ChatUiVisualV1 { version, kind: "ui", id, toolCallId?, title, catalogVersion, tree, dataJson?, state?, fallbackText, layout? }` lives in the message field `uiVisuals`. It is parsed leniently per entry, so one bad visual never hides the others. Key names avoid every key Aiden Remote clients treat as private (`isWireSafeKey`), and the model's data is stored as a JSON string (`dataJson`) so its keys are never wire keys.
4. **Limits.** 2,000 nodes, depth 24, 64 KiB of data, a 256 KiB tree, 4 KiB of state, 8 visuals per response and 60 per chat; `<Each>` repeats at most 500 times.
5. **Live.** While `markup` streams, main compiles drafts every 250 ms and sends `ui_draft` events; `draft_end` retracts them. The presented visual arrives as a `ui` event, and a same-title revision keeps its first id and position.
6. **Renderer.** `AidenUiBlock` (`renderer/components/aiden-ui/`) draws the tree with the shared primitives in `ui.tsx` and `ui-primitives.tsx`. Visuals are placed after their tool row like HTML visuals.
   - Bound inputs and `setState` run locally.
   - `sendPrompt` goes through the shared visual follow-up path, and is added to the composer while a reply runs.
   - `openUrl` accepts only https links and always asks first.
   - `copy` uses the clipboard.
   - Local state is saved 800 ms after the last change (`chats:updateUiVisualState`).
   - Charts use a lazily loaded Chart.js with the live `--chart-1…8` tokens, and every chart has a screen-reader table of its numbers.
7. **CLI.** `render_ui` compiles with the same compiler and prints the fallback text.
8. **Safety.**
   - **The compiler never throws.** Flattened unknown elements count toward the depth cap, and the parser stops nesting past 64 open elements.
   - **Renders are budgeted.** One render draws at most 2,000 loop iterations and 4,000 components in total, so nested `<Each>` cannot multiply.
   - **Follow-ups need confirmation.** A native button's `sendPrompt` waits in the same Aiden-drawn confirmation chip as HTML visuals, because its label is model-written and need not match the text it sends.
   - **Saved state follows the newest copy.** A newer saved state re-seeds an untouched visual. In a visual the user has changed, it fills in only the keys that are missing.
9. **Downgrade.** Older builds rebuild messages from the fields they know, so an older build that rewrites a chat drops `uiVisuals`. A reply that was only a visual then shows as an empty bubble there. HTML visuals only lose their placement.

## Snapshots and paired devices

1. **Capture.** After a reply commits, main renders each of its visuals in a hidden, sandboxed window on the default session (`main/services/visual-snapshot-main.ts`): HTML visuals in their sandboxed frame, inline as the desktop draws them, with charts drawn at their final values; native visuals through `visual-snapshot.html`. Both use the light theme at 720 px (column) or 1024 px (wide), at the display's scale. The guest is inlined as `srcdoc` in a data: host page whose CSP is the guest policy (host libraries, no network) framing only that document, and the window refuses every other frame navigation, so a guest stays offline here exactly as it does in the main window. Captures run one at a time, each with a 6 s timeout, and never delay the reply. A capture that times out or whose chat is deleted destroys its own window, so a runaway guest cannot stall the next capture. When only this hidden window is left and closing should quit, it is released so the app quits.
2. **Storage.** Each image is an ordinary PNG (JPEG over 2 MiB) attachment on the same message with a reserved `visual-snapshot_<sha256>` id, linked by `visualSnapshots: [{visualId, attachmentId}]`. The desktop hides a snapshot only beside the visual it pictures (`attachmentsShownWithVisuals`), so a paired Mac's chat still shows it as an image. Snapshots never count against image limits and never reach the model.
3. **Remote.** Contract revision 28 (`chat-visuals-v1`) projects `visuals` on each assistant message: kind, title, the tool call that drew it, fallback text, and the snapshot attachment id. Markup, data and saved state stay on the Mac. A new snapshot changes the chat revision.
4. **Phones.** iOS and Android place each snapshot after its tool row, fall back to the text description, and hide snapshot attachments from the attachment strip.
5. **Remote turns.** Turns sent from a paired device follow the Mac's Appearance setting, and the model is told those readers see still images, so the first view should carry the answer.

## Extension points

- Add future payloads to the closed `ChatArtifactV1` union in `renderer/shared/chat-artifacts.ts`; do not weaken an existing parser. Interactive HTML widgets use kind `"html"` and a sandboxed frame, not Markdown HTML.
- Keep the live operation envelope versioned independently from artifact payload versions. Its reserved `reset` operation may be used only when the host can prove that the corresponding presentation effect was rolled back; an ordinary provider retry is not such a rollback.
- Contribute GUI tools through a chat-scoped `PiAgentRuntimeExtension`, not `buildAgentTools` or the process-global extension registry.
- Give each artifact kind a main-owned authority check, bounded transport, durable representation, renderer parser, accessible fallback, and live/reload/deduplication tests.
- Keep large or seekable media out of Pi history. HTML bytes stay in the app-owned store and cross the renderer only as a main-owned `aiden-genui://preview/` URL, never as renderer-concatenated `srcDoc` or a workspace `file://` path.
