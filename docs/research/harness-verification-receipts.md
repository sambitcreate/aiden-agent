# Host verification receipts (H2a)

The host stores version 1 receipts in `pi-verification-receipts.json`, beside the existing effect journal, with mode 0600. Existing readers of the effect journal remain compatible: its schema and Remote protocol are unchanged. No receipt is serialized into transcripts or advertised to desktop, CLI, iOS or Android as task acceptance. These consumers continue to see lifecycle completion with its existing meaning. A future presentation change must include all clients and additive wire compatibility.

Every managed operation using the production effect journal records an immutable `response_ended` receipt. Its `lifecycle_only` limitation explicitly separates successful lifecycle completion from correctness. Terminal operations are the durable publication outbox: startup backfills missing receipts even if a previous receipt publication failed after the effect journal committed. Restart interruption records an inconclusive lifecycle receipt. This never replays a tool or external write. A missing receipt is unavailable evidence, never an inferred pass.

The actual `run_command` process runner brands its observed exit/output in a module-private WeakMap. The production harness consumes that observation before extension result patches, retaining a `tool_execution` receipt with `command_only`. Exit 0 passes that particular command; nonzero fails it; timeout/output-limit/unknown exit are inconclusive. Model-authored result details cannot forge this brand. The receipt snapshot identifies immutable command-result bytes, not a claim about the current workspace.

`PiVerificationStore.check` is an internal host API, absent from agent tools. Host code supplies the artifact identity, complete artifact digest callback, and actual observer. Only the observer's result becomes a check receipt; model prose and tool return strings cannot manufacture one. `artifact_check` and `task_predicate` express explicit checks; `tool_execution` carries `command_only`. The host must not classify a zero exit code as acceptance of unrelated requirements. Observation exceptions become inconclusive without retaining error text. Pre-dispatch cancellation records not-run; cancellation after observation starts records inconclusive. Artifact changes during observation invalidate the result. Later edits are detected by `inspect` against a newly computed digest.

Raw output is retained only through the existing ToolOutputStore implementation in a separate private `pi-verification-evidence.json` namespace, preventing independent store caches from interfering with ordinary tool output. Receipt metadata has opaque bounded identities, a SHA-256 snapshot, closed result/kind/limitation enums, timestamp and optional handle; no command, path, arguments or error text. Authorized host reads require the original chat and authority scope; callers must revalidate their current authority before passing that scope. `readEvidence` returns bounded windows. Missing or evicted evidence is explicit in `inspect`. The host must inspect evidence availability and artifact freshness before using an old passed check in an acceptance decision.

Receipts and output expire after seven days and are bounded to 512 receipts and existing output byte/count bounds. Chat deletion and orphan reconciliation revoke in-flight publication immediately, then delete private receipts and evidence; an observer completing afterward cannot resurrect either. Corrupt or unknown-version receipt files are preserved and rejected, never normalized into passed results. Duplicate delivery in a process is serialized and returns the immutable receipt without rerunning the observer. A reused check identity with different ownership is rejected. Check IDs identify observations, so a new check of an edited artifact requires a new ID.

Validation is deterministic offline evidence, not model-quality measurement. Focused behavioral suites cover success/failure, cancellation, changed snapshots, restart, duplicate delivery, redaction, revoked scopes, missing/expired evidence, corrupt receipts and production effect-journal integration. Production harness suites remain separate from the protected six-task evaluation and live pilot.
