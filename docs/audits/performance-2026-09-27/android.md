# Android performance and optimistic interaction audit

Audit date: 2026-09-27. Baseline: `a9baa4aa3027893e5455043083465c34b4c8b4ac`. Scope: Android native client, read-only source audit; no product changes, real account actions, device interaction, or network requests. File references below are repository-relative, with exact baseline line numbers. `A/` abbreviates `android/app/src/main/java/sbtbiswas/AidenOnTheGo/`.

## Assessment and evidence boundaries

The strongest immediate opportunities are synchronous draft/transcript disk work on Main, image preparation on Main, and invisible tabs initiating their own loads. Long-session memory and large-workspace row composition are also structurally unbounded by the visible viewport. Existing stream transport and summary/image caches already contain meaningful performance work; replacing them wholesale would risk correctness without evidence.

These are source-supported execution paths and complexity observations, **not measured frame drops, ANRs, battery drain, memory leaks proven by a heap dump, or latency improvements**. No runtime suite was executed for this documentation-only audit. Physical-device cold/warm navigation, frame timing, allocation and energy baselines remain unmeasured. Read the root `AGENTS.md`, plan inventory, existing performance plan, current `.memory/upgrade-35-android-state.md`, `.memory/mobile-stream-recovery.md`, `.memory/chat-scroll-follow.md`, `.memory/upgrade-14-android.md`, and `.memory/upgrade-16-android-sse.md`. Current implementation and those focused memories supersede the older project summary where they differ.

Historical measurements in `docs/testing/aiden-on-the-go/chat-summary-performance.md` are **2026-09-01 JVM fixture results, not fresh Android-device measurements**: medium full-list decode 14.616 ms / 32,383,248 allocated bytes; first summary page 0.344 ms / 481,608 bytes; cached summary hydration 1.413 ms / 1,441,696 bytes. Preserve that distinction in any release claim. The current benchmark harness remains in `android/app/src/test/java/sbtbiswas/AidenOnTheGo/AidenChatSummaryTest.kt:525`.

## Ranked findings

Effort: S = localized change with focused tests; M = multiple owners/lifecycle or renderer changes; L = persistence/recovery architecture. Priority reflects likely impact and exposure, not an observed timing threshold.

### AND-01 — P1: every draft edit performs synchronous disk work on Main

- **Evidence:** `A/features/chat/AidenChatViewModel.kt:664` assigns the draft and directly calls `draftStore.save`. `A/persistence/AidenChatDraftStore.kt:81` synchronizes save; `:97` serializes the envelope; `:101` writes bytes directly. `:166` additionally counts code points and encodes UTF-8 for bounds. Chat construction synchronously hydrates draft and transcript at `A/features/chat/AidenChatViewModel.kt:206`. These calls originate from the Compose composer/voice callbacks, including `A/features/chat/AidenChatDetailScreen.kt:278`.
- **Impact:** typing or dictation repeatedly hashes/validates/serializes/writes the entire draft on the UI thread. The current bounds are 100,000 scalars / 400,000 bytes (`A/persistence/AidenChatDraftStore.kt:39`). Work scales with draft length and edit count; disk latency sits directly on the input path.
- **Recommendation:** publish draft state immediately; serialize ordered latest-value persistence through an IO owner with a small bounded coalescing window. Use atomic replacement and explicitly flush send-clear, failed-send recovery, app background and owner close. Reserve generation/sequence authority before queueing IO.
- **Risk:** naïve debounce loses recently typed data at process death; naïve background writes resurrect a cleared or removed draft. Preserve the recently fixed durable failed-send reconciliation and session/purge fencing.
- **Validation:** extend `AidenChatTest` held-POST and restart tests with rapid edits, send-clear followed by newer input, delayed write after purge and process-restart reads. Add a debug StrictMode/main-thread IO probe and device typing trace at 1k/100k scalars; count disk writes and bytes per edit burst.
- **Confidence:** high. **Effort:** M.

### AND-02 — P1: transcript acceptance synchronously persists the full chat and summary cache

- **Evidence:** Main-scoped `loadChat` (`A/features/chat/AidenChatViewModel.kt:701`) calls non-suspending `acceptRemoteChat` (`:1828`), which calls `chatCache.saveChat` before publishing the chat. `A/persistence/AidenChatCache.kt:371` holds the cache monitor; `:386–401` updates admitted state, serializes the full transcript and calls `saveSummaries`. Atomic file writing includes `fd.sync()` at `:725`. The send receipt path also calls `acceptTurnReceipt` from Main (`A/features/chat/AidenChatViewModel.kt:838`). Summary persistence scans/hash-verifies retained chunk files (`A/persistence/AidenChatCache.kt:248–278`).
- **Impact:** receipt/terminal reconciliation and initial detail loads can block UI on JSON, filesystem, fsync and summary work. IO summary pagination can also hold the same synchronized cache monitor while a Main caller waits. A 10 MiB individual cache-file limit (`A/persistence/AidenChatCache.kt:85`) is a safety bound, not a responsive Main-thread budget.
- **Recommendation:** separate synchronous in-memory admission from ordered background durable writes, or provide a serialized suspending cache API and await it off Main while retaining ownership checks. Keep summary/token reservations at request admission, not after an IO await; batch companion summary persistence.
- **Risk:** moving only the call into `withContext(IO)` without preserving write-token, accepted-receipt, removal and purge semantics can reintroduce the races documented in `.memory/mobile-stream-recovery.md`. UI must continue using admitted authoritative data even if best-effort persistence fails.
- **Validation:** preserve held-load/terminal/receipt/delete regressions in `AidenChatTest` and summary ordering tests; add a held disk-writer test proving Main stays usable and a later deletion defeats a queued write. Profile terminal reconciliation on a maximum-size synthetic chat plus 10,000 summaries.
- **Confidence:** high. **Effort:** L (correctness-sensitive).

### AND-03 — P1: selected-image preparation resumes on Main and can fully decode a 40-megapixel source

- **Evidence:** `A/features/chat/AidenChatDetailScreen.kt:244–262` launches from the Compose scope. Only `readContentUriBounded` switches to IO (`:1658`); `imageUpload` is invoked directly afterward (`:257`). `A/features/remote/AidenChatFeature.kt:13–16` permits 32 MiB source images and 40,000,000 pixels. `:54` performs full `BitmapFactory.decodeByteArray`; `:56–84` repeatedly scales, PNG/JPEG-compresses and Base64-encodes candidates. This is separate from the already optimized transcript thumbnail decoder.
- **Impact:** large HEIC/other conversion or oversized PNG/JPEG preparation can monopolize Main and allocate a full source bitmap plus scaled/encoded intermediates. A 40 MP ARGB_8888 bitmap alone would be about 160 MB; actual decoder configuration/peak allocation is unmeasured.
- **Recommendation:** query metadata/read on IO; perform image validation/decode/compress/Base64 on a bounded Default worker. Decode sampled toward the largest accepted output edge before allocating full pixels. Release intermediates reliably, show an attachment-specific preparing state immediately, and keep bounded serial or very small concurrency.
- **Risk:** preserve alpha, orientation, server byte/dimension checks, ordered attachment selection and cancellation. Do not process ten large images in parallel to hide latency.
- **Validation:** synthetic oversized JPEG, alpha PNG, rejected dimensions, cancelled selection and ten-item batch; device peak RSS and frame trace during conversion. Extend attachment tests with output size/content invariants rather than private implementation matching.
- **Confidence:** high. **Effort:** M.

### AND-04 — P2: both product tabs remain composed and fetch while one is invisible

- **Evidence:** `A/features/remote/AidenProductShellScreen.kt:178–211` always composes Workspaces and Bots and changes only alpha/z-order/accessibility. `A/features/workspaces/AidenWorkspaceHomeScreen.kt:220` hydrates/loads on connection changes; `A/features/bots/AidenBotsHomeScreen.kt:314` loads Bots. Workspace loading starts summary, scheduled-task (when permitted), usage and model requests (`A/features/workspaces/AidenWorkspaceHomeViewModel.kt:193–210`); Bots starts two more (`A/features/bots/AidenBotsViewModel.kt:88–89`).
- **Impact:** initial tab availability shares bandwidth/CPU with the hidden surface and retains both trees and state collectors. The static fan-out is up to six requests for these two surfaces alone; it is not six continuously recurring requests. Existing loaded-client deduplication limits repeated loads. This is hidden-but-composed tab work in the foreground; it does not establish periodic OS-background fetching.
- **Recommendation:** keep view state/cache retained for fast switching, but gate initial refresh and active collection on selected surface. If prefetching the other tab is useful, make it a bounded deferred policy after visible content is ready. Publish independent Bot list/conversation results as each completes: today both awaits precede either publication (`A/features/bots/AidenBotsViewModel.kt:90–97`).
- **Risk:** avoid resetting scroll/search on tab switch and avoid suppressing explicitly needed notifications; connection/capability changes must still invalidate cached authority.
- **Validation:** held MockWebServer responses prove first visible tab does not wait for hidden requests; count requests on launch, tab switch and reconnect. Device trace for time-to-first-visible-list and memory with each tab selected.
- **Confidence:** high. **Effort:** M.

### AND-05 — P2: “show all” workspace chats are children of one lazy item

- **Evidence:** `A/features/workspaces/AidenWorkspaceHomeScreen.kt:502` creates one lazy item per workspace section. `:876–882` chooses the entire chat list after reveal-all; `:884` wraps the section in a Column; `:932` composes every visible chat with `forEach`. The default preview limits work, and recents already use independent keyed lazy items at `:530`.
- **Impact:** a single large expanded workspace can compose/layout all its chats even when most are off screen. The overall summary cache permits 10,000 rows, so viewport virtualization is lost exactly on the high-cardinality route.
- **Recommendation:** flatten workspace headers, chat rows and show-more controls into one stable-key lazy sequence; retain expansion/reveal/search state separately. Add `contentType` where it improves measured reuse.
- **Risk:** preserve accessibility grouping, scroll restoration and stable chat identity while sections expand/reorder.
- **Validation:** extend `AidenWorkspaceSidebarUiTest` with one workspace containing 2,000 rows, reveal-all, scroll, collapse/reopen and search. Measure composed-row count and frame timing; require work to scale with viewport plus bounded prefetch rather than section size.
- **Confidence:** high. **Effort:** M.

### AND-06 — P2: chat navigation retains activity-owned ViewModels and full-detail cache entries

- **Evidence:** detail calls `viewModel(key = installation/device/chat)` without a route-scoped store (`A/features/chat/AidenChatDetailScreen.kt:110`). The app uses `AnimatedContent` over a `currentScreen` value (`A/MainActivity.kt:76`, `:166–222`), not a per-destination ViewModelStore. Disposal stops only standalone progress observation (`A/features/chat/AidenChatDetailScreen.kt:217`); normal stream/reconciliation jobs stop in `onCleared` (`A/features/chat/AidenChatViewModel.kt:610`). `A/persistence/AidenChatCache.kt:101`, `:118`, `:388–400` retain complete chats in maps with no LRU/total-byte eviction; this cache instance is constructed by the activity and shared among screens (`A/MainActivity.kt:53`), separate from each per-chat ViewModel’s fields; the per-file 10 MiB cap does not bound the aggregate.
- **Impact:** browsing many chats can retain many full transcripts, catalogs, StateFlows and notification collectors until the activity store is cleared. Navigating away does not cancel active stream consumption; that can be intentional for live notifications, but each retained owner needs an explicit budget/policy.
- **Recommendation:** separate active run ownership from screen presentation; use route-owned or bounded reusable presentation models and a byte-budgeted detail cache. Preserve active stream identities and short-term warm reuse while evicting completed inactive transcripts/catalog duplicates. Define background behavior explicitly (bounded notification/run owner versus foreground-only presentation).
- **Risk:** blindly clearing a ViewModel on navigation breaks ongoing-turn notifications and warm reconnect; evicting ownership tokens can admit stale writes. This is a lifecycle redesign, not a request to cancel the server turn.
- **Validation:** navigate through 100 synthetic chats, force GC, inspect retained ViewModel/transcript count and heap; active turn continues exactly once, completed streams release resources, revisit restores draft/scroll, background/resume reconstructs from the accepted stream identity.
- **Confidence:** high for retention structure; medium for practical memory/energy severity. **Effort:** L.

### AND-07 — P2: stream deltas repeatedly copy/reparse growing response strings

- **Evidence:** each text/reasoning event concatenates the full StateFlow string (`A/features/chat/AidenChatViewModel.kt:1095–1102`). `A/features/chat/AidenChatDetailScreen.kt:1549–1553` constructs a regex, scans the complete message and formats it during composition; code-containing text reformats leading/trailing slices (`:1572`, `:1600`). Live chronological projection also runs for changing text (`:1160`). There is no explicit visual coalescing policy in the event reducer.
- **Impact:** cumulative copying for many small deltas grows with total prefix sizes; Markdown/code-rich live content repeats parse/allocation work. StateFlow conflation may already collapse some visual renders, so event rate does not imply equal recomposition rate.
- **Recommendation:** measure first; if confirmed, maintain bounded accumulation and publish visual snapshots at a frame/time budget while flushing terminal, approval, question and error transitions immediately. Cache completed formatting keyed by text/style; incrementally retain settled blocks if profiling justifies it.
- **Existing mitigation:** the live StateFlow collectors are inside the live lazy item (`A/features/chat/AidenChatDetailScreen.kt:727–730`), and persisted rows use stable keys. Do not describe the whole transcript as recomposing per token. Preserve the current reverse-list scroll-follow architecture.
- **Validation:** 2k/20k/100k-character synthetic streams with code/reasoning/timeline, bursts and tiny deltas; count reducer publications/parser calls and capture allocations/frame misses. Verify exact final text, immediate control events, snapshot replacement and no scroll jump while reading history.
- **Confidence:** high for repeated work; medium for visible impact. **Effort:** M/L.

### AND-08 — P1 correctness prerequisite for optimism: ambiguous sends/create-chat retries are not durably reconciled

- **Evidence:** send clears the composer optimistically (`A/features/chat/AidenChatViewModel.kt:801–810`), but all non-cancellation exceptions remove the optimistic row, restore the submitted draft/attachments and clear stream state (`:860–867`). `A/models/AidenChat.kt:1297–1316` retains one pending request/key in memory and changes the key when request contents change. A lost response followed by edits or process death can therefore lead to a new key without reconciling the first admission. Workspace create waits for the POST before navigation (`A/features/workspaces/AidenWorkspaceHomeScreen.kt:264–289`); `A/networking/AidenRemoteClient.kt:728–737` supplies a fresh default key on each invocation.
- **Impact:** a transport failure can mean “accepted, receipt lost,” not “failed.” Current same-request in-process retry is deduplicated, but edited resend/restart is not the same operation. Faster speculative UI must not increase duplicate work or suggest server rollback occurred.
- **Recommendation:** distinguish definite rejection from unknown outcome; retain an operation record/key and show a pending/reconciling row with recoverable draft. Reconcile server admission before allowing the old attempt to be replayed under another identity. For create, use a pending navigation shell and stable key; do not fabricate a server chat ID or let Send target it before admission.
- **Risk:** persistence may involve sensitive draft payloads; use existing app-private storage and purge rules. Protocol support for querying an admission may need shared server/iOS work. No automatic mutation retries beyond the existing idempotency contract.
- **Validation:** accept POST then disconnect before response; retry identical request, edit draft, kill/recreate owner, remove installation and switch device. Assert one accepted turn/chat per logical action and that newer text is never silently discarded. Extend production ViewModel/MockWebServer tests, then shared server and iOS tests if contracts change.
- **Confidence:** high for missing client distinction/durability; duplicate server work after a changed attempt depends on server admission state and is a risk to reproduce, not an observed incident. **Effort:** L.

## Existing mitigations to preserve

- Summary-first, capability-negotiated listing; disk hydration on IO (`A/features/workspaces/AidenWorkspaceHomeViewModel.kt:152`), bounded 200-summary chunks and 10,000 summaries (`A/persistence/AidenChatCache.kt:86–88`). Older-server fallback is intentional compatibility, not permission to silently downgrade advertised endpoint failures.
- Ordered cache admission and receipt/removal/purge fences; no per-SSE-event durable cursor writes. Cold replay starts from zero because partial buffers are not durable (`A/features/chat/AidenChatViewModel.kt:743–754`); warm reconnect uses the in-memory sequence (`:1016–1023`). Reintroducing per-token fsync would be a regression.
- SSE IO reader, suspending channel send/backpressure, and socket cancellation in `awaitClose` (`A/networking/AidenRemoteClient.kt:1030–1075`). Recent REST cancellation remains connected through body consumption (`:2016`); do not “optimize” back to a header-only cancellation lifetime.
- Progress SSE lifecycle starts/stops with screen foreground (`A/features/chat/AidenChatDetailScreen.kt:200–221`); voice and read-aloud stop on background (`:184–194`). Reconnect delays already back off, capped at 30 seconds (`A/models/AidenChat.kt:1256`); healthy-status but failing SSE may retry at one-second cadence (`A/features/chat/AidenChatViewModel.kt:1052`). Measure that partial-failure mode before adding retry jitter/foreground policy.
- Attachment requests deduplicate in flight and disk work runs on IO (`A/features/chat/AidenChatViewModel.kt:941–982`). Thumbnail decode runs on Default with sampling, 24-entry/32 MiB LRU (`A/features/chat/AidenMessageImageAttachments.kt:527–566`); attachment disk cache is bounded at 96 MiB (`A/persistence/AidenChatCache.kt:89`). These limits exclude referenced bitmaps and conversion intermediates, so they are not total process-memory guarantees.
- Bot search already waits 250 ms and cancels the prior request (`A/features/bots/AidenBotsViewModel.kt:124–138`). Home loads have loaded/in-flight-client deduplication (`A/features/workspaces/AidenWorkspaceHomeViewModel.kt:172–181`). Prefer bounded stale-while-refresh policies rather than new background polling.

## Additional profiling candidates, not promoted to proven user-impact findings

1. Coordinator lifetime: `MainActivity.kt:48–67` reconstructs stores/coordinator in `onCreate`, while `AidenRemoteCoordinator.kt:43` owns a private Main + Job scope and has no dispose method. Activity-owned ViewModels survive configuration recreation and retain their original coordinator. Instrument recreation and retained owners before choosing a single application/activity ViewModel owner; this could affect correctness as well as retained resources.
2. Catalog duplication: workspace home fetches models (`AidenWorkspaceHomeViewModel.kt:210`) and each newly opened detail fetches again (`AidenChatViewModel.kt:718`). A device/client-scoped immutable snapshot with explicit invalidation may remove repeat navigation requests; measure payload and hit rate first. Never introduce new models.dev traffic; the native client fetches the paired server catalog.
3. Release optimization: `android/app/build.gradle.kts:21` disables minification. Measure optimized release startup/APK/method loading and validate serialization/reflective integrations before enabling R8 or adding baseline profiles. Source alone does not establish a material benefit.
4. Notification debounce: `AidenChatViewModel.kt:224–229` debounces the combined stream by 400 ms. A continuous stream can defer updates until a quiet interval; evaluate periodic latest-value sampling for timely background notification delivery without increasing wakeups. This is a notification responsiveness experiment, not justification for per-token notification posts.
