# Design mode

Design mode puts an infinite canvas beside a chat. Aiden designs screens as HTML pages under `design/`, places them on the canvas, and checks each one as it writes it. The canvas belongs to the workspace, and each chat has its own page on it. Turn it on with the Design button, ⇧⌘L or `/design`, or let Aiden ask when a request is visual.

Design mode v2 (the live app canvas) is being built behind experimental flags. Its spec is [`docs/superpowers/specs/2026-11-23-design-mode-live-app-design.md`](superpowers/specs/2026-11-23-design-mode-live-app-design.md).

## DESIGN.md (experimental)

Aiden can treat an app's `DESIGN.md` as its design system's source of truth. `DESIGN.md` is Google Labs' open format: Markdown with YAML design tokens (colours, typography, spacing, corner radii, components) and prose sections.

**Turning it on.** Start Aiden with `AIDEN_EXPERIMENTAL_DESIGN_LIVE=1`. Design mode must also be on (it is by default). With the flag off, nothing here runs.

**Where Aiden looks.** For each app in the workspace, Aiden looks for a file named exactly `DESIGN.md`:
- first in the app's folder, then in each folder above it, up to the workspace root;
- or at the file that `.aiden/canvas.json` names for that app, for example `{"version": 1, "apps": [{"root": "apps/web", "designMd": "design/system.md"}]}`. If that file is missing, Aiden says so instead of looking elsewhere.

Files outside the workspace, including symlinks that point out of it, are refused, and so is a `DESIGN.md` that is, or links to, a file Aiden keeps from the model, such as `.env`, `.npmrc` or a key.

**What Aiden does with it.**
- The canvas note tells Aiden which `DESIGN.md` each app uses and how many errors and warnings it has. `canvas_read` includes the same line.
- Aiden's `design_system` tool reads the tokens and sections, lists the findings, exports Tailwind, DTCG or CSS-variable output, or drafts a starter file from the app's own styles.
- When an app has no `DESIGN.md`, Aiden asks once (per workspace and app) whether to draft one, and writes the draft only after you say yes, with its ordinary file approvals. If the first such app was offered before, the next one without a `DESIGN.md` is.
- When a design change adds or alters a token, Aiden updates `DESIGN.md` in the same turn, through the same approvals, and checks it again.

**What the checks cover.** Aiden bundles `@google/design.md` 0.4.0 and runs its linter offline, in a separate worker, with a 2-second limit per check. A check that runs out of time is tried again after five minutes; if the linter can't load within 10 seconds, Aiden stops trying until it restarts. The canvas note waits at most 3 seconds for these checks and otherwise goes without the `DESIGN.md` line. Files over 64 KiB aren't checked, and an export over 64 KiB isn't shown. Version 0.4.0 doesn't know a `motion` token group or the Motion and Voice & Content Strategy sections, and doesn't resolve `@file#fragment` references. Aiden adds two warnings of its own: a section that appears twice, and a token reference to a group that doesn't resolve.

**Privacy.** The file, its tokens and its findings stay on your device. Nothing is sent anywhere. Usage data records only that a check ran (with bucketed error and warning counts) and that a draft was written, never the file or its contents. See [analytics](analytics.md).

## Live apps (experimental)

With live apps, design mode runs your workspace's own web app so the canvas can show it. Phase 2b runs the dev server, and Phase 2c adds a status chip, its logs, Retry, and connecting a dev server you already run. Phase 3a adds [app frames](#app-frames): Aiden places the app's routes on the canvas, where they run [live](#live-frames), and you can download them as pictures.

**Turning it on.** Start Aiden with `AIDEN_EXPERIMENTAL_DESIGN_LIVE=1`. Live apps run on macOS and Linux only. With the flag off, nothing here runs.

**Starting the app.** When you turn design mode on in a chat, Aiden finds the workspace's web app (Next.js, React Router, Remix, TanStack Start, Nuxt, Angular, Astro, Gatsby, Create React App, TanStack Router or Vite) and shows a **Run app?** card above the composer. The card shows the exact command, the install command when one will run, the text of every script that runs, and the names of the config, rc and workspace files the start reads. Every line break in a script is marked with ↵, and a run of blank lines or spaces shows as its count, so no line hides below another. When the details are long they scroll inside the card, and **Allow** and **Not now** stay on screen. When several apps ask at once, each gets its own card. Nothing runs until you choose **Allow**. **Not now** starts nothing. Aiden can also start, stop, restart or read the app's output with its `design_app` tool, which asks on the same card. It runs only the app's own dev script, and at most four starts per reply. A chat without write access to the workspace can't start it. When design mode turns on with several chosen apps, they start together.

**When the card comes back.** Aiden remembers what you approved, for that folder on disk. The card comes back, as **Run app again?**, when a script, an install lifecycle script, the package manager, a lockfile, an rc or workspace file, or a framework config changes, when the workspace points at another folder (another checkout, even one with the same files) or its folder moved, and before an install that wasn't approved yet.

**Installs.** When the app has no `node_modules`, or Aiden's own last install didn't finish or is out of date, Aiden installs the dependencies first with the app's package manager (npm, pnpm, Yarn or Bun) from your package registry. Installing runs your dependencies' install scripts, which the card says. Aiden never installs over dependencies you installed yourself, and never installs in a parent folder: when the lockfile is outside the workspace, install there yourself, then start the app again. When the app has no lockfile, the install writes one. That lockfile is the only change, so the card doesn't come back for it.

**Only on this computer.** The app runs at `http://127.0.0.1:<port>`. Aiden checks every socket the server's processes open, and stops a server that listens beyond this computer. To fix that, remove `--host` from the dev script. Remix 3's starter ignores the host and port Aiden passes: make its `server.ts` listen on `process.env.PORT` at `process.env.HOST`.

**Environment.** The server runs with your shell's environment, minus your AI provider keys, Aiden's own `AIDEN_*` variables, npm's `npm_*` and `npm_config_*` variables, `NODE_ENV`, `ELECTRON_*` and `INIT_CWD`. An app that needs a key reads it from its own `.env`. Aiden also turns off framework telemetry (`NEXT_TELEMETRY_DISABLED`, `ASTRO_TELEMETRY_DISABLED`, `NUXT_TELEMETRY_DISABLED`, `GATSBY_TELEMETRY_DISABLED`, `NG_CLI_ANALYTICS=false` and `DO_NOT_TRACK`) unless you set those yourself.

**When it stops.** The server stops 60 seconds after no canvas for its workspace is on screen: you left design mode, the stacked layout shows the Chat pane, or the window is minimized or hidden. A window behind other windows still counts as on screen. It also stops when the workspace's folder or access changes, when it doesn't start listening within two minutes of quiet (ten minutes at most), and when it listens beyond this computer. Aiden never restarts it on its own; a crash shows a short notice and the server's own output stays in its log. When the server stops or crashes, Aiden also stops the processes it started, including ones that left its process group. After Aiden quits unexpectedly, the next launch stops what the last run left behind, found by a marker in each process's environment. On macOS, `ps` can't read that marker for Apple's own programs (such as `sleep`), so one of those left behind by a crash keeps running.

**Monorepos.** In a workspace with several web apps, you (or Aiden, through the same card) choose which app runs. The choice is saved as `script` in `.aiden/canvas.json`'s `apps`, for example `{"version": 1, "apps": [{"root": "apps/web", "script": "dev"}]}`, so you choose once. If Aiden can't save the choice (the file is a link, unreadable, or written by a newer Aiden), the app doesn't start. Choosing an app that is already running restarts it through the choose card.

**The status chip.** A chip before the canvas's view tools says whether the app runs: "Vite · :5173" while it runs, "Starting…", "Installing…", "Waiting for approval", "Crashed", "Not running" after a problem, or "Start" when it's stopped. With several apps it says "2 apps". Its menu starts, stops and restarts each app, shows its logs, and has **Choose apps…** (in a workspace with several web apps) and **Connect running server…**. A workspace without a web app shows a **Connect** chip whose menu has only Connect running server…. The chip changes as soon as you choose an action and settles when Aiden answers; when an action can't run, the menu says why. A screen reader hears when a running app crashes and when a connected server goes away on its own; your own **Disconnect** isn't announced. The chip appears only with the flag on, and not in a chat that can't run apps (a Bot's chat, or one without a workspace folder).

**Show logs.** Opens a read-only drawer at the bottom of the canvas with the server's own output. It starts at the last 256 KiB of the current run, follows new output while the canvas is shown, and keeps 256 KiB. The text is plain: colour codes and other escape sequences are removed, even when one is split between reads, and hidden characters show as escapes such as `\u{200B}`. A sequence that a line break interrupts, or one longer than 4 KiB, shows as escaped text instead, so it never hides the lines after it. A line longer than 4 KiB is cut with a count of what was left out. When the drawer falls more than 256 KiB behind (the canvas was hidden for a while, or a new run started with a lot of output), it drops what it showed, says output was skipped, and shows the latest 256 KiB. Scroll up to stop following; **Jump to latest** goes back to the end. Escape closes it.

**Retry.** After a crash, or a start that failed in a way a retry can fix (a failed or timed-out install, a missing Node or package manager, a server that never listened, or a choice that couldn't be saved), the menu offers **Retry**. Aiden looks for Node and the package manager again, then decides what runs: a failed choice is retried as that choice, with its card; an install failure, or a crash that says a module is missing, installs again; anything else restarts. A server that listened beyond this computer isn't retried, because its script has to change first; the menu says how.

**Choose apps….** Lists the workspace's web apps with **Run** next to each. Run goes through the same card, and the choice is saved as described under Monorepos.

**Connect running server….** Lists dev servers you already run, read from this computer's process and socket tables only when you open the list or press **Refresh**; Aiden never sends a request to a server to find it. A server is listed when it's your own process (not another user's), it runs from a folder inside the workspace, and it listens on a port from 1024 up. Each row shows its address, the process and folder it runs from, and the app it belongs to. Servers started in Aiden's terminal are listed; Aiden's own processes, the apps design mode started, background jobs (even a process a job started that has since left it), and its debugging ports (9222, 9229, 24678) never are. Aiden tells a background job's processes by a marker in their environment, so a server whose environment it can't read isn't listed and can't be connected; on macOS that includes Apple's own programs, such as `/usr/bin/ruby`. Some rows can't be connected, and say why: a server that listens beyond this computer (restart it bound to 127.0.0.1, for example with `--host 127.0.0.1` or `--hostname 127.0.0.1`; Next.js listens on every address unless you pass `--hostname 127.0.0.1`), one on a loopback address other than `127.0.0.1` or `::1`, one with a process that runs as another user, or an app design mode already runs. When some processes couldn't be read, the list says some servers may be missing. Servers in Docker, a VM or behind an SSH tunnel can't be connected, because their process doesn't run from the workspace folder. A server on `::1` only (as Vite on macOS often is) is connected at `http://[::1]:<port>`.

**Connected servers.** Choosing **Connect** is your approval; Aiden checks the server again before connecting. A connected server is yours: Aiden never starts, stops, restarts, replaces or signals it, and doesn't read its output, so it has no logs. **Disconnect** only disconnects; the server keeps running. To have Aiden run that app instead, disconnect first. A connection ends when the server stops listening, starts listening beyond this computer, or gets a process of another user; when its process runs from a folder outside the app, or Aiden finds a background job's marker or an environment it can't read among its processes, which Aiden checks every couple of seconds, even if the process has replaced its program in place; when the workspace's folder or access changes; and 60 seconds after no canvas for the workspace is on screen. A server that restarts itself under the same parent, as watch-mode tools do, stays connected if the new process takes the same address and port within six seconds and runs from the same app's folder; a new process from another folder, or one a background job started, disconnects at once; after any other restart the chip says **Connect again**, which opens the list for that app. A chat without write access to the workspace can't connect.

**A server in `.aiden/canvas.json`.** An app entry can name a server you run instead of a script: `{"version": 1, "apps": [{"root": "apps/web", "url": "http://127.0.0.1:5173"}]}`. The url must be `http:` on `localhost`, `127.0.0.1` or `[::1]` with a port from 1024 to 65535, and nothing after the port but an optional `/`. When design mode turns on, Aiden shows a **Connect to <process> at <address>?** card naming the process and folder it found holding that port; **Allow** connects only if the same process still holds it. Aiden remembers the approval for that address, entry and workspace folder, and asks again when any of them change. A url wins over a `script` in the same entry, and Aiden never runs the script of an entry with a url, even when the url is one it won't connect to; the menu then says the url is invalid. Such an entry can't be chosen to run in **Choose apps…** either. Aiden can connect such an entry through its `design_app` tool, after the same card, but it can't connect to any other server.

**In the browser panel.** Running design apps, started or connected, are listed first under **Local servers** in the browser panel, labelled "design mode", so you can open one there.

<a id="app-frames"></a>**App frames.** Aiden can place a route of the running app on the canvas as an app frame, with `canvas_place_frame`. The frame is sized like a browser window (1280 × 800 unless Aiden picks another size), drawn at a scale, and resizing it from a corner keeps its shape. While the app runs, the frame shows the route [live](#live-frames); otherwise it shows its last picture. With live apps off, app frames from an earlier run say "Live apps are off", and Aiden can't place new ones.

<a id="live-frames"></a>**Live frames.** While the app is running, an app frame shows its route live, at the frame's browser size. Up to six frames on screen are live at once; another says "Too many live frames" over its last picture. Until the page has loaded, the frame keeps its last picture. When the app isn't running, the frame shows its picture under the app's state: "Not running" with **Start app** (**Connect** for a server you run), "Waiting for you to allow the app to run", "Starting…" or "Connecting…", or "The app's dev server stopped." with **Retry**.

- **Using the page.** Double-click a frame, or select it and press Return, to click and type in the page. Esc, or a click on the canvas, gives the keys back to the canvas. A frame you haven't entered can't be clicked or tabbed into, and while presenting, frames stay that way. A page's own `focus()` calls can't take the keyboard from Aiden: with live apps on, Aiden starts Chromium with its `BlockingFocusWithoutUserActivation` feature, and app frames don't allow focus without a click. If the app stops or restarts while you're in its frame, you leave it; moving to another slide while presenting, or clicking off the slide, leaves it too. The title row shows the page's current path when it has moved off the frame's route, and the browser size. The Dark switch asks the page for its dark scheme. A hot update in the dev server refreshes the frame without a reload, and the frame's picture follows.
- **Localhost only.** The page reaches only servers on this computer over `http:` and `ws:` (the app's own and other local services, as from your browser), never Aiden's own ports. The internet, your network, `https:` to this computer, Aiden's own files and anything else are blocked, for the page, the frames inside it, and its workers and service workers. "N blocked" in the title row lists the hosts the page tried (up to 20), with "Design mode only lets apps reach localhost for now."
- **Links out of the app.** Redirects within the app work. A link or redirect to another site, or a `mailto:` link, is blocked, counted in "N blocked", and the frame goes back to the page it was on. Nothing opens outside Aiden. For a web address, a "*host* is outside the app" notice offers **Open in browser**, which opens it in the browser panel only when you press it; a `mailto:` or other link gets no notice.
- **No dialogs, popups or permissions.** `alert`, `confirm` and `print` return at once, and the title row says so. The page can't open windows, start downloads, navigate Aiden's window, or get the camera, microphone, screen, location, notifications, clipboard, fullscreen, Picture-in-Picture or any device.
- **Errors.** When the page reports an uncaught error, an **Error** label in the title row opens its message and, for the app's own code, the file and line.
- **Cookies.** Cookies your app's own server sets are marked `SameSite=None; Secure` for the canvas, so signing in works inside the frame. Cookies from other local ports aren't changed. The app's own pages show even when they send `X-Frame-Options` or `frame-ancestors`.
- **IPv6.** An app that only listens on `[::1]` isn't shown: the frame asks you to restart it on `127.0.0.1`.
- **Not covered.** WebTransport (HTTP/3 over QUIC), WebRTC relays over TCP and the dev server's own server-side requests aren't blocked.

**Downloading an app frame.** Download saves the route as a PNG, at the frame's width in browser pixels, or as a PDF. Aiden draws it in a hidden window with your app's cookies and storage, and waits until the page has made no new request for half a second, or at most 15 seconds. The app must be running in this workspace: otherwise you see "Start the app to download this frame.", and no Save dialog opens. Frames inside your app draw empty. The hidden window shows no dialogs, opens no windows, starts no downloads and is refused every permission. It reaches only servers on this computer, and not Aiden's own. Other local services stay reachable, as they are from your browser. WebTransport (HTTP/3 over QUIC), WebRTC relays over TCP and the dev server's own server-side requests aren't covered.

**Privacy.** The app's folder, scripts, port and output stay on your device. Usage data records only which framework and package manager an app used and whether it ran. See [analytics](analytics.md).
