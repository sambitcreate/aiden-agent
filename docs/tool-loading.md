# Built-in tools load on demand

Every request to the model carries the definitions of the tools it may call. Aiden used to send all of its built-in tools on every request, which was the biggest fixed cost in the context meter (**Built-in tools** in the Context tab). Two changes keep that cost small.

## One `skill` tool

Skills are listed once, in `<available_skills>` in the system prompt, and loaded through a single `skill` tool that takes the skill's `name`. Before, every skill was its own tool (`skill_<key>`) and was also listed in the prompt, so each installed skill cost tokens twice.

- The tool loads only skills the model may invoke in that chat. A workspace skill is unavailable under **No access**, and a skill that turned off its model invocation is never listed.
- Turning Skills off in Settings applies from the next `skill` call, as before.
- A Bot's `skill` tool loads only the skills granted to that Bot. The requested name is checked against the Bot's current grants when the call is made, so taking a skill away stops it at once.
- The per-skill key (`skillToolKey`) is still each skill's internal identity for grants and slash commands; it is no longer a tool name. The tool matches a listed name first and a key only when no name matches.

The server (`aiden serve`) has no `skill` tool. Its workspace chats, scheduled runs and subagents start Pi with skill loading turned off, so they see no skills; only Bots it hosts use skills, through their own per-skill tools (`skill_<hmac>` in `packages/cli/src/bots.ts`) for the skills granted to them.

## Rarely used tools load on demand

A chat starts with its everyday tools: files, commands, web search and page reading, questions, to-dos, memory, the `skill` tool, codemode and `tool_search`, the browser gateway and Bot cards. It also gets `load_tools`, whose description lists every other built-in tool in one line: the first sentence of the tool's description, or, for tools that declare one with `declareOnDemandSummary` (`render_ui`, `render_artifact`, `visualize_guide`, `workspace_artifact` and `design_mode`), a routing line of up to 160 characters that says what the tool does and when to use it. The model loads what it needs by name, and the loaded tools are declared from its next step. The list lives in `ON_DEMAND_TOOL_NAMES` in `main/services/on-demand-tools.ts`: subagents, the advisor, scheduling, visuals and artifacts, images, classification, background jobs, pull-request following, Aiden's app tools, past-chat recall, Computer Use, form filling, devices, Bot routines, image inspection, hooks (desktop chats that run [hooks](hooks.md) only), `design_mode` (behind the design mode flag), and the rarely used canvas tools (`canvas_page`, `canvas_duplicate`). The everyday design canvas tools (`canvas_*`) are not on the list: a chat in design mode declares them from the start, and a chat that enters design mode mid-reply (from Aiden's card or the person's own Design switch) gets them, with the design mode prompt section, from the next step. The canvas's counts (frames, HTML files, open comments) are not in the system prompt: a turn that starts in design mode carries a one-line conversation note with them in its first request ("Design canvas when this was noted: …", worded as a point-in-time fact so it stays true after the chat leaves design mode), and a turn that enters design mode mid-reply gets it from the next step, only when they changed since the last note. The note is saved with the chat's model history (never shown in the chat, on the phone or in Remote), so the next turn's unchanged counts add nothing and the prompt cache holds. The check reads the messages the request actually sends. A chat with skills turned off sends its visible history in place of the saved model history, and keeps each earlier note right after the chat message it followed, so unchanged counts still add nothing there. A chat with no saved model history (a journalless session) starts each turn from its visible history alone, so the note is added again at the end of that turn's history, after the part the provider can cache.

- Nothing is granted by loading. Every tool is still built, admitted, approved and run exactly as before; only the moment its definition is sent changes. `load_tools` refuses names the chat was not given.
- A tool loaded mid-reply is declared by a short message appended to the conversation, never by rewriting the tool list at the start, so the earlier part of the request stays in the provider's prompt cache. Later requests in that chat keep declaring it, in the order the chat first loaded it. "Never" holds only on wires that append system messages. On plain Anthropic Messages, and on the next turn once the head collapse folds the load into the head, the tool list changes once, which costs one cache miss per tool load.
- A chat declares the same tools on every turn, whoever sends it. A turn that cannot use a tool keeps the declaration and refuses the call before anything runs, with a reason that names the condition: `hooks` and `workspace_artifact` on a turn a phone or paired Mac sends, `hooks` and Computer Use on an unattended follow-up, Computer Use on a paired-device turn, `render_artifact` and `render_ui` when inline visuals are On request and the person did not use /visualize, and app-tool topics a paired device cannot show. The approval gate still decides every approval.
- A direct call to a tool that was not loaded yet fails as "not found", and the tool is declared on the next step so the retry works.
- The visual tools (`render_ui`, `render_artifact`, `visualize_guide`) are declared from the start, without a load, on a `/visualize` turn and on every turn of a chat in design mode. They are added at the end of the list, after the tools the chat already uses, and from then on they stay declared in that place like any loaded tool, called or not. Each run records its on-demand list in the chat's model history (an `aiden.on-demand-declared.v1` entry, written at a run's start whenever the list differs from the last record, and again at the run's end, inside the turn's saved envelope, when the run loaded or called a tool mid-run), and the next run starts from that list, so a `/visualize` turn or a design-mode session changes the tool list once, by adding at its end, and never reorders or drops what was declared before. The one exception is a tool the chat is no longer given, for example after a switch to a model that cannot use it or a setting that turns it off: it leaves the list, and the shorter list is recorded. A chat with skills turned off keeps the record too, since it holds only tool names. Only a chat with no saved model history (a journalless session) has no record, so each of its turns starts from the tools its visible history loaded or called, plus that turn's preloads. The record also keeps a loaded tool declared after a compaction folds away the message that loaded it, including one loaded during the run just before the compaction.
- The answer that loads a visual tool carries the guide it needs: `render_ui` the component catalog, `render_artifact` the design, HTML, charts and interactivity parts, and `workspace_artifact` the markup catalog. A part two tools in one load share comes once, and the first visual needs no separate `visualize_guide` step. A part a tool result in the chat already holds (the model called `visualize_guide` for it, or an earlier load answer carried it) is left out, and the lead-in line goes only with a part that is sent; a part a compaction folded away comes again. Tools declare these with `declareOnDemandLoadNotes`.
- The system prompt still describes held-back tools such as `aiden_help` and `subagent`; `load_tools` tells the model to load a tool before its first use.
- Workspace chats use this only when codemode is on (it is by default). Codemode scripts can still call every callable tool without loading it.
- Bots use the same list. Their tools stay installed, and a request simply leaves out the definitions of tools the Bot has not loaded. Bot computers (`computer`, `computer_shell`) stay declared from the start.
- The context meter counts only what is declared. Held-back tools are not shown as a deferred connection.

## Measured savings

Measured on 2026-10-28 with the end-to-end LM Studio fixture (a fresh workspace chat with Full access, the two built-in skills, codemode on), counting a quarter token per character of each tool definition as the context meter does:

| | Before | After |
| --- | --- | --- |
| Tools declared | 45 | 22 |
| Built-in tools in the Context tab | 9.7K | 3.6K |

Each installed skill now costs one prompt line instead of a tool definition plus a line. Computer Use (about 1.8K) and the device tools (about 0.8K) are held back too when those features are on, so a Mac with them enabled saves more. A Full Access Bot with subagents, routines, image sharing and Computer Use declares about 3.7K fewer tokens per request.
