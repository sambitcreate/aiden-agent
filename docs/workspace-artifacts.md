# Workspace artifacts

Workspace artifacts are small interactive pages that Aiden builds for a workspace and keeps in the **Artifacts** tab beside the chat. Each one shows status the person comes back to, for example the open pull requests, CI on main, a release checklist or a TODO board. Every chat in the workspace sees the same pages, and the data on them is read again each time the page refreshes.

They are a desktop feature on macOS and Linux. The CLI, Bots, Telegram and the iOS and Android apps do not have them.

## Starting one

There are two ways to start a page, and both end in the chat:

- Ask in any chat in a workspace, for example "make me an artifact that shows the open PRs for this repo".
- Choose **New page…** in the Artifacts tab: the button on its empty state, or the **+** beside the page title once there are pages. Say what the page should show, in your own words, or pick one of the suggestions (open pull requests, CI status on main, a TODO board from `TODO.md`, a release checklist), and choose **Draft in chat**. The request, such as "Make a workspace artifact page that shows this repository's open pull requests.", is added to the message box of the chat beside the tab, and focus moves there. It is never sent for you: read it, change it if you like, and send it yourself. With no chat from this workspace open beside the tab, Draft in chat is off and the dialog says to open one first.

In a workspace without a folder, or with workspace access set to **No access**, a page can't read files or run commands: Aiden can only make pages whose data it writes into the page itself. Pages like the open pull requests or CI status need a folder with access turned on.

The Artifacts tab never builds a page itself. Aiden uses the built-in **aiden-artifacts** skill and the `workspace_artifact` tool. It lists the workspace's pages first, so it updates an existing page rather than making a near-duplicate. The Artifacts tab opens on the new page beside the chat that made it.

Aiden builds a small working page first and checks it before adding more. Each save refreshes the page's sources once and draws the page with that data, the way the tab would. The result tells Aiden about:

- reads that come back empty, such as a misspelled field, `.length` on a list (pages use `len()`), or `<Each>` over an object;
- list props whose rows would draw empty, such as a `<Checklist>` given plain text instead of `{label, done}` items, or a `<Timeline>` whose items have no `title`;
- `run()` calls that name no action or pass the wrong number of values;
- sources the page never reads.

Aiden fixes those with another update. It doesn't press a button that changes something just to test it. The check only sees what the page draws with this data, so it also says what it couldn't cover: a source that didn't load, a list that was empty, an `<If>` branch hidden with this data, or a page too large to draw in full. Reads behind a guard, such as `<If test={$pulls.error}>` or `$x.note || "none"`, are not flagged. The check is a hint for Aiden, not a guarantee that the page is right.

The tab is in the tools launcher next to the terminal, files and browser once the workspace's pages have loaded, including before there are any: a workspace without pages shows the empty state with **New page…** and **Import page…**. The tab closes when the last page is deleted, and when you switch to a workspace without pages.

## How pages get their data

A page is written in Aiden UI Markup, the same component catalog that inline `render_ui` visuals use. Aiden reads the markup through the `visualize_guide` tool's `catalog` module, which is offered with `workspace_artifact` even when Settings → Appearance → Inline visuals is Off or Only when I ask; it then covers pages only and does not mention chat visuals: it teaches the page buttons `run` and `compose`, the page's `layout`, and changing a page by its id. A page declares named **sources**:

| Source | What it reads | Limits |
| --- | --- | --- |
| `shell` | A command run in the workspace folder that should only read, such as `gh pr list --json number,title,url`. Aiden asks for read-only commands but cannot enforce it, which is why Ask shows every command first | 30 seconds, 256 KiB of output |
| `file` | A workspace-relative text file; credential paths, hard links and links outside the folder are refused | 30 seconds, 256 KiB |

Each source parses its output as `json`, `lines` or `text`, and the page reads it as `$name`. Source, button and param names are identifiers (letters, digits and `_`, at most 40). A few are reserved: built-in object properties such as `constructor`, and keys Aiden's phone apps treat as private, such as `path`, `token` or anything starting with `child`; the refusal says so and suggests a free name such as `myPath`. A source that has not loaded yet reads as `null`. A source's parsed data holds up to 64 KiB, and so does the page's own `<Data>`; a larger result fails that source with a message to select fewer fields or rows. A page has at most 8 sources, and a workspace has at most 20 pages.

Pages refresh when they are shown (unless the page turns that off), when the person presses **Refresh**, and, if the page asks for it, on an interval of at least 60 seconds while the tab is visible. The last data read is saved with the page, so it paints immediately and keeps showing the last good data when an ordinary refresh fails. A credential-policy denial erases that source’s cached data before it can be returned or displayed. After this security upgrade, older file-source caches are cleared once and need a refresh. The page header says which sources didn't load, and the page lists each failed source with its error, for example `gh: not logged in`.

## Buttons

Page buttons can:

- `sendPrompt("…")`: ask Aiden in the chat beside the page, after the same confirmation chip as inline visuals;
- `compose("…")`: put text in that chat's composer without sending it;
- `run("name", value…)`: run one of the page's declared **actions**, a shell command template such as `gh pr merge {{number}} --squash`;
- `openUrl`, `copy` and `setState`, as in inline visuals.

Action values from the page never become shell syntax, and they only reach a short list of programs. A template with a `{{param}}` is never given to a shell: Aiden reads it with its own small grammar and runs each command as a program and its argument list, so what the checks look at is exactly what runs and each value is exactly one argument. The grammar has plain words, `'…'` (literal text), `"…"` (without `$`, backticks or backslashes other than `\"` and `\\`), `{{param}}` placeholders, `|`, `&&`, `||`, `;` and line breaks between commands (a `\` at the end of a line continues it), and only three redirections: `2>&1`, `>/dev/null` and `2>/dev/null`. Everything else a shell would read as syntax is refused there, including `$` (variables and `$(…)`), backticks, `( )`, `{ }`, `[[ ]]`, `(( ))`, `<`, other `>` forms, a lone `&`, `#`, `!`, unquoted `*`, `?` and `[`, a word starting with `~`, shell keywords (`if`, `for`, `case` and so on) and `NAME=value` before a command. Each command must start with one of these programs, written as a plain word and found on an absolute `PATH` entry: `git` with `status`, `log`, `show`, `diff`, `branch`, `switch`, `checkout`, `fetch`, `pull`, `push`, `add`, `commit`, `restore`, `reset`, `tag`, `stash`, `merge`, `rebase`, `cherry-pick`, `revert`, `rev-parse`, `grep`, `blame`, `ls-files`, `config`, `worktree list`/`add`/`remove` or `remote -v` (only `--no-pager` or `--no-optional-locks` may come before the subcommand); `gh` with a verb from its group's list: `gh pr` `view`, `list`, `status`, `diff`, `checks`, `checkout`, `create`, `edit`, `ready`, `merge`, `comment`, `review`, `close` or `reopen`; `gh issue` `view`, `list`, `status`, `create`, `edit`, `comment`, `close` or `reopen`; `gh run` `view`, `list`, `watch`, `rerun` or `cancel`; `gh repo` `view` or `list`; `gh release` `view` or `list`; `gh label list`; `gh workflow` `view` or `list`; or `gh browse` and `gh status`; or `ls`, `cat`, `head`, `tail`, `wc`, `grep`, `rg`, `jq`, `echo`, `printf`, `date`, `basename`, `dirname`, `sort`, `uniq`, `cut`, `tr`, `test`, `true` and `false`. `gh api` (its `-X` sends any method and `-f` turns a read into a POST), `gh workflow run`, `gh extension`, `gh alias`, `gh config`, `gh auth` and `gh secret`, shells, interpreters, package managers and build tools are refused in a template with params. Each `{{param}}` must be its own unquoted word, or joined only to plain text and other placeholders (`git show HEAD:{{file}}`, `notes/{{name}}.md`): not inside quotes, not joined to an option (`--body={{body}}`) or after a leading `+` or `@`, and not the command itself; each of these refusals says where the placeholder sits and how to write it instead, echoing the option it was joined to (`head -n{{count}}` is answered with `-n {{count}}`); a placeholder after a bare `-`, such as `head -{{count}}`, is told that the number needs its option as a separate word (`-n {{count}}`), and `tail -n +{{count}}` is told to use `-n {{count}}` for the last N lines, since starting from line N with page data is not supported. Beyond that, a `{{param}}` may sit only where a table for its program (and, for `git` and `gh`, its subcommand) says it may; every other position is refused, and the refusal names the forms that command allows. A slot is either the separate-word value of an option the table lists (`git commit -m {{msg}}`, `grep -e {{pattern}}`, `gh pr create --title {{title}} --body {{body}}`, `gh pr list --search {{query}} --limit {{n}}`) or an operand, and each slot has a rule for the value: text, a whole number, a branch or tag name, a number or branch (`gh` targets), or a file in the workspace. The tables also list the display and filter options saved buttons commonly use, written literally: `--color`, `--word-diff`, `--diff-filter=…` and `--merge-base` for `git diff`; `-M`/`--find-renames`, `-C`/`--find-copies`, `--find-copies-harder` and `-B`/`--break-rewrites` for `git diff`, `git log` and `git show`, alone or with a fixed similarity score joined to them (`-M50%`, `-M5`, `-B50%/60%`, `--find-renames=50%`; a separate word after them is a revision or file, never the score). A joined score is read as git reads it: digits with at most one `.`, then an optional `%` that ends it, and a second score after a `/` only for `-B`, so a form git refuses, such as `-M50%%` or `-M50%/60%`, is refused when saved; `--color` for `git log` and `git show`; `--merged`, `--no-merged`, `--contains` and `--no-contains` (whose `{{param}}` value is a branch or tag name), `--sort=…`, `--list`, `-a` and `-r` for `git branch` and `git tag`; `git blame --date=…`; `git stash show -p`; and `rg --color`, `--sort` and `--max-columns {{n}}`. While `git branch` or `git tag` lists (with `--list`, `-l`, `-n` for tags, or one of those filters) and nothing creates, deletes, renames or retargets a ref, an operand is a pattern and takes text such as `feat/*`, with no leading `-`. `git branch -v {{x}}` is refused, because `-v` alone does not list there: git creates a branch named by the value (write `git branch -v --list {{x}}` to filter the listing); otherwise it is a branch or tag name. The stash `git stash show`, `apply`, `pop` and `drop` read may also be `stash@{n}` or `n`. An option the table does not list is refused with the options it does list (up to 24, then how many more) and the advice to remove it, since the rest of the command still works; `git rebase -i` stays refused, since an interactive rebase waits on an editor. A few options take their value only when it is joined to them: `-U`/`--unified` of `git diff`, `git log` and `git show`, `--pretty` and `--format` of `git log` and `git show`, `git pull -j`/`--jobs`, and `--context` of macOS grep. Written apart, the program reads the next word as an argument of its own (`git diff -U 5` reads `5` as a revision or file; macOS `grep --context 2 {{p}} notes.md` reads `2` as the pattern and the value as a file), so a template with page data that writes one of them apart is refused with the joined form to write instead: a fixed `-U5`, `--unified=5`, `--pretty=oneline` or `-j4`, since page data cannot be joined to an option, or `grep -C {{n}}`, which takes page data. A placeholder joined to one of them (`git diff -U{{n}}`, `git log --format={{fmt}}`) is refused with the same fixed forms, not the usual advice to write it as a separate word, since page data cannot fill these options either way. Any other placeholder joined to an option is refused with advice to write it as a separate word only where that word saves as the option's value; where it would not, the refusal says why instead. An option whose value is optional, such as `git log --decorate=`, `--color=` or `--stat=`, never reads a separate word as its value (git reads `--decorate short` as the revision `short`), so a placeholder joined to one is told to write a fixed value or leave the option out, and `tail -n+{{count}}` is answered as `tail -n +{{count}}` is. So a `{{param}}` cannot be a verb (`git stash {{x}}`; write `git stash push -m {{msg}}`), cannot follow an option the table does not list (Aiden reads options the way the program does, so `--upload-p` is `--upload-pack` and `git rebase -qx {{x}}` is `-x {{x}}`), and cannot be the value of an option that writes or reads a file or starts a program: `--output`, `sort -o` and `-T`, `uniq`'s output file, `gh --body-file`, `-F` and `--recover`, `git commit -F`/`-t`, `--pathspec-from-file`, `git blame --contents`, `-S` and `--ignore-revs-file`, `git ls-files --exclude-from`/`-X`, `git log`/`diff -O`, `git --upload-pack`, `--receive-pack`, `--exec` and `--refmap`, `git rebase -x`, a merge strategy (`-s`, which runs `git-merge-<name>`) and `sort --compress-program`. A `git config` value is allowed only right after a key written literally that runs nothing (`user.name`, `user.email`, `init.defaultBranch`, `pull.rebase`, `push.default` and similar). The remote `git push`, `fetch` or `pull` connects to (the first operand, every operand with `--multiple` or `--all`, or `--repo`; a remote can be a URL, a path or a transport that runs a command) and every `git worktree` position but the new branch name after `-b` or `-B` are refused. `gh` takes page data only as option values (`--title`, `--body`, `--search`, `--label`, `--assignee`, `--base`, `--head`, `--limit` and similar) or one operand that is a number or branch-like name (no `://`, `@` or `:`, so it cannot name another repository); `gh repo view` and `gh repo list` take no operand from page data, since it names the repository or owner they read; a `--search` value may not hold a `repo:`, `org:`, `user:` or `owner:` qualifier, matched in any case wherever a term starts (after a space, `-`, `(` or `+`, but not inside a word such as `superuser:` or `Georg:`), which would search past this repository; `--jq`/`-q`, `--template`/`-t`, `-R`/`--repo` and `pr create --template` are refused. `jq` takes page data only as `--arg NAME {{x}}` or `--argjson NAME {{x}}`, read in the filter as `$NAME`; its filter, operands, `-L`, `-f`/`--from-file`, `--rawfile`, `--slurpfile`, `--args` and `--jsonargs` can read any file and are refused. `git diff --no-index`, which compares files outside the repository, is refused. Ordinary options such as `--title {{title}}` and `--body {{body}}` stay the recommended form. Templates without params are not limited this way and still run in a shell; the refusal says so, so Aiden can write a fixed command instead. Under Ask each press still shows the exact command before it runs. A page saved under older rules whose action these checks now refuse keeps the action but turned off; updating the page's actions rewrites it. Where a value lands decides what it may be. It may start with `-` only when it is the whole separate word after an option such as `-m`, `-e`, `--body` or `--search`, which the program always reads as that option's value; anywhere else the program would read it as an option, and a literal `--` does not make it safe (`gh` never honours `--`, and Aiden does not rely on it for any program). A branch or tag value must be a plain name as `git check-ref-format` allows one: no leading `-` or `+` (a forced push), no `:` anywhere (a deleted or renamed branch), no spaces, control characters, `*`, `?`, `[`, `\`, `^` or `~` (a glob such as `refs/heads/*` would push every branch), no `..`, `@{` or a lone `@`, no leading, trailing or doubled `/`, no part that starts with `.` or ends with `.lock`, and no trailing `.`. The branch `git push`, `fetch` or `pull` sends or asks for also may not be a full `refs/…` name, which could name any ref on the other side. The first `git checkout` operand and the commit a new tag points at (`git tag {{name}} {{rev}}`) take a revision value instead (below), so `git checkout {{rev}}` may check out `HEAD~1` or `v1.0` detached. git reads a `git checkout` operand that names no branch as files, so `git checkout {{branch}}` with a file name would discard that file's edits; when the template has no `--`, Aiden adds one after the branch and the options written after it, before any file operand (`git checkout {{branch}} -q` runs `git checkout <branch> -q --`, and the confirmation shows this). git then reads the value only as a revision, and a file name (or `sub/../notes.md`) fails as an invalid reference. An option written after a file operand there is refused, because the `--` would turn it into a file name; write it before the branch. A value in a file slot (the files `cat`, `head`, `tail`, `wc`, `grep`, `rg`, `sort`, `uniq`, `cut` and `ls` read, `grep -f`, `date -r`, `git diff`, `git blame` and `git grep` paths, and the operand of `test -e`, `-f`, `-d` and test's other file operators, including either side of `-nt`, `-ot` and `-ef`, which would tell the page whether an outside path exists) must name a file inside the workspace, checked on the whole argument with any text joined to it: no absolute path, no drive letter (`C:`, so `a:b.txt` is refused too), no home folder (`~` alone or followed by `/`; `~notes.md` is an ordinary file name, since nothing expands it without a shell), and no `..` that leads out of the folder. Just before the command runs, Aiden also follows symbolic links: if the file's real path (or, for a file that does not exist yet, its nearest existing folder's) is outside the workspace folder's real path, that command is not run and reports so, with status 126. Every `git` command a template with params runs, including each command of a chain or pipeline, gets `GIT_LITERAL_PATHSPECS=1`, so git reads no pathspec magic or glob in a file value or in the template itself: `*`, `?` and `[` are part of the file's name (`git add {{file}}` with `app/[id]/page.tsx` stages that file, and with `app/*.tsx` stages nothing unless a file has that literal name), and a quoted `'*.ts'` in the template is a literal name too. The confirmation shows the variable before `git`. No git setting turns this off; a person whose environment sets `GIT_GLOB_PATHSPECS` or `GIT_ICASE_PATHSPECS` gets a git error instead, as git refuses to combine them. A git file value also may not hold a `:` anywhere: leading, it is the form pathspec magic such as `:/` or `:(top)` takes, and inside, `git diff` and `git grep` read `HEAD:secret/s` as a file at a revision from the repository root; either would reach files outside a workspace that is a folder inside a larger repository. A template that joins a revision to a file writes the `:` itself (`HEAD:{{file}}`). A revision value (`git show {{rev}}`, `git log {{rev}}`, `git reset {{rev}}`, `git restore -s`, `git cherry-pick`, `git revert`, the first `git checkout` operand and a `git tag` target) may use revision syntax (`HEAD~2`, `v1.0^`, `main..feature`) but no `:` (`HEAD:secret/key` reads a file from the repository root, `:/text` searches commit messages), no glob, space or `\`, and no leading `-`, `+`, `.` or `/`. A `show`, `log` or `reset` operand before any `--` may also name a file, since git reads one that names no revision as files (`git log -p {{file}}` shows a file's history, `git reset {{file}}` unstages it), so Aiden decides per press when the template has no `--`: if every such value also passes the file rule above (inside the workspace, no leading `-`, no `:`), the command runs as written and the runner checks each value's real path as a file before it runs; otherwise Aiden adds a `--` after the revisions and the options written after them, before any file operand, so git reads the value only as a revision (`git reset {{rev}}` with `sub/../../secret/key`, which would unstage a file outside the workspace, runs `git reset <rev> --` and fails as an unknown revision). A value that is neither a revision nor a file inside the workspace is refused. The confirmation shows exactly what runs, with or without the `--`. Since `git log` and `git show` read no option after a file, a template that writes an option after such a value (`git log {{x}} --oneline`) is refused when saved, with advice to write the option, with its value if it takes one, before the whole word that holds the value (`git log --oneline {{sha}} -n {{n}}` is told to write `-n {{n}}` before `{{sha}}`, and `git show HEAD~{{n}}` with a later `--stat` to write `--stat` before `HEAD~{{n}}`); `git reset` reads options after a file, so it is not. A `cherry-pick` or `revert` commit, which git never reads as a file, always gets the `--`, as the first `git checkout` operand and a `git tag` target do. For `git log`, `git show` and `git reset`, `{{rev}} --` is the clear form for a revision and `-- {{file}}` (`git log -p -- {{file}}`) the clear form for a file: without them a branch named like a workspace folder fails with git's "ambiguous argument", and a deleted file fails as an unknown revision. Saved pages follow the same rule on every press, so a page saved with `git log -p {{file}}` while Aiden always added the `--` works again without changes. To read a file at a revision, write `git show HEAD:{{file}}` (or `{{rev}}:{{file}}`): git reads the path after `REV:` from the repository root, not the folder it runs in, so Aiden runs it as `HEAD:./<value>`, read from the workspace, shows that in the confirmation, and checks the value as a file in the workspace; an index path `git show :0:{{file}}` (stage 0 to 3) runs as `:0:./<value>`, since git reads `:./0:f` as a file named `0:f`; the stage is written in the template, so `git show :{{n}}:{{file}}` is refused with that advice. A whole-number slot (`--limit`, `head -n`) takes digits only, and control or invisible characters are refused, except a line break or tab in a text value (a commit message body or comment), which is passed as plain text. The command that runs is always the one saved with the page, never text from the page itself. A page has at most 16 actions, each with a 2-minute limit.

These rules can tighten in a new release. A page saved earlier stays in the Artifacts tab with its history, but an action whose command the current rules refuse is turned off: pressing its button shows why, Aiden's `list` marks it turned off with the reason, `run` refuses it, and it runs again once the page's actions are rewritten. That includes a saved button that uses an option the current tables do not list: after an update it is turned off, and once its command is fixed (for example by removing the option) it needs approving again under Ask before it runs. Under Ask, an approval also covers which buttons were turned off when you allowed it: a button that was turned off then and that a later release's rules let run again needs allowing again before it runs. A rule change that turns a button off, or back on, asks once more under Ask; a rule change that leaves every button as it was keeps the approval. A page file exported with such an action imports the same way: the page comes in with that action turned off, the import review marks it "turned off: it won't run" beside its command, and it never runs until the actions are rewritten. A page Aiden could not read is kept aside in the workspace's file and read again each time it loads, so a page an earlier release set aside comes back once it reads.

Aiden can also run a page's action when you ask it in chat, for example "merge PR 12" with a pull request board open. It uses the `workspace_artifact` tool's `run` operation, which goes through the same checks as a button press:

- Under Ask, the approval card shows the exact command with its values, and nothing runs until you allow it. Allowing covers that one command only: if the page or the values change before it runs, it doesn't run.
- A page whose commands you haven't allowed yet doesn't run, and no card is shown; allow the page in the Artifacts tab first.
- Under Full access the action runs without a card, as a button press would. Aiden's skill tells it to run actions only when you ask and never to press buttons to test a page, but under Full that is guidance, not something the app enforces.
- Without a folder or with workspace access off, nothing runs.

A failed command fails the tool call with its output, and the page refreshes afterwards either way.

## Access

External Markdown images in the surrounding desktop transcript require **Load image** before any request. This is separate from a workspace page's own content policy. See [chat image privacy](transcript-images.md) for public-network checks, image limits and keyboard behavior.

Pages follow the workspace's access setting, the same way chats do:

- **No access**: nothing runs. The page shows its last saved data and says why it is not live.
- **Ask**: when Aiden creates or changes a page, the approval card lists every command it can run. Allowing it approves exactly that set of commands, and any later change to them needs approval again. The person can also review and allow a page from the tab, which reads its sources at once. Each button press shows the exact command and waits for **Run**. File sources run without approval, subject to the model file policy. `.env` except `.env.example`, protected credential names and canonical aliases to them are refused whenever a page is saved (created, updated, restored or imported) and again when it reads. Human Files-panel editing retains its own access contract.
- **Full access**: sources and buttons run without asking.

Changing a workspace's access cancels any refresh or button already running. Commands run with the same environment as `run_command`, and Aiden's own secrets are withheld. Like `run_command`, a source or button command that leaves a background job holding its output has that job stopped 1 second after the command exits (a job started with `setsid` or as a daemon leaves the command's process group and is not stopped); redirect a job's output (`> file 2>&1 &`) if it should keep running.

## Managing pages

The page header has a switcher between pages, **New page…** (the **+**), the time of the last refresh, **Refresh**, and a menu with **Ask Aiden to change this**, **Rename**, **Earlier versions**, **Export page**, **Import page** and **Delete**. Delete asks for confirmation first. Aiden deletes a page only when the person asks, and its delete always shows an approval card.

Pages and their saved data are stored on the device under Aiden's user data folder (`workspace-artifacts/`), not in the repository, and they are not part of portable settings. Removing a workspace removes its pages.

## Earlier versions

Aiden keeps the last 5 versions of each page (`WORKSPACE_ARTIFACT_LIMITS.history`), so a bad update can be undone. Every reply in which Aiden updates a page (and every restore) keeps the version it replaced. All of Aiden's saves to one page within one reply fold into a single version, so restoring the newest earlier version goes back to the page as it was before that reply, and a save that changes nothing (same name, description, page, data sources, actions and refresh) makes no version and keeps the page's current state. Renaming a page, allowing its commands and the page's own state do not make a version. A page you rename while Aiden is still replying keeps your name when Aiden saves it again in that reply, even if the rename lands while that save is being prepared, and the renamed page is kept as its own version; only a new title Aiden gives on purpose replaces yours. The description works the same way: when another chat changes a page's description while Aiden is preparing a save from the page it read, the save keeps the other chat's description unless it sets one of its own. Everything else works that way too: a save keeps the page, layout, data sources, actions and refresh another chat saved in that window, and replaces only what it sets itself.

- **Earlier versions…** in the page menu lists them newest first, with when each was replaced and its name at the time if it differed. **Restore** makes that version the page again as a new version, so a restore can itself be undone the same way.
- You can also ask Aiden, for example "undo the last change to the PR board". It uses the `workspace_artifact` tool's `restore` operation, and `list` shows each page's `earlierRevisions`.
- A restore keeps the page's current name. It also brings back that version's page state (checked boxes, the chosen tab and similar), because the state is saved with the page. Changes to the state alone are not versions. State saved from a version the page has since left is dropped, so a change made just before a restore or update can't overwrite the new version's state.
- Under Ask, a version whose commands differ from the ones you allowed needs allowing again: the page menu marks it "Different commands — needs allowing again" (including while the current page is itself still waiting to be allowed), and Aiden's restore shows an approval card listing the commands, like an update. A version with the same commands as the allowed ones restores without asking.
- In a workspace without folder access, Aiden can't restore a version that reads files or runs commands. **Restore** in the page menu still saves it, but nothing runs until the workspace has access.
- After a restore from the page menu, the page re-reads its sources if it is allowed to.

Earlier versions are stored on the device next to the pages (`<workspaceId>.history.json`), never with an approval. They are deleted with the page, and with the workspace, including when a delete lands while an update is still saving the version it replaced. If the history file is damaged it is replaced rather than repaired, and if it can't be written the page update or delete still goes through; the pages themselves are unaffected. A restore is different: it keeps the current version first, and if that can't be written the restore is refused and the page stays as it was, so a restore can always be undone.

## Export and import

A page can be saved as a file and added to another workspace, on this computer or another one.

- **Export page…** in the page menu saves the page as `<title>.aiden-page.json` wherever you choose. The file holds the page's name, description, layout, its `<Data>` text, the state its markup starts in, its sources, its buttons' commands and its refresh settings. Very long names are shortened so the file always saves.
- The file leaves out the approval of the page's commands, the page's and workspace's ids, the chat that made it, its revision and dates, its earlier versions, the data its sources last read (which may be private) and the state you gave the page since (the tab you chose, boxes you ticked, text you typed). An imported page therefore starts where its markup starts, with no data until it refreshes. A page made before Aiden kept its starting state apart exports no state, so it starts with none.
- **Import page…** is in the page menu and, in a workspace without pages, next to **New page…**. Choose a file (at most 2 MiB). Aiden checks it exactly like a page it saves itself (the same limits, command rules, and everything the markup compiler checks: components and their settings, values, links, actions and data) and refuses a file of another format or a newer version, saying why. Nothing is added yet: a dialog says which workspace it is added to, quotes the file's own description as the file's, shows every command it can run and every workspace file it reads, and says what happens next under the workspace's access. **Import** adds it; **Cancel** adds nothing. If a page here already has its name, the import is called "Name (2)", "Name (3)" and so on.
- An imported page never arrives allowed, whatever the file says. Under **Ask** its commands don't run until you choose **Review…** on the page and **Allow** them, as for a page Aiden just made; its file sources are read as soon as the page opens, as files are under Ask.
- Under **Full access** the dialog says plainly when commands run: a page whose command sources refresh as it opens runs them as soon as you import it (and then on its timer, if it has one), so the button reads **Import and run**. Its buttons run when you press them, with no card. Only import pages from people you trust, and read the commands in the import dialog first.
- With **No access** nothing runs or is read until access is turned on. A workspace without a folder can still import a page, by design, but nothing on it runs or is read; the dialog says so.
- Aiden can't export or import pages itself: the `workspace_artifact` tool has no operation for it. Only you can, from the Artifacts tab.

## For developers

- Shared contract and parsers: `renderer/shared/workspace-artifacts.ts`.
- Confined reads: macOS uses the packaged descriptor-relative worktree file helper; Linux uses Node directory descriptors through `/proc/self/fd`, with pinned root/file identities, no-follow traversal and bounded reads. Linux requires procfs descriptor access and fails closed without it; it does not depend on the macOS helper.
- Store, tool, runner, page check and skill: `main/services/workspace-artifacts/`. The page check (`check.ts`) uses the evaluator's `onRead` hook, which only the check sets, to record each `$name` and member read the page actually takes. The page file format, its strict reader and the pending-import tokens are in `transfer.ts`.
- IPC: `workspaces:artifacts:list`, `rename`, `delete`, `saveState`, `approve`, `refresh`, `run`, `history` and `restore` (which never records an approval), `export`, `importPreview`, `importConfirm` (which never records an approval) and `importDiscard`, plus the `workspaces:artifacts-changed` notification (`main/handlers/workspace-artifacts.ts`).
- Tab: `renderer/components/artifacts-panel.tsx`, wired into the Environment panel.
- Tests: `npm run test:workspace-artifacts`.
- Design and decisions: [Workspace Artifacts plan](plans/workspace-artifacts-plan.md).
