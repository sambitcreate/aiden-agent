# Guided connection for Providers and onboarding

**Implemented locally on 2026-11-05.** Both desktop flows now use Guided connection. The optional chat shortcut was omitted so existing drafts and model choices stay under the composer’s control. Mounted tests cover key validation, cancellation and local recovery. Electron tests cover first run, deferral, relaunch and Settings. The first-time usability exercise below remains a release follow-up.

A person with an Anthropic key should be able to choose **Connect AI → I have an API key → Anthropic**, enter the key, and learn whether a chat model is available. They should take the same path during first run and from Settings later. Before this change, the similarly named **Add provider** in Settings only added local or custom endpoints, whereas the built-in Anthropic action lived in a separate list. Onboarding put that same key behind **Other ways**.

The deliverable is a desktop UI change on macOS and Linux. Keep existing saved connections, credentials, model choices, auth ownership and validation contracts. There is no proposed Remote revision, native client change, settings migration or new analytics event. The [authentication and validation plan](../onboarding-auth-and-provider-validation-plan.md) owns provider readiness; this plan changes how people reach and understand those operations. The prototype's sample keys, artificial failure controls, simulated replies and blanket “connected” state are not product requirements.

## What the person sees

**Settings → Providers.** While loading, show a loading state; on a read error offer **Try again**. Only show the empty state (“Give Aiden a way to reply” / **Connect AI**) when the read succeeds and there are no configured connections. Otherwise show **Your connections** first: icon, name, one truthful status line, and one trailing action such as **Manage**, **Sign in again**, or **Check for models**. Keep incomplete and voice-only configurations reachable even when there are no chat-ready rows. Show **Connect another AI** below the list. **Try a chat** may open a composer for a usable connection; preserve existing drafts and per-chat model choices, and never send a message or silently set a global default. If an existing navigation path cannot honor those constraints, omit the shortcut in the first slice.

**Onboarding.** Show three visible stages: **Your name → Connect AI → Finish setup**. Keep the required name and its local profile/context explanation. The middle stage opens the chooser inline, with no preselected provider. Offer **Use this connection** when an existing connection meets onboarding's readiness check; otherwise show how to repair it. **Set up later** is available without opening a form. On successful setup, name the service and usable model before **Continue setup**; on deferral, say where to connect later. Finish keeps the usage-data control and its details visible before completion. Offer the existing first Bot chooser and feature gallery as optional sections; keep supported features, artwork, keyboard access and the existing capability gates. Do not create a Bot by expanding the section. Preserve the current explicit creation action and open the chosen Bot chat only after finishing.

| Choice in either surface | Next screen and action | What counts as success |
| --- | --- | --- |
| **I have an account** | Offer supported sign-in methods, with ChatGPT prominent. Name the service on the button. Distinguish OpenAI account sign-in from the existing Codex connection; retain account-specific disclosures, cancel, fallback and repair. | The existing auth owner reports the result, and the intended provider has a selectable chat model before onboarding progresses. |
| **I have an API key** | Choose a provider first. Show one masked field, who bills usage, and an action matching that provider's actual capability: **Validate key** for an explicit supported check, **Save key** when only storage is possible. | Say what happened: “Key saved”, “Credentials accepted”, or “Ready for chat”. Never infer a successful remote check from a saved key or a bundled model list. |
| **I run a local model** | Choose LM Studio or Ollama. Explain how to start the server and load a model, then **Check for models**. Use its canonical profile and keep an existing customized address. The address override is available under Advanced. | Distinguish unreachable server from reachable server with no chat models. Offer the corresponding fix and retry. Save the discovered selection only when usable. |
| **Advanced connection** | Custom or Tailscale server, with URL and required auth visible once chosen. Put nonessential protocol/model overrides, capabilities, effort and classifier options behind the editor's disclosure; keep required fields discoverable on error. | Use the existing editor. Require a usable discovered/default model in onboarding; retain the existing Settings rules for saving and managing configurations. |

Use the runtime provider inventory and supported auth methods, not a handwritten list from the HTML. A provider that supports two methods can appear in both paths; both must resolve to its real identity. Include **Other setup methods** in the chooser for ambient credentials, provider-managed setup and future unclassified entries; explain unavailable methods instead of routing them to a key field. Preserve dedicated Gemini scope and agent-runtime flows wherever supported today. A transcription-only Google credential is not a chat connection. Listing an installable runtime must never install or launch it.

**Advanced settings** is separate from the connection editor. It is collapsed on entry and holds custom/private endpoint creation, background chat-title routing (including Apple status only where supported), and manual model catalog maintenance. An existing custom connection remains manageable from the main list. Preserve the explicit refresh action, its explanation and result; expanding Advanced must do nothing on the network. Keep the chat connection’s own billing, data-sharing, and readiness information at the action. Move the unrelated speech, image-key and paid cache-warming explanations from the choice screen to an optional privacy disclosure on Finish, retaining their meaning and destinations.

## Delivery order

1. **Share the chooser and test its routing.** In the renderer, extract the method chooser and row presentation around [provider display helpers](../../../renderer/lib/pi-provider-display.ts) and [the existing setup row](../../../renderer/components/settings/provider-setup-row.tsx). Route by provider ID, method and capability. Keep the chosen route and transient form state separate from saved connection state. Keep two host adapters: Settings opens its existing editors and refreshes its list; onboarding checkpoints the exact ready provider and preserves model-selection behavior. Do not duplicate auth, credential or discovery logic. Before replacing either screen, exercise fixtures for multi-method, ambient-only, custom, voice-only, missing-model and repair states.
2. **Ship Settings first.** Replace the old add menu and built-in wall in [Providers Settings](../../../renderer/components/settings/providers-settings.tsx) with the connected list, shared chooser and Advanced panel. Reuse the built-in/custom editors, Codex management, Gemini scope dialog, model-visibility controls and removal confirmations. Map current entry points, including empty-chat and credential-repair links; they must land on a useful action. Check that a second connection does not replace the first or change an existing chat.
3. **Use the chooser in first run.** Replace the provider cards and generic Next dispatch in [onboarding](../../../renderer/components/onboarding-flow.tsx). Keep explicit non-billable key validation where supported; never use a generated response as a probe. On cancel/back/switch discard abandoned secrets and ignore late results; do not cancel an auth commit already finishing. Keep the modal focus boundary and return focus to the invoking control. Map the three visible stages onto the existing [v2 checkpoints](../../../renderer/shared/onboarding.ts): an existing profile resumes at connection if needed; a ready provider or completed Bot checkpoint resumes at Finish. Persist the Bot checkpoint at the same meaningful action, avoid duplicate creation, and keep the usage notice tied to being shown. Finishing after **Set up later** records deferred with no provider ID; closing early remains incomplete. Settings → About → Show onboarding remains non-destructive.
4. **Verify the journeys and update guidance in each shipping slice.** Follow the [settings design system](../../settings-design-system.md): grouped rows, shared squircle actions, neutral keyboard focus, background/caret focus for text inputs, responsive layout, and reduced motion. Reuse the existing tour art. In the same PR as each behavior change, update the affected Settings, onboarding and Linux instructions; search README, PRODUCT and current guides for old menu names or paths. Update this plan and the index as milestones land. The two UI slices can be reviewed separately or reverted independently; neither needs a data migration.

## Acceptance before release

| Journey | Observable check |
| --- | --- |
| First-run success | Enter a name, choose Anthropic, reject an invalid key, correct it and see the accepted provider/model. Relaunch after setup; find the same connection in Settings. No chat was sent. |
| Local recovery | From either surface, distinguish a stopped server from one with no chat model. Load a model, retry and finish. A preconfigured LM Studio profile retains its ID, address and metadata across relaunch. |
| Existing install | Open Settings with a mix of usable, needs-attention, transcription-only and custom connections. Each has an accurate status and a working action. Cancel a repair or removal without changing saved state. |
| Deferral and resume | Skip connection, review usage data, finish and reach the empty-chat link back to Connect AI. Close and reopen partway through setup. Reopening an existing setup preserves connections, selections and previously created Bots. |
| Manual-only actions | With instrumented provider/auth/catalog boundaries, open both screens, switch methods, expand Advanced, cancel and navigate back. No external auth, discovery, generation, catalog fetch, installation or process launch. An explicit catalog update invokes only the existing foreground operation. |
| Accessible setup | Complete and cancel the flow by keyboard at narrow width; errors identify the relevant field; loading/success is announced once. Focus returns from each editor. Check light/dark, reduced motion, macOS-only title controls and their absence on Linux. |

Extend existing **behavioral** suites: provider settings, catalog update, onboarding flow and provider validation. Update the shared E2E setup helpers together with [guided setup](../../../tests/e2e/guided-setup.spec.ts) and [LM Studio onboarding](../../../tests/e2e/onboarding-lmstudio.spec.ts); replace assertions about the old four cards with journeys that check outcomes. Run `npm run test:onboarding`, `npm run test:model-catalog` and the focused Settings tests. On Mac, run the relevant Electron specs through `npm run test:e2e:space -- tests/e2e/guided-setup.spec.ts tests/e2e/onboarding-lmstudio.spec.ts tests/e2e/settings-unification.spec.ts`; also exercise changed macOS-only branches on the host. Use fixtures, not live accounts. If implementation proves to require a change to provider or Remote contracts, split it out and review all consumers before shipping.

For a usability check, give a first-time tester an Anthropic test key without telling them which button to press. Ask them to connect it, say who receives a chat message and who bills it, then find the connection again. Give a local-model user the empty-server case and observe whether they can recover unaided. Treat wrong turns as feedback on labels and placement, not as a reason to add more introductory copy.
