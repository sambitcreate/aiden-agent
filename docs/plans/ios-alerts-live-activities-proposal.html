Aiden On The Go · iOS

Hear from Aiden after you lock your phone

The Live Activity and run alerts already look good. They stop working shortly after the phone locks, because both are driven by the app, and iOS suspends the app. Hermex and T3 Code fix this with a small push relay. This plan does the same, keeps the privacy model Aiden already has, and adds lock-screen answers, which neither of them offers.

01 · What happens today

One run, start to finish, with the phone locked

The phone gets updates only while Aiden is running in the foreground. It has no background mode, no push token and no Notification Service Extension. The stream to the Mac stops when iOS suspends the app.

  1. 0:00
    You send “fix the flaky login test” and lock the phone.Live Activity starts: Thinking, timer running.Works
  2. ~0:10
    iOS suspends Aiden.The stream to the Mac closes. The card stays on its last state (Reading files), and the system-drawn “Updated … ago” keeps ticking.Silent freeze
  3. 3:10
    The agent asks to run npm run test:e2e.Nothing on the phone. AidenRunAlertNotifier would post a Time Sensitive alert, but it runs inside the suspended app.Missed
  4. 5:00
    The stale date passes.The card greys out: “Latest status shown”. It still doesn't know an approval is waiting, so it can't say “Open to answer”.Stale
  5. 11:00
    You glance at the phone, then open Aiden.The app reconnects and shows the approval card. The agent has been blocked for 8 minutes.8 min lost
  6. 7:00 am
    A scheduled task or Bot routine finishes overnight.The feed is polled “while the app is foregrounded” (AidenScheduledRunNotifier), so you hear about it when you next open the app.Late

Already built well

  • ✓Lock Screen + Dynamic Island card with 12 statusesStatus colors, timer pill, progress rail, tool count
  • ✓Freshness and stale copy“Updated … ago”; stale approval says “Open to answer”
  • ✓Sanitized text and old-payload decodingTitle, activity and excerpt are capped; new fields decode as optional
  • ✓Leftover cards reconciled on relaunchCards for a run that already ended are closed
  • ✓Run alerts with good mannersTime Sensitive for asks, quiet while you're in that chat, one alert per prompt
  • ✓Permission asked after the first finished runNever at launch, never for a failure
  • ✓Taps open the right chat on the right Macaiden-otg:// links, grouped per chat

Missing

  • ✕No push of any kindNo APNs token; the card can't change while the app is suspended
  • ✕Alerts need the app aliveApprovals, answers, Bot handoffs, failures
  • ✕Scheduled and Bot routine alerts are polledDelivered only when the app is opened
  • ✕No actions on alerts or the cardA tap only opens the app, even to say no
  • ✕Fixed copy only“Needs your approval”, with no idea what for
  • ✕No notification settingsEvery alert is on or off together at the system level
  • ✕One card per runThree runs at once means three stacked cards
  • ✕No Watch, CarPlay or Always-On layoutNo supplementalActivityFamilies, no reduced-luminance styling
02 · Hermex and T3 Code

How Hermex and T3 Code handle it

Both apps route through a Cloudflare Worker that holds the APNs key. Hermex encrypts message text end to end. T3 Code shows all of your agents on one card. Neither one lets you answer from the lock screen, and both dropped push-to-start.

04 · Delivery

How a push gets from your Mac to the phone

Today Aiden has no cloud servers: phones reach the Mac directly over the local network or Tailscale. Push can't work that way, because APNs only accepts messages signed with Aiden's Apple key, and that key can't ship on every Mac. So the one new piece is a small relay that holds the key and forwards sealed messages.

Your Mac / aiden serve

Seals and sends

On a status change, it seals the preview with a key shared during QR pairing and posts to the relay. The same code goes into the CLI bundle.

Knows: everything, as today
Aiden push relay

Forwards to APNs

A Cloudflare Worker you run, holding Aiden's APNs and FCM keys. Stateless: no database, nothing logged.

Sees: event kind, random ids, push token, timing. Never chat text, titles or the Mac's address.
Apple APNs

Delivers

Alerts go out as mutable-content banners. Card updates use the liveactivity push type, priority 10 for a status change and 5 for progress.

Sees: the same as the relay
iPhone

Opens and shows

A new Notification Service Extension opens the sealed text and falls back to fixed copy if it can't. The card gets only statuses and counts; its title was stored on the phone when the run started.

Shows: real text, actions, a live card

Alert push, as the relay sees it

{
  "aps": { "alert": { "title": "Aiden", "body": "New activity" },
           "mutable-content": 1, "interruption-level": "time-sensitive",
           "category": "AIDEN_APPROVAL", "thread-id": "c9f2…" },
  "kind": "approval", "pairing": "7ab1…",
  "sealed": "base64(AES-256-GCM(title, body, deep link))"
}
// the service extension replaces title/body; on any failure the fixed copy stays

Card update push (content state)

{
  "aps": { "event": "update", "timestamp": 1795327931,
           "stale-date": 1795328831,
           "content-state": { "v": 2, "status": "waiting_for_approval",
             "tool_calls": 4, "started_at": 1795327740,
             "updated_at": 1795327931 } }
}
// widgets can't decrypt, so no text is sent; the title is already on the phone
Recommended

A. Aiden relay

The approach Hermex and T3 Code both ship. A small Worker, the APNs key in its secrets, sealed messages only. It needs a policy section in AGENTS.md like the analytics one: a fixed host, opt-in, and a list of what's sent.

Not viable

B. Mac sends straight to APNs

Every Mac would need Aiden's APNs signing key. Anyone could extract it and send pushes to any Aiden user.

Fallback only

C. Background App Refresh

iOS decides when it runs, often hours apart, and never in Low Power Mode. Good for catching up the scheduled-task feed, useless for an approval.

05 · The relay decision

What the relay is, who runs it, and what it keeps

Only Aiden's Apple push key can reach the App Store build, and only Aiden's Firebase project can reach the Play build. So whoever runs the relay holds those keys, and users can't bring their own. The real choices are who operates it, whether it stores anything, and how it gets turned on.

Recommended

You run a Cloudflare Worker

About 300 lines in the repo. The APNs key and FCM service account live in Worker secrets. Cloudflare's free plan allows 100,000 requests a day, and the $5 paid plan covers 10 million a month. APNs and FCM are free.

Possible

A push vendor

OneSignal, Firebase for iOS too, or Expo. Less code, but a third company sees every device token and event, and most ask for an SDK inside the app. That goes against Aiden's no-SDK, fixed-host rules.

Gives up the goal

No relay

Ship phase 1 only. Alerts get better while the app is alive, but approvals are still missed once the phone is locked.

Abuse guards with no database

  • ✓The relay builds the visible banner itself from a fixed template per kindA forged request can show at most “Aiden needs you”. Real text only comes from the sealed blob, which only the phone can open.
  • ✓Tokens can't be guessed and are only given to paired MacsBeing able to send pushes to a phone already means having been paired with it.
  • ✓Cloudflare rate limits per IP and per token, a size cap and an allow-list of kinds
  • ✓The relay code lives in this repoAnyone can read what it does with a request.

Request from the Mac to the relay

POST https://push.<aiden domain>/v1/send
{
  "platform": "ios",               // or "android" → FCM
  "token": "a1b2…",                // from the phone, over pairing
  "kind": "approval",              // fixed list
  "thread": "c9f2…",               // random per chat
  "pairing": "7ab1…",              // tells the extension which key
  "sealed": "base64(AES-256-GCM)"
}
// 200 sent · 410 forget this token · 429 slow down

How it gets turned on

  • 1After pairing or the first finished run, the phone asks: “Get alerts when your phone is locked?”Off until you choose. Each Mac is chosen separately.
  • 2Yes: iOS permission, then the token and a new preview key go to that Mac
  • 3The Mac lists “Phones with push” in Connections, with Turn off
  • 4The Mac contacts the relay only for a phone that turned push on, and only with the fields aboveWritten into AGENTS.md as a network rule, like analytics

Setup only you can do

  • □Apple Developer → Keys: create an APNs auth key (.p8)
  • □Add Push Notifications to the app IDThe app has the Time Sensitive entitlement and an app group already; aps-environment is missing
  • □Cloudflare account, plus a domain or subdomain for the relay
  • □Firebase project and service account for AndroidThe Android app has no FCM yet. Phones without Google Play services would stay app-only.
  • □App Store privacy label: declare the device ID used for push
06 · Order of work

Four phases; the first ships without a server change

Phase 1 · app only

Better while the app is alive

  • Restyle the card and island as plain text: no dot, rail, pill, chips or tints
  • Settings → Notifications page
  • Approve / Deny / Reply on today's local alerts
  • Deny + Review buttons on the card
  • Summary card from 2 runs up
  • Watch / CarPlay small family, Always-On styling
  • Short background task so a run that's about to finish can still alert

iOS only. No contract change.

Phase 2 · relay + alerts

Alerts with the phone locked

  • Relay Worker + APNs key
  • Preview key exchanged at pairing
  • Device token registered per Mac
  • Service extension opens the sealed text
  • Asks, results, failures, Bot handoffs, Bot needs-you, scheduled runs
  • Per-event choices sync to the Mac

Next Remote protocol revision; Android (FCM) in the same revision; network policy in AGENTS.md; docs.

Phase 3 · card over push

A card that stays live

  • pushType: .token, token sent to the Mac
  • Mac pushes status changes (p10) and progress (p5, throttled)
  • Final update carries the alert, so there's no second banner
  • Stale after 15 min when push drives the card

Builds on phase 2. Card state decoding stays backward compatible.

Phase 4 · later

Nice to have

  • Push-to-start for runs begun on the Mac or by Bots
  • App badge = open asks
  • Control Center “New chat” control
  • Quiet hours

Both other apps skipped push-to-start. Try it again against iOS 27.

07 · Your call

Three decisions before building

Who runs the relay?

Decided 22 Nov 2026: you run a stateless Cloudflare Worker that stores nothing. Push is opt-in for each Mac. Android gets FCM in the same protocol revision as iOS. See section 05.

Approve from the lock screen?

Recommend: Deny from anywhere. Approve only from the banner after Face ID, where the command text is visible. The card only offers Review, because its pushed state has no text. Hermex chose “never answer from a banner”; this is a middle ground.

Message text on by default?

Recommend: On for banners, because it's sealed end to end. Off for reply text on the Lock Screen card, matching Hermex. Bot handoff steps keep fixed copy whatever the setting, as they do today.
