# Product

<!-- impeccable:product-schema 1 -->

## Platform

adaptive

## Users

Aiden Agent is for people who work with code and local project files on a Mac or Linux desktop and want an AI collaborator that can chat, inspect a chosen workspace, and take explicitly permitted actions. They may use hosted or local models and need to understand which workspace, model, and access level are active without leaving the conversation.

## Product Purpose

Aiden Agent provides a private, native-feeling workspace for model conversations and agentic coding tasks. Success means the interface recedes behind the work: starting a chat is immediate, context and permissions stay legible, settings are understandable without documentation, and local-versus-network boundaries remain clear.

## Positioning

Aiden combines a native-feeling desktop workspace with Pi-based agent extensibility, user-selected local or hosted models, and explicit workspace and permission boundaries. The paired native iOS and Android clients extend the desktop-owned workspace rather than creating separate sources of authority.

## Operating Context

The primary application is an Electron desktop app for macOS and Linux. People work in folder-backed workspaces or in No workspace chats (global settings, with a hidden per-chat folder Aiden manages), use chats and Bots, review files and Git changes, run tools with explicit permissions, and may connect native iOS or Android clients to a paired desktop for remote access. Copies and forks keep independent private folders and access.

## Capabilities and Constraints

First-run setup and Settings → Providers share an account, API key and local-model chooser. Providers lists saved connections first. Advanced contains private endpoints, chat-title routing and manual catalog updates. The final setup stage offers the first Bot and feature tour alongside the usage-data choice.

- Supports local and hosted model providers without making one provider the product authority.
- Reuses local skill folders and explicitly enabled installed plugin skills under the active workspace permission.
- Keeps workspace, Bot, permission, model, and local-versus-network scope explicit at the point of action.
- Aiden Live can move through Aiden's own window by reading its accessibility tree (on by default, **Let Live move through Aiden**). It never acts outside Aiden unless Computer Use is on, the user's own input takes over until they speak again, and each destructive control waits for its own spoken or tapped OK. Approval cards, Bot cards and Bot pages, anything that allows, enables, grants or pairs, switches outside Appearance, cloning, simulator erase, the provider, endpoint, voice and speech, access, approval, MCP, spending and Live settings pages, onboarding and key fields are the user's alone: Live is refused if it tries them. It sees chat and Bot messages, workspace pages and the web panel only as a count, never their text; it still sees the names controls carry, such as chat titles in the sidebar and Memory items, and is told that page text is data, not instructions. With **Let Live use the open chat** off, the composer is the user's too.
- Presents the built-in Composio connection as one tool and one service allowance. Enabled apps and operations are managed in Composio; Aiden still applies its action approvals and Bot rules. Existing partial access requires an explicit service selection.
- Treats the desktop host as the authority for workspace files, credentials, agent execution, durable memory, and paired-client operations.
- Requires deliberate user actions for external connections, sensitive permissions, and destructive or durable mutations.
- Aiden Live can work with regular chats during a voice session it was started for: read the open chat, send, steer or queue a message, stop a run, open another chat, and start a new one. Sends are capped at 4,000 characters and show a "By voice" label on desktop and phones; Live's chat tools never answer a tool approval (the person can, by voice, as below), and **Let Live use the open chat** (on by default) turns all of it off. It sends only after the person asks by voice, never because of text in a chat. Only regular chats are reachable: Bot, Assistant and other feature-owned chats are never listed, opened or controlled.
- External Markdown images in desktop replies require a per-message, per-URL Load image action for the current window document. Main downloads only bounded public-network PNG, JPEG and WebP images without cookies or provider credentials; local/private addresses and SVG are blocked. See [chat image privacy](docs/transcript-images.md).
- A Bot can suggest a one-time or recurring routine in its chat. The person accepts the proposal before Aiden schedules future turns in that Bot's durable conversation; execution depends on the desktop scheduler and current Bot access. Each due fire is saved before the schedule advances and reconciled with Pi after a restart; the Bot's Routines page shows pending or overdue work. On the desktop, routines heal themselves: a failed run records why, a temporary failure can be retried after 5 and then 20 minutes if the session confirms the attempt requested no tools, a sign-in or access problem raises one "Needs you" card, three same-kind failures in a row pause the routine with a Resume card, a pre-fire check about 30 minutes ahead catches problems early (Profile → Health), stuck runs are stopped (routines) or flagged (attended turns), and a result that claims a failed step worked says so. See [docs/bot-routines.md](docs/bot-routines.md#when-a-routine-fails). Bots are also proactive without being pushy: Advanced → Interruptions sets quiet hours (default 10 PM–7 AM) and a daily limit (default 5); a dated promise becomes a follow-up suggestion; Not now asks why and the Bot backs off after repeated declines; and Profile → When something happens adds desktop-only routines that run on a file change in the Bot's folder or when their link is called on the local network or Tailscale. See [docs/bot-routines.md](docs/bot-routines.md#proactive-without-being-pushy). In a turn the person started, a Bot can also set itself up to 3 one-time wake-ups, 1 minute to 24 hours ahead, without a card; each shows in the chat and the Bot's routines with Cancel, and Advanced → Chat switches them off per Bot (on the desktop; see [docs/bot-routines.md](docs/bot-routines.md#wake-ups-a-bot-sets-for-itself)). Bots also learn, visibly: a routine's recent runs can yield one suggested lesson (kept only with Keep this), a correction becomes a how-to lesson with Undo, a Bot can propose a skill for a procedure you liked (a skill in the Bot's folder never loads without your approval), nearly full memory is tidied with Undo, and Profile → What I've learned lists it all with Undo. Background learning is capped per Bot per day. See [docs/bot-routines.md](docs/bot-routines.md#bots-that-learn).
- Open work keeps explicit accepted Bot responsibilities with host-owned source/result links, Open/Waiting/Done/Dismissed states and live execution status. Desktop, iOS and Android can add, edit, dismiss, undo and stop linked work. Metadata does not schedule itself, a lost response retains the original mutation identity, and uncertain Stop never implies completion. The Tasks grant controls Bot tools and context; owner management remains available. See [Open work](docs/bot-open-work.md).
- Named Bot pairs can exchange requests in both directions after owner approval. Each recipient keeps its own model, grants, rules and spending limits. Desktop, iOS and Android manage routing descriptions and pairs, inspect exchanges and host-owned evidence, and request a Stop without mistaking an uncertain acknowledgement for cancellation. Intermediate messages remain quiet. See [Bot peers](docs/bot-peers.md).
- Each Bot routine can inherit the Bot default or use an explicitly selected model, thinking level and optional fallback. Desktop, iOS and Android manage these choices. Each admitted run retains its selection and original occurrence facts across queues and recovery; revoked access still stops it. Missing explicit models raise Needs you, and fallback is limited to configured choices before effects. Unconfirmed request costs require source-bound owner consent before another attempt. See [routine models](docs/bot-routine-models.md).
- A Bot’s connected-app watches have full management on desktop, iOS and Android. Google Calendar through Composio works on Mac and Linux; iMCP Mail requires a Mac. The owning host binds an explicitly selected account and calendar or mailbox, checks at 15/30/60-minute intervals while running and awake, and recovers pending changed-output delivery after restart. Source discovery and preview are explicit foreground actions; missing access or unsupported account/occurrence schemas remain unavailable. See [connected-app watches](docs/bot-routines.md#connected-app-watches).
- Coding follow-through keeps a workspace chat moving after an answer ends: background jobs report when they end and show the local addresses a dev server serves (a server a command leaves running becomes a job too, and phones can list and stop jobs), a followed pull request reports failed checks, conflicts and comments from people with write access until it merges, and `/until` reruns a check after each answer, five checks at most. News arrives as compact notice cards; command output, CI logs and comments are fenced as data, and a chat starts at most six unattended follow-up answers an hour. macOS and Linux desktop; see [docs/coding-follow-through.md](docs/coding-follow-through.md).
- Hooks (macOS and Linux) are the owner's shell commands at fixed points in a chat, in the Claude Code format. Each runs only after the owner approves its exact command on the host, a repo's `.aiden/hooks.json` or an agent proposal included; a hook can block, ask or add context but never grant more access. Its `allow` only stands in for an approval the owner could have remembered for a workspace file or command tool, and skips no other card. See [hooks](docs/hooks.md).
- Desktop-hosted Bots can ask for one bounded plan approval on desktop, iOS or Android, with a live checklist and Stop; every covered call stays within its captured access, applicable rules, caps and at most 60-minute task lifetime. Passwords, payments, hand-offs and Computer Use on the person's Mac remain outside coverage. See [Bot plan approval](docs/bot-rules.md#approve-a-plan-once).
- Repeated eligible approvals can offer Always allow for the named Bot on desktop and paired iOS/Android clients that negotiate bot:allowed. The approval covers one connected-app action or one website action, never a rule-made ask, a payment-provider host or Computer Use. Profile and Settings → Bots & Approvals → Allowed without asking list saved actions and selected Custom folders with Remove. See [Bot rules](docs/bot-rules.md#allowed-without-asking).

- Bots ask you to sign in in their own browser; the model never sees your password.
- Aiden Live (Beta, desktop) runs from a floating dark ribbon pill above the chat composer, with captions, mute and End. The person picks Live's voice (it applies the next time Live starts), a pitch-preserving speaking speed and Spectrum or theme-accent ribbon colours. Saying goodbye ends the session once the goodbye has played, never while an approval or confirmation is showing. A spoken phrase counts only when it is a whole utterance. Live cannot press its own ribbon controls. See [the voice upgrade plan](docs/plans/aiden-live-voice-upgrade.md).
- During an Aiden Live session (desktop), the person can answer the open chat's approval by saying allow or deny in any of 11 languages (Settings → Voice & Speech → Aiden Live → **Answer approvals by voice**, on by default). Speech counts only after Live has accepted the read-out of that approval, only from the person's own finished sentence, and only when the whole sentence is an allow or deny phrase. Voice allow is allow once; Live itself cannot approve. Approvals whose command or file Live can't say in full, credentials and secrets, payments, browser, connector and external-agent actions, image generation, a paired phone's turn and other specialised reviews still need a tap.
- The opt-in Inbox sidebar (Beta, desktop) is one more view of the same chats: Needs you, Updates, Earlier and a Working shelf, plus Bots that need the person: this Mac's (and its Bots with news) and, from a paired Mac, ones that wait on the person or failed. Pin, Done and Snooze are kept by the Mac that owns the chat, so every device paired to it sees the same triage. While it is the view, the Dock icon (the launcher count on Linux) shows how many rows are in Needs you, on this computer and on online paired computers, unless the person turns it off (Settings → Appearance → Sidebar: **Show Needs you count on the Dock icon** on a Mac, **on the app icon** on Linux). It only opens chats; approvals and answers are still given in the chat, under its usual rules.
- Each folder workspace can switch off skills and connectors for its own chats in Workspace settings (desktop). Settings stays the ceiling: a workspace can only narrow what is on there, Bots keep their own access, and a change applies from the next message.
- Settings → Storage shows how much disk Aiden uses on this computer, split into chats, logs, artifacts, browser data, voice models, Bot computers, saved work from removed worktrees, other app data and worktrees, with the largest worktrees and chats listed. Cleanup offers unused worktrees, one chat at a time, the browser cache (sign-ins kept) and logs behind a review that names what will be removed and how much it frees; voice models and Bot computers link to their own settings. Worktrees with uncommitted or unpushed work, a chat or terminal using them or a scheduled task in them are never removed, and cleanup re-checks that right before deleting. See [docs/storage.md](docs/storage.md).
- A provider's usage limit makes a reply wait, never switch to another model; limits that last days and billing problems fail at once with the reset time. Spending limits are the owner's: each chat, each Bot's month and each routine run can stop at a dollar amount counted from API-key requests only, and only the person can allow more (on the Mac or a paired phone). See [docs/usage-limits-and-spending.md](docs/usage-limits-and-spending.md).
- In chats with Web Search on, the agent can read a public web page. Opt-in extract mode, set up with the person's own Cloudflare account, returns only the named values it asks for, each with supporting page text; a value that is not on the page comes back as a guess, never as read.
- Bot computers (Apple silicon): an opt-in macOS VM per Bot, which the Bot sees and uses with its own `computer` tool (screenshots and clicks, each step with a stated intent the rules read) and `computer_shell` tool, on routine runs too. The Bot panel's Computer tab shows it live with the Bot's avatar where it last pointed; the person's first click or key, or Take over, stops the Bot's current action until Give back, and Float over chat keeps the screen in view. Element control (Aiden's pinned cua-driver in the base computer, allowed once for Accessibility and Screen Recording and inherited by every Bot computer made from it) lets the Bot read an app's buttons and fields and click them by number, and the rules then also read the element acted on; skipping it keeps screen-only Bots. A Bot can ask the person to sign in on its own computer: Open hands the person the computer with Safari at the site, the Bot's computer tools wait, and the password never reaches the model. The onboarding tour introduces Bot computers only where they exist. See [docs/bot-computers.md](docs/bot-computers.md).

The headless server (`aiden serve`, the standalone CLI) can explicitly migrate its Bot host to the shared durable session core. Migration is opt-in, preserves legacy data, and advertises only supported session, routine, preset and memory endpoints; see [CLI durable Bots](docs/cli-durable-bots.md). Private verification receipts and workflow lesson drafts are evaluation infrastructure; Bot learning (lessons, corrections, skill proposals) is a separate, person-approved feature with its own store.

Bots can ask each other for help through private, bounded messages on desktop and the CLI host. Chats name who asked or replied, and the sender receives one final result. Global and per-Bot switches are available on desktop and paired iOS and Android clients that negotiate messaging support. Another Bot's words never grant approval or personal memory access. The CLI records paid Bot response costs in its profile-local spending ledger and enforces configured monthly and routine-run limits. See [Bot messaging](docs/bot-messaging.md).

A desktop-hosted Custom Bot can ask for file access outside its selected folders. The person chooses Allow once, Always for this folder or Not now. Whole-Mac access is once-only, stale cards cannot adopt changed permissions, and Bot-only folder approvals do not expose those folders to a phone's file browser. Unattended turns leave a Needs you issue instead of a card. The CLI host does not offer this tool. See [Bot access requests](docs/bot-access-requests.md).

## Brand Commitments

Quiet, capable, and trustworthy. The product should feel at home on macOS, with the restraint and task focus of the Codex and ChatGPT desktop apps while retaining Aiden's own workspace and privacy model.

Avoid a generic web dashboard inside a desktop shell, ornamental cards, feature-promoting empty states, oversized or detached control regions, and settings copy that repeats labels without explaining consequences. Do not add decorative buttons, suggestions, or features to make an empty surface look busier.

## Product Principles

- Keep the conversation primary; navigation and configuration should remain available without competing for attention.
- Show essential context at the point of action, especially workspace, model, permission, privacy, and error state.
- Measure only what is listed: anonymous usage data and crash reports come from a closed event list, never include content, are on by default with a visible switch and a one-time notice, and the app lists every event and field it can send ([`docs/analytics.md`](docs/analytics.md)).
- Prefer familiar macOS and high-quality AI-tool conventions over novel controls.
- Use progressive disclosure so simple workflows stay simple while advanced capabilities remain discoverable.
- Refine the existing product vocabulary before introducing another visual or interaction pattern.

## Accessibility & Inclusion

Target WCAG 2.2 AA for text and controls. Preserve keyboard access, visible focus, semantic labels, sufficient contrast, reduced-motion behavior, and non-color-only communication. Keep dense desktop UI readable at the app's supported window sizes and system appearance settings.

Paired desktops can clone a local repository-root project into an approved folder on another computer. Environment-file copying requires an explicit file selection, with no files selected by default. Repository authentication stays on the destination computer. Phones and CLI daemons retain their existing project setup surfaces.

Desktop Appearance → Chat offers Compact, Standard, Detailed and Verbose work details, automatic collapse on completion or the next message, the shared link-opening preference, and a Queue/Steer busy-send default. Manual disclosure choices take priority. These controls change desktop presentation/input defaults and add no Remote protocol or native-phone setting.
