# Routine models and Resume on Android

A host offering and granting `bot:routine-models` (Remote revision 59) exposes **Bot profile → Routine models**. Its directory includes every owned scheduled, event and connector watch routine, including event routines that Android’s scheduled routine list does not otherwise project. Older hosts hide the Profile entry; a restored destination explains the missing support or grants. No feature token or pairing capability is added.

Reading the directory, saved choices and recent runs requires Bot-read and chat-read visibility plus the negotiated capability. Catalog discovery, Save and Resume status additionally require Bot-edit permission. Read-only devices show saved choices and run facts without fetching the catalog or enabling changes. Loading this page does not contact providers or run a routine.

The default is **Inherit Bot model**. Choose an exact provider/model and one of the thinking levels the host offers for it, or clear the override. Fallback is optional and must be explicitly selected, with its own exact model and supported thinking. Unavailable saved choices are kept and labeled; a catalog refresh never silently substitutes another model or thinking level. The Save explanation states the routine-only grant: the host admits it under the Bot’s existing rules and spending limits, without changing the default model or unrelated grants. Model edits affect future fires, not work already admitted.

Recent run rows display host-produced chosen and actual provider/model/thinking labels, fallback cause, admission and actual start time, and the scheduled occurrence in its host-provided timezone. Delay is shown only when an actual start is recorded and is at least a minute late. Missing run facts are not reconstructed from the current choice. Provider identities, revisions and decimal submission identifiers remain exact strings.

The page refreshes cached host settings/run facts every 15 seconds while resumed and stops on pause/disposal. It preserves the authored selection if the host revision changes. **Keep draft and review current revision** explicitly accepts the latest revision before Save; **Use saved choice** discards the draft only when chosen. Refresh never sends a write.

Model drafts, their baseline and the frozen UUID/full save payload are durably committed before transmission using Android’s existing encrypted preferences, excluded from backup and device transfer. Scope includes host, device, pairing generation, Bot and routine. Atomic compare-and-replace prevents another activity/controller from overwriting an outstanding identity. Pairing replacement, revocation and forgetting purge the namespace and fence late callbacks. Confirmed Bot deletion from Profile, the Bots list or chat also purges only that Bot’s model and Resume records and removes its memoized model controllers. Live journal handles are invalidated by a Bot-scoped generation, so held reads/replies cannot recreate the deleted state. Other Bots and pairings are preserved; a failed or uncertain deletion keeps the original requests. A first typed `unavailable` or lost/unreadable response retains the request. Every later refusal also retains a previously unknown request. Explicit retry uses the original UUID, revision, catalog revision and exact selection; a matching authoritative `lastMutationId` can settle it. Matching content or timestamps cannot. After 23 hours an ordinary unknown request remains visible and readable but is not replayed or replaced by a new UUID.

**Resume interrupted work** is separate from **Resume Bot** on a paused Profile. Unpause uses the existing pause route and never performs a cost acknowledgement. Choosing Resume on interrupted work checks the host’s passive status first on capable hosts. If unknown cost requires consent, Android shows the fixed warning:

> The cost of an earlier provider request is unconfirmed. Resuming may incur another charge. Known spending limits still apply.

Only **Resume and acknowledge** sends `acknowledgeUnknownCost: true` with the exact positive decimal `expectedSubmissionId` and opaque `expectedCostReceiptId` from that status. A true status requires both the interrupted input and `costReceiptId` (`cost_` followed by 64 lowercase hexadecimal characters); a false status forbids a receipt token. Consent stays tied to that exact receipt, even if another device resumes the same input and creates a new unknown cost. The host refuses an old or tampered receipt; reviewing a new status and confirming again is required for the new receipt. If the displayed session changes, the screen closes or the foreground visit ends before confirmation, the consent is discarded and Resume must be reviewed again. A delayed preflight, including a response requiring no acknowledgement, cannot start work after its session or foreground visit changes. The host also refuses stale submission consent. Ordinary Resume sends `{}`. A frozen unknown `{}` request cannot acquire consent because a capability arrived later.

Resume’s UUID, exact request and original attempt time are committed in the same protected pairing/Bot-scoped store before POST. Unknown responses survive restart and every subsequent refusal. A first typed `idempotency_in_flight`, internal, recovery or unrecognized outcome also retains the exact request regardless of HTTP status or `retryable`; only a recognized refusal before effects may release a first-attempt key. This Resume-specific rule also applies to legacy empty-body controls; explicit retry reuses the original input, cost receipt and UUID without another preflight or an upgrade to a different source or receipt. Acknowledged requests wait when routine model access is missing, retaining their exact token through reconnect and foreground changes. Older acknowledged journals without a receipt token, and malformed journals, fail closed without a POST or a fresh preflight; older ordinary `{}` requests remain valid. Expired unknown requests remain retained after the 23-hour replay cutoff. No session snapshot or changed content is treated as a Resume receipt. There are no automatic Resume retries. A successful replay settles the exact request but its cached control response is historical. Android passively reads the current session for both managed and legacy Resume retries, preserves the visible interruption while that read waits or fails, and does not wake the message outbox. Normal epoch/sequence, pairing and foreground-visit fences still apply.
