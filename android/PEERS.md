# Bot peers on Android

On a Remote revision58 host offering and granting `bot:peers`, **Bot profile → Bot peers** manages owner-approved pairs. Metadata settings and the read-only Bot catalog require Bot-read access; writes additionally require Bot-edit access. Exchange lists, details, transcript links and retained evidence also require chat-read access. Old hosts hide the entry; restored destinations explain missing support or access. The capability is negotiated alone, without a new feature token or pairing permission vocabulary.

The owner can edit a bounded routing description shared only with approved peers, approve a named pair in both directions after a confirmation naming both Bots, and revoke the pair. The description is owner-authored routing metadata, not permission to share private chats, instructions, tools or credentials. Pair approval never broadens either Bot’s own rules, grants, model or spending limits. Unavailable catalog choices remain unavailable. A changed settings/catalog revision requires explicit review rather than silently rebinding an approval. Description drafts survive conflict and unknown outcomes; Keep my draft rebases only after the person reviews current settings. Read-only pair metadata and the catalog remain useful without chat-read or write permission. Owner names come from the host’s Bot summaries; no provider, model-catalog or authentication request is started by this screen.

Exchanges show sender and recipient names, request, result, host execution/return state, update time and blocking reason. **View source** and **View result** fetch actual retained plain text, with a truncation notice; a missing source (including status/FYI messages) reports unavailable. Host-owned exchange/source IDs never become arbitrary paths. Evidence source ownership is the sender Bot and result ownership is the recipient Bot, independent of which Bot’s screen is open. Decimal submission and entry IDs remain strings. Evidence text is at most32KiB UTF-8 in a bounded256KiB response and is not put into mutation journals.

**Stop linked work** appears only for host-admitted Stop on that exchange. A requested, uncertain or stopping execution from another device allows passive refresh instead of generating a competing Stop. A locally requested Stop keeps its exact original nonce/body/revision through requested or uncertain success, restart, disconnect and permission loss. **Check Stop** replays that same request. After23hours it first performs a fresh scoped GET: only a matching `lastStop.mutationId` in requested/uncertain state proves the pending receipt is protected beyond ordinary retention and permits POST. A matching terminal receipt settles stopped, no-longer-running or blocked outcomes. Blocked explicitly says Stop was refused; it never claims cancellation. Earlier external effects may remain even when the host confirms stopped.

Before every POST the phone durably writes the exact UUID, full typed body and original start time to existing encrypted preferences excluded from backup and transfer. Records are scoped to host instance/device/pairing/Bot and, for Stop, exchange. Restoration never automatically sends. Concurrent controllers use compare-and-replace so an old window cannot overwrite another pending identity. Storage failure blocks transmission. First transport/typed uncertain outcomes (including unavailable or an in-flight409) stay frozen; every previously unknown request survives later refusal without a new UUID. Ordinary settings retries stop at a conservative23hours and await authoritative reads. Only exact host `lastMutationId`, same-key success, or exact terminal Stop evidence settles a pending operation; title, content and timestamps are never matching heuristics.

Forgetting or replacing a pairing purges its records. An accepted Bot deletion through Profile, Bots list or either chat path purges only that Bot’s peer settings/Stop records and memoized controller, invalidating held callbacks. Failed or uncertain deletion preserves them; other Bots/hosts/devices remain intact.

The resumed screen refreshes the host’s saved cache every15seconds and stops on pause/disposal. Refresh does not execute a Bot, send peer messages, discover tools or retry mutations. Transcript rows are quiet **Messaged…** / **Message from…** links to the scoped exchange; the final marker is display metadata and never drives unread state. Peer completion uses the existing routine-notification feed with `kind:peer`, stable ID deduplication and an initiating-Bot chat tap target. Late pairing or peer-capability loss prevents posting and cursor advancement. There is no new feed or per-hop notification loop.

JVM suites cover revision58 fixtures, strict DTO/privacy/Unicode bounds, routes/body/role validation, grant negotiation, real lost HTTP responses without automatic retries, durable restart and CAS behavior, conflict review, Stop acknowledgement/protected retention, read-only refresh, deletion and notification fences. Compose instrumentation covers explicit both-name pair review and read-only controls. Compile/JVM/lint results do not establish physical-device, TalkBack or visual acceptance.

An accepted or replayed pair decision cannot resolve a separate description conflict. The phone retains the original description baseline and draft until explicit review, including after restarting the controller. The focused controller suite passes11/11 after reproducing the missing-review failure before correction; the earlier full1,260-test run remains recorded separately.
