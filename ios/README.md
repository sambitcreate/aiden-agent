# Aiden On The Go

Aiden On The Go is the native SwiftUI companion for Aiden Agent on macOS and Linux. The paired desktop owns execution, persistence, providers, workspaces, and permissions; iPhone and iPad provide an authenticated remote control surface over a local network or Tailscale.

Opening a chat already running on another device restores available reply text, reasoning and tool activity from a revision 58 host. The phone resumes live updates from the same point. Earlier hosts use their retained run events.

If the selected computer is unavailable, choose **Switch connection** in the recovery panel to select another paired computer or pair another Aiden Agent. This remains available when a secure-identity failure prevents retrying.

Public new-chat links wait through connection readiness, then require confirmation of their installation and workspace and never start dictation. iOS App Intents use a one-shot foreground action inside the app process, so the intentional voice shortcut remains available. Existing-chat widget and notification links only navigate. Unsent composer drafts and unresolved-send records remain protected device-only storage and are excluded from backups, including stores from older versions during app startup without opening a chat; backup restore does not migrate them.

On hosts that offer and grant `bot:watches`, open a Bot’s profile → **Watches** to discover sources, create or edit a watch, pause or resume it, test a check, delete it, or explicitly **Run now**. Sources use host-produced provider, account and resource labels; connector bindings and credentials stay on the host. Discovery happens only when you tap **Discover sources** or **Refresh sources**. The host reports unavailable templates and repair guidance. Composio Calendar watches bind an exact account and calendar on Mac and Linux Electron hosts; iMCP Mail stays Mac-only. The standalone CLI does not offer watch management.

Watches execute on the paired host while Aiden is open and the host is awake. A test shows a bounded preview without advancing the watch baseline or running the Bot. Drafts and unresolved requests stay in this phone’s protected, backup-excluded private storage across editor close, disconnect and app restart; removing or replacing the pairing purges them. Stale saves retain the draft and require review of the latest host revision. An unknown write outcome freezes further changes. Refresh can confirm a create by its exact mutation-derived watch ID or a deletion by absence. Unknown edits, pause/resume and Run now retain their exact UUID and body until a successful response to that same request, including an explicit same-request retry; matching values at a newer host revision are not proof. A later denied retry keeps the earlier outcome unknown. Older hosts and pairings without `bot:watches` keep their existing profile.

In a Bot’s Advanced → Custom access, Composio has one service allow choice. Manage its enabled apps and tools in Composio; the Bot’s Aiden rules and a watch’s selected account still apply. An older partial Composio selection requires explicit review and replacement with the host’s current service choice. Other MCP connections keep their host-projected choices.

On hosts that offer and grant `bot:open-work` alongside Bot and chat read access, Profile → **Open work** manages unfinished responsibilities. Add a title and note, edit an item, record a waiting reason, mark it done, reopen or dismiss it, and use the host’s per-item **Undo last change** within 24 hours. Add records metadata only; it does not start a Bot run or schedule work. The host’s current source and result links open retained transcript text, with truncated excerpts labelled explicitly.

**Stop linked run** and **Stop and dismiss** appear only when the host can safely stop that item’s linked work. Mixed-input runs explain why Stop is unavailable. A requested or uncertain Stop stays unfinished until an acknowledgement arrives; Stop and dismiss waits for that acknowledgement before dismissing. Protected, backup-excluded drafts and exact pending requests survive disconnect and restart and are scoped to the host, paired device and Bot. Lost responses and typed `unavailable` outcomes keep their original UUID and payload, including after a later denied retry. Ordinary expired unknown requests are never issued under a fresh identity; pending Stop checks can keep using their protected original request beyond 24 hours. Pairing removal, revocation or replacement purges local Open work drafts and attempts. Older or ungranted hosts keep their existing profile.

On hosts that offer and grant `bot:routine-models` with Bot and chat read access, Profile → **Routine models** lists every existing scheduled, event and connected-app watch routine. Each saved routine and watch also has a **Model** action. Choose **Inherit Bot model**, an exact primary provider/model and one of its host-supported thinking levels, or an explicit fallback. Saving authorizes those choices only for that routine under the Bot’s existing rules and spending limits; its default model and other routines stay unchanged. New routines initially inherit. Missing choices remain visibly unavailable until you explicitly replace or clear them; the phone never substitutes another model. The model-only catalog loads only while this foreground sheet is open, using the host’s configured providers without phone credentials. Recent run details show the chosen and actual provider, model and thinking, configured fallback reason, admission, start, scheduled time, timezone and delay.

Model drafts and exact unresolved saves stay in protected, backup-excluded storage scoped to the host, paired device, Bot and routine. Stale revisions require an explicit review, and an unknown response retains its UUID and complete payload across restart or a later denied retry. Only a matching host `lastMutationId` or accepted response confirms the save. Requests older than 23 hours are kept as unknown and cannot be retried under a fresh identity. Pairing purge, privacy opt-out and Bot deletion remove the corresponding local journals.

Before **Resume** restarts interrupted work on a supporting host, the phone checks whether an earlier provider request has an unconfirmed cost. When needed, it asks: “The cost of an earlier provider request is unconfirmed. Resuming may incur another charge. Known spending limits still apply.” Only explicit confirmation sends the acknowledgement. The confirmation binds the exact interrupted submission and unconfirmed-cost receipt returned by the host. If another provider request becomes unconfirmed on that same submission, the old confirmation cannot acknowledge the new cost. An unresolved Resume retains its UUID, exact submission ID, cost-receipt token and original acknowledgement body across restart; an earlier empty request is never silently upgraded. Confirmation and pending preflight reads expire when the Bot or interrupted input changes, the chat is covered or left, or the phone leaves the active foreground. Returning requires a fresh owner action and review; the background hand-off feed remains live. Already dispatched unknown requests retain their exact identity and can only be explicitly retried from an active, visible visit. If routine-model capability disappears, an unresolved request blocks legacy fallback until access returns. A previously saved confirmed request without its required receipt token is kept unreadable and cannot be upgraded to a later token; ordinary saved empty requests remain valid. A first typed unknown or in-flight outcome retains the same request even when its HTTP status is 409 or its retryable flag is false; recognized before-effect refusals remain distinct. A replayed receipt settles that original request, then a passive session read supplies the current state; a cached historical Running reply never replaces newer interrupted work or starts another Resume. Profile **Resume Bot** only unpauses a Bot and never acknowledges a cost or restarts interrupted work. Older hosts keep their existing Resume behavior.

On a host that negotiates Remote revision 54's `bot:messaging`, the Bots list offers **Bots can message each other**. Advanced → **Other Bots** controls whether each Bot receives and sends messages. Turning messaging off globally disables both per-Bot switches with **Turned off for all Bots**. Older hosts show no messaging controls. Saves apply optimistically and reconcile against the desktop after a lost response; failures restore authoritative values and show an error.

Bot messages use the existing labelled transcript rows, including a saved answer returned while the sender was paused. A `message` notification opens the Bot's chat without starting or resuming a turn, and displays only the host's bounded, redacted preview.

Open `AidenOnTheGo.xcodeproj` and use the `AidenOnTheGo` scheme. Hardware verification is performed with terminal-based `xcodebuild` and `xcrun` commands against an explicitly selected physical device.

To verify ActivityKit persistence and authenticated reconciliation across two real app-host processes without reinstalling the app between phases, run:

```sh
npm run ios:activitykit-process-proof -- \
  --xcode-device-id <physical-xcode-udid> \
  --core-device-id <physical-coredevice-uuid>
```

The command rejects simulated or mismatched destinations, builds once, starts a uniquely identified Live Activity, confirms the first test host has exited, relaunches the installed destination artifacts, reconciles through `AidenRemoteClient`, ends the activity, and moves its temporary result bundles to Trash. Its cleanup phase is best-effort even when a proof phase fails.

Bot peers (Remote revision 59) are managed from a Bot’s Profile on hosts that negotiate `bot:peers`. The owner can edit the routing description shared only with approved peers, approve a named pair in both directions, revoke it, and inspect exchanges. Each Bot keeps its own rules, access and spending limits. Read-only owners can inspect settings and the local host catalog; exchange history additionally requires chat read access. Unavailable Bots remain visible and names never rebind a saved pair.

Exchange details show host state, request/result text, bounded source/result evidence and a Stop action for only that linked exchange. Requested or uncertain Stop stays pending until a matching host acknowledgement; earlier effects may remain. Quiet Messaged / Message from transcript rows (including a host-marked final update) and peer-linked Open work open the same scoped exchange. A `kind: peer` final notification uses the existing foreground feed, deduplicates its stable ID, and opens the initiating Bot’s chat. Hosts omit peer content for clients without the capability.

Peer mutations and Stop use protected, backup-excluded journals scoped to host, device, Bot and exchange. A lost or typed uncertain response keeps the exact UUID and body through restart, disconnect, capability loss or a later rejection. Settings conflicts retain drafts for explicit review. Ordinary unknown requests are not replayed after 23 hours; an older Stop is checked only when a fresh authoritative read proves that exact Stop remains requested or uncertain. Accepted Bot deletion and pairing/privacy removal purge the matching journals and invalidate live controllers. Phones never deliver delegated work or hold peer execution authority.

Pair approval and revocation preserve a separate unsaved routing-description draft, including after restart and matching-receipt recovery. A host-pending Stop allows passive refresh rather than a fresh Stop UUID when this phone has no saved action. Notification posting rechecks pairing and peer access after the system call returns; revoked access cannot advance or recreate the old cursor or delivered-ID set. An already accepted system banner cannot be withdrawn through this notification abstraction.

Hosts that announce Remote revision 55's `bot:access-requests` are asked for that capability in a separate foreground connection negotiation. Bot chats then show bounded access cards with only the host's offered **Not now**, **Always for this folder**, and **Allow once** actions. Whole-Mac cards offer no persistent grant. Retrying the same choice after an uncertain response keeps its idempotency key and body. Choosing a different answer sends that choice with a different key. An expired card stays dismissed; other failures restore it unless a newer feed update has replaced it. Access-needed issue cards offer **Not now** to dismiss them and may offer **Allow this folder** for a persistable folder. A successful answer with `savedForFuture: true` shows "Folder approval recorded." This acknowledges the exact committed approval operation, even when replayed after the folder was removed. It does not confirm current saved access, restore the old card, or grant access to an ended task. Older hosts keep their existing behavior.

Hosts that offer Remote revision 56's `bot:plans` are asked for it in a separate capability call. Bot chats show the host's plan with its reason, ordered steps and coverage. **Approve plan**, **Not now**, **Show details**, and an active plan's **Stop plan** use the same wording as desktop. Active checklists show step states, remaining minutes and usage counts; ended plans show compact progress. Long reviews scroll with decisions kept outside the review area. Visible pending plans hold Send while the draft stays editable. File coverage names the enforced location, read/change mode and any plan-only lifetime. Show details retains the exact location. If the location cannot fit safely, the phone omits that pending card and keeps the waiting signal; review and approve on the host desktop. Send remains available in that fallback, and a delayed phone approval is refused before granting access. Active plans retain Stop with a safe folder summary. A receipt acknowledges the answer; the host's session or event stream changes or clears the card. A `409 plan_expired` clears only the matching unchanged card. An identical pending-plan snapshot during the answer does not invalidate that refusal. A changed plan or explicit response generation still fences the old response. Unknown-outcome retries reuse the same plan-and-decision key and body; another decision gets its own key and body. Late answers cannot replace a newer card. Older hosts show no plan card or controls.

Hosts offering Remote revision 57’s `bot:allowed` are asked for that capability alone. When it is held, Bot profiles show **Allowed without asking**, with a count from the complete paginated rule-and-folder list. Remove keeps the row disabled until the host returns a fresh list; failures retain the row and show an error. Stale or foreign cursors restart from the first page. Rule rows show usage; folder rows show only their added date. Host-offered approval counts enable **Always allow for <Bot>**. B folder counts require both `bot:access-requests` and `bot:allowed`. Unknown outcomes retain the exact wait, decision and scope key/body; another scope or decision uses another key. **Always allow requested.** acknowledges the choice, while the host confirms saved access. Earlier hosts retain their existing UI.

For focused allowed-list, approval and protocol regression tests from the repository root, use an explicitly selected simulator and a new result path for each run:

```sh
DEVELOPER_DIR=/Applications/Xcode-beta.app/Contents/Developer xcodebuild test \
  -project ios/AidenOnTheGo.xcodeproj -scheme AidenOnTheGo \
  -destination 'platform=iOS Simulator,id=2FBB28DB-0E20-495C-B964-5A678C417E89' \
  -derivedDataPath /tmp/aiden-bot-messaging-ios-derived \
  -resultBundlePath "/tmp/aiden-bot-allowed-$(date +%s).xcresult" \
  -disableAutomaticPackageResolution -onlyUsePackageVersionsFromResolvedFile \
  -collect-test-diagnostics never \
  -only-testing:AidenOnTheGoTests/AidenBotAllowedTests \
  -only-testing:AidenOnTheGoTests/AidenBotSessionApprovalTests \
  -only-testing:AidenOnTheGoTests/AidenRemoteClientTests \
  -only-testing:AidenOnTheGoTests/AidenRemotePhase0Tests \
  -only-testing:AidenOnTheGoTests/AidenBotPlanTests \
  CODE_SIGNING_ALLOWED=NO
```

Use an installed Xcode and simulator destination appropriate to your machine. Simulator XCTest with signing disabled verifies compilation and behavior, not physical-device, Keychain, entitlement, or release acceptance.

Bot notification polls retain the fetch's original negotiated visibility through system permission and notification posting. Losing Bot/chat read, messaging, issue, access-request or peer visibility keeps the cursor and delivered IDs unchanged until a fresh authorized poll; issue rows do not expose their private subtype. Host support alone never grants visibility. Older hosts without a separate support inventory retain the existing Bot/chat read baseline for routine notifications only. A system banner already accepted before access changed cannot be withdrawn by this notifier.
