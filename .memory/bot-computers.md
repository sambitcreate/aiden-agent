## Lume (pinned 0.6.1)
- Pins: `scripts/bot-computers-lume-pins.mjs`, `resources/bot-computers/lume-artifact.json`, compiled copy in `lume-binary.ts` (`lume-binary.test.ts` checks drift). Vendored by `scripts/vendor-lume.mjs` to `build/bot-computers/lume.app`, packaged at `Contents/Helpers/lume.app` (signIgnore covers the whole bundle; not in `mac.binaries`). `verify-macos-package.mjs` checks hash, requirement, `com.apple.security.virtualization`, `embedded.provisionprofile`.
- `resolveLumeInstallation` (darwin+arm64 only): lstat non-symlink, X_OK, size, realpath inside the bundle, sha256, plutil id/version, `codesign --verify --strict --deep -R=`. The host caches the result per launch.
- CLI facts from Lume source (`lume-cli.ts`, `lume-output.ts`, `tests/e2e/lume-fake.mjs`): `delete` needs `--force` (else it prompts); `ssh` options go before the name; `run --detach` re-execs through nohup and reports failures only in `--log-file`; `--shared-dir` splits at the first `:` (refused in paths) and a `:` in a VM name triggers a registry pull; `get`/`ls --format json` print a pretty JSON array with `\/` escapes; status can be `provisioning (stale)`; the reported VNC host is hard-coded `127.0.0.1`; logger lines `[ts] LEVEL: msg` go to stdout (`LUME_LOG_LEVEL=error`).
- Env: fixed PATH, telemetry/update off, `HOME`/`CFFIXED_USER_HOME`/`XDG_*`/`LUME_HOME` under `userData/bot-computers/home`, passthrough only LANG/TMPDIR/USER/`__CF_USER_TEXT_ENCODING`/LC_*. The fake takes `--fake-config <json>` because the env allowlist strips `AIDEN_*`.

## Host (`main/services/bot-computers/host.ts`)
- Root `userData/bot-computers/`: `vms/` (Lume storage), `home/`, `logs/`, `restore-images/`, `base-shared/`, `state.json` (0600), ssh key and `known_hosts`.
- Set up: `restore-image-download.ts` (pinned URL, `redirect:"error"`, Range resume, sha256, low-disk check before fetch) → `lume create aiden-base --unattended tahoe` → `provision.ts` steps install_key, capture_host_key (both over `lume ssh`), rotate_password (store first; dscl + keychain + kcpassword), harden_sshd (`sshd -T` check), disable_updates, suppress_prompts, shared_folder, shut_down → IPSW deleted. `updateBase` builds `aiden-base-next` and swaps.
- Free-space check: `bytes − partial + 60 GiB`; Settings states `requirements.setupFreeBytes` (same figure; host test ties them). Start needs 8 GiB available memory (`vm_stat`) and 5 GiB disk.
- Cap 1|2 (default 2), LRU stop of an idle computer (no lease, not person-controlled, no active action, unused ≥ 60 s), else queue (`waiting_for_slot`).
- A base build (Set up or Update base) holds a running place too (`baseHoldsSlot` counts in `occupied()`), because `lume create --unattended` boots the VM (Lume's `Create.swift` defaults to no display for unattended) and provisioning runs it. Before the install the host stops an idle LRU computer for it, or fails with `busy` when every running computer is in use; Bot starts meanwhile queue. A `create` that fails with the VZ limit maps to `vm_limit`. The fake's `limit` applies to unattended `create` as well as `run`.
- Memory: Set up checks 8 GiB before downloading (only when no Bot computer is running) and again before the install, after the place is taken.
- `setUp()` on a Mac whose store has a base routes to `updateBase()`: Settings' "Try again" after a failed update must never rebuild `aiden-base` in place (it deleted the working base first). Idle stop via injected `schedule` (default 10 min), re-armed while the person controls it or a lease/action is active.
- Each start: random VNC password, G22 loopback host check, plus `vnc-exposure.ts` probing every external interface address; either failure force-stops.
- Pause → `pauseBotComputer` in P2's `botPauseEffects`; delete → `deleteBotComputer` in `deleteEffects` after rules `forgetBot`, before `eraseBotData`. `deleteForBot` writes the store only when a record exists (deleting a Bot on a Mac without Bot computers creates nothing). Quit and delete use `lume stop --force`.
- `invalidateBotRuntimeInventoryAuthority("inventory_changed")` only on setup ready and Remove everything.
- Secrets: `aiden-internal:bot-computers:*` (guest password); Remove everything deletes the family.
- Trust material survives Update base (review fix): every base gets the one stored guest password (`BotComputerSecrets.get`, strict; a new random one only when none is stored), and `writeKnownHost` adds each base's host key beside the ones already pinned (each macOS install has its own key; clones keep their base's). Overwriting either broke SSH to every outdated computer, and a failed update broke the working base too.
- Set up resolves the bundled Lume before downloading, and `lume()` resolves it before creating `vms/`, so a missing helper never costs the 20 GB download or makes later deletes and startups run Lume. `deleteForBot` without a record treats the derived-name delete as best effort; with a record it still throws (Delete Bot retries).
- Shared starts (`SharedStart` in host.ts): every `ensureRunning` caller joins one start with its own signal; the start is abandoned only when the last caller gives up, and a caller arriving while an abandoned start winds down starts afresh. Progress goes to every joined caller.
- `reconcile` skips VMs this launch is using (`vmsInUse`: starting, running, stopping, and the base or staging base while a build runs); Lume reports a starting VM as running before Aiden holds its connection.
- `deleteVm` force-stops a VM that is still running first. Lume refuses to delete a running VM (it holds its resize guard; `delete` only stops a VM run by its own process), and Remove everything then deleted the files underneath it, leaving it running unseen. The fake's VNC child keeps running when its storage is deleted, like a real detached VM, and logs its pid (`kind: "vnc"`) so the harness kills every one.

## Owner-Mac / not yet
- Pause latency: `pauseBotComputer` awaits a graceful `lume stop --timeout 30` (then force) inside P2's `afterPaused`, which runs inside the per-Bot serialize queue before the paused state is published, so Pause can take as long as the guest's shutdown. Suggested: start the stop without awaiting its end (state is `stopping` at once), or force-stop on pause. Not changed: the wiring is Electron-only and has no test seam here.
- Guest command timeouts: `runGuestCommand` reports `timedOut` for exit 142 (SIGALRM through sh), but if the login shell execs perl, sshd reports an exit signal and OpenSSH exits 255. Confirm on the owner Mac before P10 relies on it.
- Fixtures in `fixtures/` are assumed until recorded on a Mac (README there says how). Unconfirmed: `--vnc-password` visible in `ps` (and VNC may use only 8 chars), perl in the guest, `sudo -S` stdin, `sshd -T` on macOS, `CFFIXED_USER_HOME` isolating `~`, exact VM-limit error text, whether Apple's URL redirects, base size (~50 GB).
- Disk-used overcounts APFS clones. NAT guests can reach services on the host.
- Update base swap window: `deleteVm(aiden-base)` then `clone aiden-base-next → aiden-base`. A crash between the two leaves no base; the next reconcile resets setup to not set up, the person must Set up (download) again, and the complete staging VM stays until Remove everything. Lume 0.6.1 has no rename, so a crash-safe swap would need the store to name the current base VM (a change to the fixed `aiden-base` name of G17).
- Onboarding gallery not updated: opt-in, Apple silicon only, nothing to configure at first run.

## P10: `computer` (VNC lane) and `computer_shell` (branch `wp/p10-computer-tool`)
- Tools: `computer-tool.ts` (`createBotComputerTool(botId, deps, {routine})`), `computer-shell-tool.ts`, schema `computer-schema.ts` (`intent` ≤120 required on click/double_click/right_click/drag/scroll/type/key, checked in `parseBotComputerCall`, not the schema), keys `computer-keystrokes.ts` (US-layout shift, Command = Super_L, Option = Alt_L, chord grammar and blocked combos from `parseComputerUseKeyChord`). P9's `keysyms.ts` has the same `chordKeyStrokes`/`textKeyStrokes`; dedupe onto it after both merge.
- Flow: `host.ensureRunning({reason: routine ? "routine" : "tool", onProgress → onUpdate})`, then everything under `control.run`, `sessions.screen(botId, signal, {reason})`, `host.touch` in finally (also after a call that only waited for Give back; the mid-action Take over path `return await`s the wait so the touch lands after Give back, not at Take over). Person in control at call time → nothing runs, `waitForBot`, returns `BOT_COMPUTER_GIVE_BACK_NOTE`; `BotComputerTakenOverError` mid-action → same, after releasing held keys/buttons without the aborted signal.
- Guidance: `botComputerToolDescription(attended)`. Sources pass `{routine, unattended: routine || telegram}`; unattended turns have no `hand_off` (UNATTENDED_WITHHELD), so their guidance says never enter passwords, codes or payments and say in the reply what the person must do. A test ties "description names hand_off" to `botToolVerdict("hand_off", …, turn)`.
- `BotComputerToolState` (one per process, made in sources-main from `botComputers().control`): newest capture's space per Bot plus a control epoch bumped on every `control.onChange` and the run key (vmName, VNC port and password; memory only). A click needs a capture from this run and epoch: else "Take a capture first", "restarted", or the give-back note.
- Captures: `screen.capture({format:"jpeg", maxWidth:1280, quality:70})`, re-captured with a smaller maxWidth when portrait; anything non-JPEG or over 1280 on the long side is refused. Coordinates scale `round(x * fbW / width)`, clamped to fbW-1; `recordPointer` gets framebuffer px with framebuffer size.
- Errors to the model: `BotComputerError` messages as is, anything else generic; the VNC password is redacted from any text. The shell: 120 s, 64 KiB, `run_command` formatting (20,000 chars via `boundedToolOutput`), truncation is a note not an error; Take over ends the local ssh (no pty, so the guest side is not signalled and can run on until it ends or the perl alarm fires; children of a compound command can outlive the alarm) and returns "may have partly run, or still be running". The guest user `lume` is an admin account (Lume's unattended preset); only sudo and system changes need the guest password.
- Runtime: capability kind `computer` ("Bot computer", available via `botComputersReady` dep = `botComputersEnabled() && host.baseReady()`; `baseReady` is a store read, true through Update base). `BotToolFacts.hasComputer` (granted && flag && `host.computer(botId)` exists). Verdict: capability, then hasComputer ("This Bot doesn't have a computer yet."), `computer` also needs image input; allowed on routine/tg (not in `UNATTENDED_WITHHELD`). `approvalFor`: `computer` → `botComputerAction`, `computer_shell` → undefined. beforeRequest keeps the newest 3 `computer` images (`BOT_OLDER_COMPUTER_CAPTURE_NOTE`).
- Activity: `computer` → existing phase `app` with app label "its computer" (`TOOL_APPS` in `renderer/shared/bot-activity.ts`; the `computer` phase word is "Using your Mac"), detail = intent; `computer_shell` → `command` with its description. No new Remote enum value; phones show "Using its computer". Timeline label "Use its computer", agent-steps verbs "Using/Used its computer".
- `host.ts`: a stopped computer clears its activity line (stale "Ada is using…" after restart otherwise).
- Tests: `computer-tool.test.ts`, `computer-shell-tool.test.ts` (bot-computers glob), `bot-runtime/bot-computer-tools.test.ts` (real turns over `assemblyDeps`; in `test:bot-runtime`), all in runtime-subagents.
- Not yet / owner Mac: P9's real screen (until then `sessions.screen` throws "isn't available in this build" and the tool returns that sentence); Apple VNC server keysym mapping (Super = Command?) and event pacing; guest timeout exit status (see above) affects the shell's "timed out" wording only.
