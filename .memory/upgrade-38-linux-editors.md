# Linux external editors (lane38)

The existing workspace editor picker is unconditional (`renderer/main/chat-pane.tsx`, `renderer/components/open-in-editor-picker.tsx`, `main/handlers/workspaces.ts`). Linux previously searched only Mac bundles and exposed Finder. The branch's union model now discovers executables in absolute inherited PATH directories across a broad Linux table (VS Code, Insiders, VSCodium, Zed via `zed`/`zeditor`, Sublime via `subl`/`sublime_text`, and others) plus Flatpak fallbacks. Candidates must be regular executable files and PATH-directory order is major over alias order. Launch uses the discovered path and one absolute folder argument without a shell, and resolves after spawn rather than GUI exit. Forced discovery at open detects removed/permission-changed launchers.

Linux exposes a `file-manager` id labeled "Files"; Electron `shell.openPath` still handles it. The `finder` id remains the macOS file-manager entry. Mac bundle matching, ordering, native icons and `/usr/bin/open -b` remain unchanged. No renderer, IPC DTO, native client, onboarding or catalog capability changed. Desktop files, Flatpak IDs and launchers outside inherited PATH are outside this bounded support.

References (read-only conceptual study): OpenCode v2 `packages/app/src/components/session/session-header.tsx` uses a Linux command mapping and `packages/desktop/src-tauri/src/lib.rs` routes opening by OS, but its `check_linux_app` returns true unconditionally; Aiden verifies executability instead. OMP `packages/coding-agent/src/utils/external-editor.ts` separates platform launch from editor selection; its shell-based user-command semantics are not appropriate here and were not copied.

Validation: four Linux production-discovery regressions fail against the original service. Focused service/preference tests pass after the fix; original Mac matching/open argument and refreshed-availability tests remain. Native Linux desktop acceptance is outstanding: tests inject process.platform on a Mac and run controlled executable fixtures.

Review correction: [Zed's official CLI reference](https://zed.dev/docs/reference/cli) documents both `zed` and `zeditor`. Search directories in PATH order, then `zed` before `zeditor` within each directory, retaining file/executable guards and one picker entry. Production discovery/launch fixtures cover alias-only installation, cross-directory precedence, same-directory tie-break, non-executable files/directories, removal and literal workspace argv.

Linux Cursor support is withheld in this PR. [Vendor support's Linux thread](https://forum.cursor.com/t/open-cursor-with-the-editor-window-active-not-the-agent-window/163197) says `--classic` is version-dependent and records ignored flags with Linux AppImage launchers, including a follow-up reporting failure after updating. [CLI installation](https://cursor.com/docs/cli/installation) documents the separate `agent` command, not a desktop editor contract. Later staff suggestions for recent builds do not establish a supported Linux launcher/version matrix. No guessed threshold, capability probe, flag, or native acceptance claim is introduced. An executable named `cursor` is omitted on Linux; a stale direct selection receives an explicit unsupported message. Existing Mac Cursor bundle discovery and launch are unchanged.
