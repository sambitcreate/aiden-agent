# Browser crash recovery ownership — 2026-09-19

Baseline: `5cc831a17aa8971fb5b89c7dd9278a6ec4022beb`; branch `feature/upgrade-18-browser`.

Recovery now owns exactly one timer, clears ownership before executing, and cancels on a new main-frame document navigation, manual Reload/Stop, tab close, or another crash. Stop leaves an honest manual-reload error. Same-document and child-frame navigation do not cancel recovery.

## Pullfrog: queued native crash notifications

PR #164 review `PRRT_kwDOTctvDc6j9uyL` demonstrated the reverse ordering: navigation starts before the old crash notification is delivered. Verified Electron `v43.1.1` `shell/browser/api/electron_api_web_contents.cc:2045-2065`: `PrimaryMainFrameRenderProcessGone` posts delivery, and details contain only reason/exitCode, with no originating document identity. The pinned Chromium `150.0.7871.114` implementation backs `isCrashed()` with native main-frame process status and resets it when the primary process becomes alive. Source links:
- https://github.com/electron/electron/blob/v43.1.1/shell/browser/api/electron_api_web_contents.cc#L2045-L2065 (SHA-256 `0ee59ca23c4706734a5f46681f9a8cff1b4a71f9d287104bf603227ab1885060`, MIT)
- https://github.com/chromium/chromium/blob/150.0.7871.114/content/browser/web_contents/web_contents_impl.cc#L12486-L12492 (SHA-256 `19371b9936b62a08fd58bc99e47ab1dd9e71cf47ab1d22ae438cbaeabfaa59ae`, Chromium BSD-style license)

Ignore a queued notification when the current native page is no longer crashed or a replacement main-frame load is underway. Do this before touching recovery state; also invalidate recovery at main-frame commit. This uses current native ownership because Electron does not expose the crashed document's identity in the queued event.

## Luna: current crash while the main-frame response is pending

The preceding broad native-loading check was insufficient. A real initial-navigation crash with a held main-frame response reports `isCrashed=true, isLoadingMainFrame=true`; published head `6287ef56` schedules no retry and leaves the browser state falsely uncrashed. The subsequent-navigation control can instead clear the native loading flag, so tests must distinguish these lifecycle states rather than require identical flags.

Capture whether the native renderer is already crashed when a new main-frame navigation starts. Such a navigation supersedes that crash. A crash that happens after navigation began still owns recovery even with a pending main-frame response. Reset suppression when Electron emits `frame-created` for the active primary main frame or commits navigation, so renderer recreation admits fresh crashes. The pinned Electron `RenderFrameCreated` source excludes speculative frames (`electron_api_web_contents.cc:1952-1974`).

The new initial-navigation test also proves `reload()` cannot revive a tab without a committed history entry. Capture the interrupted navigation URL and retry it with `loadURL`; keep ordinary reload for committed documents. Regression coverage requires native recovery to the intended URL and truthful `crashed=true, loading=false` state before recovery. No sleeps or arbitrary delays choose event ownership.

## Native terminal-navigation controls and abandoned recovery targets

Independent review hypothesized that failed replacement navigation would retain crash suppression indefinitely. Native controls on `629aeb20` do not reproduce that scenario: both HTTP 204 (native `did-stop-loading`, no normal commit) and a connection reset (real `did-fail-load`, native error-page commit) recreate a live renderer. A queued old crash correctly schedules no retry in both cases. No speculative deferred-crash recovery was added.

Pullfrog `PRRT_kwDOTctvDc6j-DAz` / comment `4052610222` identified a distinct reachable bug. After HTTP 204 cancellation or explicit Stop, the committed `/original` page remains current but `pendingNavigationUrl` still points to `/replacement`. A later genuine renderer crash retries the abandoned target. Both exact-`629aeb20` native regressions fail with `{originalRequests:1,replacementRequests:2}` instead of `{originalRequests:2,replacementRequests:1}`. The two queued-notification terminal controls pass. Evidence: `/tmp/aiden18-abandoned-target-baseline.log`.

Move the pending target into tab-owned state so Stop can discard it immediately, and clear it when native loading finishes with a live renderer process. Keep it when a current renderer dies during active navigation, including the zero-history initial-response case. Existing timer ownership and native crash-admission rules remain intact. No new event identity heuristics or recovery budget changes.

Native teardown ordering requires checking the OS process handle as well as `isCrashed()`: a subsequent held-response crash emits `did-stop-loading` while cached `isCrashed` may still be false. Electron 43.1.1 `GetOSProcessID` (`electron_api_web_contents.cc:2617-2620`) reads the primary renderer's native Process and returns zero when invalid. Chromium 150.0.7871.114 `RenderProcessHostImpl::ProcessDied` resets `child_process_launcher_` **before** calling any `RenderProcessExited` observer; `GetProcess()` then returns an invalid process. This provides a synchronous teardown boundary, independent of queued `render-process-gone` delivery or elapsed event-loop turns. The final implementation has no deferred target cleanup or stale cleanup callback. The earlier next-turn candidate was discarded.

Source: https://github.com/chromium/chromium/blob/150.0.7871.114/content/browser/renderer_host/render_process_host_impl.cc#L5573-L5615 and `GetProcess` at lines4041-4055. Together with the pinned Electron source above, this is the version-specific process-handle ordering relied upon. Aiden uses ordinary out-of-process renderers. Native tests observe PID zero during crash-induced stop and positive PID during healthy canceled/error-page completion without mocking native state. Rerun these native cases when upgrading Electron.

## Closeout: request-owned terminal navigation

The b7 `did-stop-loading` cleanup was insufficient: Chromium's global frame-tree stop may precede completion of the current main-frame navigation. Electron exposes no navigation handle in this event. A deterministic regression controls that documented global stop/loading snapshot while a real native main-frame request remains held, then forcefully crashes the renderer and checks recovery navigates to the held target.

The correction correlates each main-frame request ID with the existing tab navigation generation in the previously unused session `onBeforeRequest` callback. Matching HTTP204/205 response headers definitively retain the committed document; a matching request error clears the target only with a live native renderer. New navigation invalidates request ownership, and global loading-stop cannot discard it. Existing explicit Stop and commit handling remain. The existing session `onBeforeSendHeaders` preview authorization callback is untouched; no duplicate event listener registration is introduced. No new polling, defer window, permission, network destination, shared-client contract, or onboarding capability is added.

Sources: Electron43.1.1 `WebContents::DidFinishNavigation` returns for uncommitted navigation; the official WebRequest contract provides request ID, owning WebContents, resource type and per-request headers/error callbacks. Native HTTP204 probe `/tmp/aiden18-request-events.cjs` confirms no `did-fail-provisional-load` event and `ERR_FAILED` loadURL rejection. The racy global stop boundary is deterministic/source-backed rather than claimed as an independently reproduced natural Chromium race.
