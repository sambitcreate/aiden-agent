# MCP and Plugins remediation stack — 2026-10-13

Plan: `docs/plans/mcp-plugins-remediation-plan.md`. Origin: five read-only audits comparing Aiden's MCP stack with Pi 1.2.0 (`/Users/sambitbiswas/projects/opp/pi`).

Key facts established by the audit:
- Desktop and Aiden-managed CLI MCP both run on `@modelcontextprotocol/sdk` 1.30.0; `pi-mcp` is declared by the CLI but unused. The CLI also loads Pi's built-in MCP extension (native `mcp.json`, plaintext `mcp-auth.json`) next to Aiden's `aiden-mcp.json`.
- Every chat turn awaits `collectMcpAgentTools` (all enabled servers, up to 17 s each); every Bot tool call re-inspects every server with a fresh client (`inspectConfiguredMcpToolsForBotCatalog`).
- SDK bugs Pi fixed in its own client and Aiden inherited: no single-flight refresh (concurrent 401s can delete freshly saved tokens), cancelled requests re-sent after an auth refresh, `nextCursor: ""`/null rejected, non-object `structuredContent` rejected by `CallToolResultSchema`.
- Pi 1.2.0 breaking changes that touch Aiden: `before_agent_start` union (`session-parity.ts`), `pi-durable` `ToolExecutionResult.output`, patch anchor `enableInstallTelemetry` moved to `SETTINGS_DEFAULTS`, theme schema URL. pi-codemode 1.0.3 can crash the main process on a built-in-patching script (fixed 1.0.4).

Status: plan committed; slices are implemented by Opus 5.5 medium subagents, reviewed and committed by the orchestrating session.

## Slice 5: MCP latency and caching (2026-10-13)

- Codemode-lane turns (`workspaceCodemodeEnabled` in llm-client, shared by the pre-discovery deferral decision and the extension composition) admit MCP servers ready within 1.5 s (`admitMcpServerDiscovery`); slower servers join `McpLateDiscovery` within their own 17 s budget. Late tools reach the harness through `lateDeferredTools` (snapshotted once per tool object, duplicates ignored, never declared). `tool_search` and codemode scripts that search/list or reference an unknown `tools.<name>` wait on `settled(signal)` first. Late servers never add prompt instructions. Strict (scheduled) runs and non-codemode turns keep blocking discovery.
- `createMcpToolInventoryCache({ ttlMs })`: desktop uses 30 s for servers without `tools.listChanged`; the CLI still calls it without a TTL (unchanged). Closing a client forgets its entry. Calls after an idle reconnect go through `callMcpToolOnLiveClient`, which checks the live client's own inventory (unknown tool fails before dispatch).
- `McpRecentFailures` (45 s, per connection generation) skips a server that just failed (diagnostic `failurePhase: mcp-recent-failure`, `backoffMs`); strict runs bypass it; disconnect/forget/closeAll clear it; a late success clears it.
- `McpBuiltToolsMemo` reuses MCP AgentTool objects while client, inventory object, server id/name/description, and lease are unchanged. The resource tool is still built per turn (it caches its own listing). The harness's `snapshotAgentTool` still clones parameters per harness, so pi-ai's validator WeakMap still misses across turns.
- `withConfiguredMcp` admission is per server (`createMcpAdmissionQueue().shared`), mutations stay exclusive and wait for in-flight admissions. `McpPendingJournalState` skips the journal read once this process knows it is empty.
- `mcpOAuthStore.get` serves decrypted sessions from memory (invalidated around every mutation, stale in-flight reads discarded) and throws `McpOAuthCredentialStorageError` for unreadable storage instead of `{}`; `hasOAuthTokens` maps it to false, re-authorize starts fresh. `bot-capability-credential-signatures.ts` (Bot lane) now sees the throw.
- Bot catalog and provider-auth connects are bounded by `connectMcpWithinDeadline` (10 s, client closed on timeout/abort).
- Prewarm (`prewarmMcpServers`): app ready, mcp:save, mcp:authorize, mcp:setPresetKey (when set), mcp:reconnect.

## Slice 7a: names, search, mcp_servers section (2026-10-13)

- `mcp-tool-identity.ts`: names are `<prefix>__<tool>`, `[A-Za-z0-9_]` only, <=64. Prefix = lowercased sanitized server name (runs of `_` collapsed, no leading digit, <=24 chars); servers whose prefixes collide (case-insensitive) each get `_<6-hex sha(id)>`. Tool hash `_<8-hex sha(id\0tool)>` only for >64 chars or a same-server sanitize collision (whole group). Inputs: every configured server (enabled or not; `configuredMcpToolNamingServers` in mcp.ts) + that server's full inventory. Subagent children see only scopes (server id, no name/inventory): `mcpScopedAgentToolName` hashes any lossy-sanitized tool, prefix from server id; so child names differ from the parent's.
- Built MCP tools carry `markMcpAgentTool` identity (symbol, survives spread); claim-check (`isConnectorTool` option) and the Assistant prompt (`mcpToolNames`) use it instead of `name.includes("__")`. The subagent projector still uses `includes("__")` (child-only names).
- Bot naming passes the catalog connection's tool list as inventory (`exactBotMcpToolNames` callback gets it). Catalog drops unclassifiable tools, so a same-server sanitize collision with a dropped tool would fail closed (tool not offered).
- Discovery metadata gains `alias` (the tool prefix). `searchTools`/`describeNamespace`/`tool_search` accept key, display name or alias (case-insensitive, separators equivalent; ambiguous fails). Ranking is BM25F (name 3, label/alias 2, description 1), OR semantics, stop words, light stemming, 0.5 partial token match. >512 callable tools: first 512 searched, `inventoryTruncated: true`, one `mcp-degraded` diagnostic.
- `withMcpServerInstructions`/collector removed. `renderMcpServersSection` (<=4 KiB, <=250 chars/line, handle + label + reach + first line of description, else "service says" first line of instructions; JSON-quoted, angle brackets neutralised) is appended by `createMcpServersSectionRefresher` as a `sections["mcp-servers"]` system patch (same mechanism as AGENTS.md) at turn start and in `prepareNextTurnWithContext`, from `candidate.getCallableTools()` (so late servers patch in). Bots render it from offered connection tools in `assembly.guidance`. With codemode declared, full instructions only via `describeNamespace`. Without codemode (Bots, direct-tool or tool_search-only turns) the section also carries each server's full instructions as `{"server":handle,"guidance":...}` JSON records under an untrusted header (<=8 KiB/server, <=32 KiB total, whole records omitted, `<`/`>` neutralised), still as the section patch.
- Activity: `GenerationTimelineProjector.setToolLabels` + `mcpToolActivityLabel` (identity marker) give MCP steps the tool's `server/tool` label (clamped to 120 UTF-16 units, the native limit); `toolName` and wire shape unchanged. Wired in llm-client and the CLI daemon (CLI MCP labels stay `Server: tool`).

## Slice 11: credential hygiene for custom servers (2026-10-13)

- Env/header values never stay in config.json: each name maps to an opaque marker `aiden-secret:v1:<32 hex random>` (`renderer/shared/mcp-field-secrets.ts`); values live in one encrypted secrets entry per server, `mcp-fields:<serverId>` (JSON marker→value, `mcp-field-secrets.ts`). A new marker is minted whenever a value is typed, so the existing `envHash`/`headersHash` credential snapshot (Bot grants, schedule bindings, leases, cleanup journal) changes exactly when a value changes. No snapshot code changed.
- Save path: `saveConfiguredMcpServer` (`mcp-server-save.ts`, used by `mcp:save`) plans markers, stores new values before publishing config, rejects a kept marker the store doesn't have ("enter it again"), and computes cleanup against `mcpFieldSecretCleanupBaseline` so a pure move into the keychain is not a credential change (OAuth/preset key survive). The cleanup journal's reconcile prunes unreferenced values (`pruneStoredMcpFieldSecrets`; remove deletes the entry).
- "Move on next load": `sealPlaintextMcpServerFields()` runs at startup before prewarm and after external config.json edits (watcher callback), re-reading each server inside the mutation. Until sealed, plaintext values still work. Sealing changes the authority snapshot once (Bot grants/schedule bindings re-approve once; pre-1.0).
- Resolution: `resolveAuth` (mcp.ts) fills markers from the store (missing → `McpFieldSecretMissingError` naming the field); `mcp:authorize` resolves before sign-in; `mcp:testDraft` lends stored values only when the draft keeps the saved destination (`savedDestination`: same transport + URL, or command + args).
- Settings: `McpSecretFields` (name inputs, saved values as dots + Replace, password inputs for new values); renderer sends markers back unchanged. `mcp:save` returns the stored record; authorize/provider consent use it.
- Stdio approval: `mcp-stdio-approvals.ts` (userData `mcp-stdio-approvals.json`, 0600, serverId → `mcpStdioLaunchFingerprint` = sha256 of id, command, args, env name + value-hash). `resolveAuth` throws `McpStdioApprovalRequiredError` before any spawn (all lanes: foreground, prewarm, Bots, status); diagnostics `failurePhase: "mcp-stdio-approval"`. Approved by `mcp:save(server, { approveLaunch: true })` (editor only) or `mcp:approveLaunch(id, fingerprint)` (refused if the launch changed since `mcp:launchApprovals` showed it). Toggle/model-access saves keep an approval only when the launch is unchanged. Remove forgets it. Existing stdio servers need one approval after this change.
- Hidden servers + schedules: `selectedMcpServers` (strict runs) throws "off for the model"; Remote/desktop picker list (`scheduled-task-application-service.mcpServers`) filters them; editor shows a selected hidden server unavailable with the reason; `schedule_task` rejects them; CLI scheduled inference treats them as unavailable. Remote payload shape unchanged.
- Slice 11 PR #470 Pullfrog fixes (2026-10-13): secret record v2 `{v:2, bindings: {destination: {marker: {field: "env:NAME"|"headers:NAME", value}}}}`. Editor address/command changes add a new destination group and keep the old one until cleanup, which keeps only the group matching the authoritative config (failed/cancelled publish and restart recovery keep the old address working; a never-published group is dropped, so a later outside edit to it inherits nothing). Values resolve only under the field they were saved for (`mcpFieldSecretValuesFor`); a marker moved to another name is missing, shown as unavailable in launch approval (`mcpEnvForApproval`), and can be renamed only from the editor. Pure plaintext→marker moves register an exact before/after pair in `mcpCredentialEquivalences` (cleanup-core); `externalMcpCredentialCleanupKind` (used by `reconcileExternalMcpCredentialChanges`) treats it as no credential change, and the save rebinds an API-key preset's key to the sealed snapshot. Bot/schedule authority still changes once on sealing.
- Slice 11 PR #470 second Pullfrog round (2026-10-13): structural fix. (1) `stageMcpFieldSecrets` only ADDS before publication (new markers, new destination groups; an editor field rename mints a new marker copying the value; existing entries are never rebound or removed). (2) Pruning runs only after publication against the published record, and in journal recovery against the disk-reloaded config. (3) Every marker occurrence is checked against its stored field (`mcpFieldSecretFieldValues`, keyed by field), so an alias of a valid marker under another name never resolves and approval shows it unavailable; aliases and outside reassignments are refused by any save. Changing a header/env value no longer clears OAuth/preset keys (nothing is bound to them); Bot grants, schedule bindings and leases still use the full snapshot. Preset keys saved for a preset that had hand-added headers must be re-entered once.
