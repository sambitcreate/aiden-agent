# Prompt cache stability (feat/prompt-cache-stability)

Plan: `docs/plans/prompt-cache-hit-rate.md` (one PR, phases 0-8).

## Phase 0 (2026-11-18)

- `main/services/pi-cache-telemetry.ts` ports Pi 1.5.2's unexported `detectCacheMiss` rules and attributes each miss to the first changed section of the normalized transcript: `model`, `retention`, `tools`, `system:<label>` (`base` = head prompt), `messages`, `ttl` or `unknown`. Only hashes and labels are kept.
- Desktop: `llm-client.ts` wraps the stream function with `withPromptCacheTelemetry` (before cache warming). It logs at debug level and adds `lastCacheMiss` to the context pressure feed. Compaction resets the chat's state and clears the last miss; a later cache read clears it too (`onMissCleared`). The panel shows "N% from cache" (0% only when the chat has cache activity, a documented cache or a miss) and "Cache missed: ...". `ttl` uses `promptCacheTtlMs(model)`, falling back to 5 minutes. Hashes are salted per process and memoised per message object.
- `aiden serve`: `daemon-chats.ts` uses the same code, writing to stderr only with `AIDEN_PROMPT_CACHE_DEBUG=1`. Before each request it feeds Pi's `cache_warm` session entries (`promptCacheWarmsSinceLastResponse`) to `observeWarm`, which ignores warms no later than the latest request. `lastCacheMiss` is not in the Remote pressure contract.
- `main/services/chat-prompt-assembly.ts` (`buildWorkspaceChatBasePrompt`, `assembleChatPrompt`) builds llm-client's system prompt and tools; `composeBotSystemSections` (`bot-system-prompt.ts`) builds the Bot runtime's fixed sections. The harness uses both, so its cases run the production builders.
- `main/services/prompt-prefix-harness.ts` runs each turn through `PiAgentRuntimeHarness.runManaged` over a real durable session, with the AGENTS and MCP refreshers, generation-context transform and Anthropic or OpenAI Responses adapters, offline. `RecordedPromptRequest.carries(text)` checks a value reaches the payload. `prompt-prefix-stability.test.ts` holds the baseline as `todo` cases; each later phase turns on its cases.
- Gotcha: the managed run's shared prepare step folds the head and turn-start system patches into one system message before every run, compaction on or off, so an unchanged MCP section is stable on every wire. Only mid-turn section changes can miss.
- Gotcha (Bots, Pi Durable): a changed section (open work, `aiden-memory`) goes out as a trailing system patch; the Anthropic adapter hoists it into the system block, so the wire misses while the transcript fingerprint only grows. Telemetry would attribute nothing; Bots have no telemetry wired yet.
- Bot `aiden-memory` is rendered per request: the Bot's own `bot_memory` save keeps it stable within a session; a person's `memory.edit` changes it (phase 3 todo).
- `chat-prompt-assembly.ts` takes `bot: { definition, workspace, fileAuthority }` and applies `withBotRuntimeInstructions`; Bot chats never use on-demand tools.
- `createPromptRequestRecorder` renders any provider context (workspace harness and Bot cases). The in-place test re-fingerprints deep copies to guard the WeakMap hash memo.
- Gotcha: the Anthropic adapter writes the newest user message as a text block with `cache_control` and older ones as strings; the harness normalizes both before hashing.
- Not modelled: browser discovery (llm-client generation setup), per-request hook context.

## Phase 1 (2026-11-18)

- AGENTS.md nonce = `agentsInstructionNonce(chatSecret)`: HMAC-SHA256(chatSecret, "agents-instructions"), 128 bits in UUID form. `chatSecret` is required on `createAgentsInstructionRefresher`; llm-client and the harness both build it through `createChatAgentsInstructions({ userDataDir, chatId, ... })` in `chat-prompt-sections.ts` (Electron-free factory), which uses `chatPromptSecret(promptSectionDeviceKey(userDataDir), chatId)` from `prompt-section-secret.ts`. Device key file `prompt-section-key`: temp file (`wx`, 0600) hard-linked into place (EEXIST -> read theirs; damaged/symlink -> rename over, re-read; no-hardlink volumes -> rename if absent); loose mode tightened to 0600 or untrusted. Unwritable folder -> process-local key, one console.warn; then the nonce changes every restart and an ACP chat with AGENTS.md replaces its native session once per launch. Not stored in chat metadata on purpose (records reach renderer, phones, exports, forks).
- Records JSON escapes `</` as `<\/`, so a file cannot close the block even knowing the chat's nonce (the model sees `<\/` where the file says `</`).
- No section journaling: a deterministic section patched at turn start is folded into the head, so it is stable on all wires. Phase 8 dependency (in the plan): journal or otherwise stabilize both sections before removing the head collapse.
- ACP: `STABLE_AGENTS_NONCE` removed; `hostInstructionsFingerprint` hashes the delivered text. Existing ACP chats with AGENTS.md get one native-session replacement after upgrade.
- MCP: `<mcp_servers>` used to re-render between steps from `candidate.getCallableTools()` (late discovery included), a mid-turn change. Now `createChatMcpServersSection({ inventory, declared, latePending })` (chat-prompt-sections.ts) renders once per generation from the turn-start inventory; late servers stay out for the whole generation (steering turns included), callable via codemode/tool_search, listed from the next generation. If `latePending() > 0` at turn start and codemode/tool_search is declared, the section ends with the fixed line "More services may still be connecting; once connected, find them with <codemode or tool_search>." (`connecting` option on `renderMcpServersSection`, bytes reserved in the budget; rendered even with zero servers). Harness option `lateMcp: { tools, pending }` drives the same factory; `harness.callableTools()` / `executeNestedToolCall` let a test build a real `createPiCodemodeTool`.
- Stability suite: AGENTS.md case on (3 wires), restart case (same userData dir -> same bytes), edited-AGENTS oracle, MCP late-admission (late server called mid-turn via real codemode; connecting note) and MCP removal (linear+notion -> linear -> none) cases; 7 todos remain (phases 2, 3, 7). Mutations checked: random secret per generation, re-render per step, no connecting note each fail the suite.
- Phase 1 does not touch the Bot hoisting finding (Bots don't use the AGENTS refresher); that is phase 3.
