# Bot chat activity (2026-10-14)

## Timeout race follow-up (2026-10-15)
- In `AidenBotRequestRace`, publish `AidenBotRequestTimedOut` before cancelling the request. Cancelling first could let a sleeping request throw `CancellationError` and win the race, so Chat Activity cleared a choice made during a timed-out save instead of reconciling it after refresh. Hosted PR #498 run 38816353400 exposed this in `AidenBotChatActivityTests/testAPickMadeWhileASaveTimedOutGoesOutOnceTheRefreshShowsThatSaveLanded()`; the focused 23-test simulator suite passed after the ordering fix. No timeout or retry policy changed.

## Slice B (desktop) — what shipped
- Phase vocabulary and tool classifier: `renderer/shared/bot-activity.ts` (shared with main, the CLI, and slice D's phones). Unknown ids → `working`. Always "Thinking" keeps waiting/stopping/reconnecting.
- Main derives `BotLiveSnapshot.activity` + `activity` event in `live-projection.ts` (`liveBotActivity`), gated on session state `running` (a paused Bot still has `pi.live.run`). Stop reaches it through `notifyStopping` in the `bots:stop` handler; Resume reaches it through the service's `onResumed` callback (`bot-session-main.ts`) → `notifyResuming`, so a Resume from any surface marks it; approvals refresh it via `botApprovals.onChange`.
- Run identity is the run's first input (`inputs[0]`), not the generation task id. Resume is marked by the service's `onResumed` callback inside the per-Bot serialize; Stop/Resume flags are run-scoped (a double Stop never leaks "Stopping" into the next turn). `startedAt` renews for a queued follow-up turn.
- Transcript tool calls carry `kind/label/detail/app` (`bot-activity-detail.ts`). Command steps never show the command: only the model's `description`, redacted with `sanitizeDiagnosticText` before cutting to 80. Tool results carry `status: ok|failed|blocked|stopped` (Pi's `blocked` diagnostic; `stopped` for Stop/restart, rendered neutrally) and `durationMs`.
- `BotDefinition.chatActivity?` `{ level: quiet|summary|detailed, wording: follows|thinking }`; absent = Quiet/Follows; an update without it keeps the stored value. It is stored last in the Bot record (the revision hashes the record JSON); identity updates merge a partial `chatActivity` onto the freshly read Bot. Remote identity PATCH still rejects it (slice D).
- Renderer: `BotStatusLine` (hides only while reply text streams with no active tool step; the visible line is a `role="group"` named by its words; announcements go to `BotStatusAnnouncer`, one always-mounted, initially empty `role="status"` region in the pane that clears while words stream, 2 s throttle), `BotActivityRecap` (Bot-specific, not ActivityFeed), progress narration as bubbles (`BotUpdates` and `bot-reply-projection.ts` deleted), "You stopped this reply." derived from an `aborted` reply or a `stopped` tool result (a Stop during a tool run writes only the round's results; a later `interrupted` notice turns it back into a restart). The still-going note hides while the line reads Waiting or Stopping. Every user entry begins a turn (pi-durable places steers after a round's tool results).
- Queue/Steer: `pi.inbox` projected as `snapshot.queued` — the person's own inputs only, classified by durable submission requestId (`routine:`/`intro:`) plus the hidden flag, failing closed. Follow-ups show faded with Remove (`bots:withdraw` → `Harness.abortSubmission`: withdrawn | started | gone); steers are normal bubbles.
- Advanced → Chat activity (`?page=chat-activity`, `bot-chat-activity-page.tsx`): saves on pick through a serial queue, per-level Reduce Motion still frames, Reduce Motion read live.
- `BotAvatar` faces glance via `data-working` with a shared off-screen observer; list's green dot removed. Under Reduce Motion (setting or OS) a working face holds the glance's look-aside pose (`translateX(-2.6px)` on the eyes, no animation), so it still differs from idle.
- Onboarding: the Bots gallery tile (`BotsArt`: name pill, one exchange, routine chip) shows neither the list nor the Updates line. C2 changed only its header (panel toggle instead of a back chevron).

### Wire
- Token `bot-activity-v1` (announced only while activity frames, `whenBusy` and `chatActivity` are wired together) and the negotiable, authority-free `bot:activity` opt-in (any device type, 404 when unwired, never issued by pairing). Older phones' decoders refuse unknown keys and event types, so the token alone can't gate the host; holders get the new shapes, everyone else gets a no-op `state` frame at the same seqs.
- Session `snapshot` keys `activity` (`{phase, app?, startedAt}` or null) and `queued` (`[{submissionId, mode: steer|queue, text}]`, at most 20, text at most 32,000 code points), frames `activity` and `queued`, and `submissionId` on the person's own user entries (R16). `app` at most 40 code points (only for the `app` phase); `startedAt` an integer 0..2^53-1; nothing else from the step crosses.
- Bot detail `chatActivity`; `PATCH /bots/{id}` accepts it (exact keys); `POST /bots/{id}/messages` accepts `whenBusy: steer|queue` (runtime `steer|followUp`). Detail routes strip `chatActivity` for non-holders at one choke point (`writeBotDetail`); the fixture parser requires revision >= 30 for `botActivity`.
- Photo-only queued messages are omitted from `queued` (R11). The list is built by inclusion from ids the desktop's fail-closed classifier marked personal (R1): routine and intro inputs never reach a phone.

### Host
- The Remote projector (`main/services/aiden-remote-bot-session.ts`, `BotLiveProjector`) reuses B's `liveBotActivity`/`liveQueuedMessages` derivations and `liveRunKey` (R4: a changed run key resets `startedAt`, Stop and Resume). It stays silent, deriving nothing, unless `turnIntents` and `bots.supportsChatActivity` are both present, so revision-29 behaviour is byte-for-byte unchanged. `supportsActivity` is fixed at construction.
- Run start (final wave FR-I1): `createBotRunStarts` in `live-projection.ts`; the singleton `botRunStarts` (in `bot-turn-intents-main.ts`) is passed to both the desktop projection (`bot-session-main.ts`) and `AidenRemoteBotSessionService` (`runStarts`, in `aiden-remote-service-main.ts`). One record per Bot keyed by `liveRunKey`, recorded by the first surface to see the run and asked on every running frame (so a null key adopts the run's key as soon as it shows); any surface seeing the Bot not running ends it. Without it a projector created mid-run or after the 60 s idle close reset the phone's clock. Nothing durable records a run start, so a run already going at app start is timed from first sight.
- Queued classification: `createQueuedInputClassifier` (`live-projection.ts`) is the one classify-once, fail-closed, throttled-retry implementation; the desktop feed and each projector own one and pass their own lane as `retry`. `liveQueuedMessages(docs, personal)` is an inclusion filter (required set of the person's ids). `resumedFrom` is stored serialized (`JSON.stringify`) once when the Resume is heard.
- Remote ledger (R22b): `AidenOperationNotExecutedError` (`aiden-remote-operation-contract.ts`) makes the idempotency ledger forget an admission and rethrow its cause. Remote send/Resume/Dismiss/Stop wrap only the runtime call (`unlessRefusedBeforeRunning`) for `BotSessionError` `needs_model`, `model_error`, `unavailable`, `bot_paused`, which are all thrown before any write. Other routes using `executeIdempotent` are unchanged (a rejection keeps its record: a contract error replays under its own code, a non-contract error as `internal_error`, and an unknown outcome stays in flight).
- `botTurnIntents` (`main/services/bot-runtime/bot-turn-intents.ts`, singleton in `bot-turn-intents-main.ts`) is the one Stop/Resume source for the desktop projection and Remote: intents `stopping`, `stopCancelled` (R3, a failed Stop) and `resuming`. `stopWithIntents` is shared by `bots:stop` and Remote Stop; `wireBotLiveTurnIntents` (tested like `wireBotAttention`) feeds the desktop projection. Resume is announced only from the runtime's `onResumed` (R2), never before `runtime.resume`. Listener errors are logged and never block the others.
- B Resume fix (`resumedFrom`): `BotLiveActivityInput.resumedFrom` is the `pi.live` doc when the Resume began; partial text that predates it no longer counts as writing, so "Picking up where it left off" holds until the first live event after the Resume. Shared by the desktop and Remote.
- `submissionId` tagging (R16): the host resolves placed submissions into a memo keyed by entry id, sticky while the entry is in the projected view and pruned when it leaves (eviction must never emit an `entry` frame, or phones, including rev-29 ones, would grow a ghost bubble). Only the person's own inputs are tagged; stripped for non-holders. A failing lookup is reported once per streak; `submissionTagsHeld(botId)` is the test seam for the memo bound.

### Phones (iOS and Android behave the same; R14 "everything optimistic, nothing waits to connect")
- Phase tables: TS `renderer/shared/bot-activity.ts`; iOS `AidenBotActivityPhase.table` in `ios/AidenOnTheGo/Features/Bots/AidenBotSessionModel.swift`; Android `AidenBotActivityPhase` in `features/bots/AidenBotActivity.kt` with words in `strings.xml` (`bot_activity_*`). The shared fixture `botActivity.phases` in `protocol/aiden-remote/v1/fixtures/contract.json` pins them: every id, word and mark, plus unknown id -> `working`.
- Fixed app labels (`TOOL_APPS`, 2026-10-21, P10): the Bot's own `computer` and its browser (`browser` gateway and every `browser_*` tool) use the existing `app` phase with "its computer" / "its browser", so phones show "Using its computer" / "Using its browser" with no new phase id. `computer_use` stays the `computer` phase ("Using your Mac").
- Status line: shows from the send ("Getting ready"), hides only while reply text streams with no active tool step (R7), Reconnecting while the stream is down in a running turn, elapsed after 20 s, announcements throttled. No 2-minute note, no steps, recap or peek on phones. Steer/Queue pill (default Queue, Stop where it was), Queued bubbles faded, glancing faces on Bots home, photo avatars wear a glance badge; R19: under Reduce Motion/Low Power canonical faces keep a still badge (both phones).
- Optimistic outbox (R14, R17, R18): sends and Retry go through a per-Bot outbox that survives leaving the chat, a Bot switch and relaunch; a request is frozen at first attempt; reconcile is by `submissionId` (text only as fallback), one entry settles one message, an unsettled message is hidden not removed, head-of-line blocking, ambiguous failures retry 1 s then 4 s while connected. Stop/Resume/Dismiss/answers/approvals/proposals apply at once and roll back per field. Skeletons and a quiet "Connecting…" hint instead of connect-blocking screens.
- **On-disk unsent text.** Unsent message text lives on disk for up to 24 h. iOS: Application Support `BotOutbox-v1`, file protection `completeUntilFirstUserAuthentication`, excluded from backup, at most 20 messages, 10 MB. Android: `noBackupFilesDir/BotOutbox-v1`, `AtomicFile`, never backed up, 20 messages, 4 MB. Keyed by installation identity (a re-pair never restores old messages); purged on unpair, revoked credentials and access loss (401/403); expired or exhausted messages show "Couldn't send · Try again", never silently dropped; a bad record is dropped alone.
- **12 s request bounds.** Every Bot request on the phones is bounded to 12 s (iOS `aidenBotWithin(requestLimit)`; Android `withTimeoutOrNull`), because the URL session otherwise waits minutes on a dead link. A Chat activity pick made while connecting is held up to 8 s.
- **Chat activity page** (Advanced → Chat activity, shown only when `supportsBotActivity`): native `Form` on iOS (`AidenBotAdvancedView.swift`, no new Swift files and no pbxproj edits), Material 3 Expressive on Android (`AidenBotChatActivityScreen.kt`, `AidenBotChatActivityModel.kt`, `AidenBotChatActivityPreviewCard.kt`). Looping previews, level-specific Reduce Motion still frames, paused when inactive or off-screen. Picks save instantly, coalesce, roll back on failure; a `revision_conflict` or timeout refreshes the Bot and adopts the Mac's choice; the row opens offline from the cached Bot. Android picks run on the coordinator's scope (`launchDetached`) so they outlive the dialog, and are reported to the screens behind once.
- **iOS rule:** no new Swift files (and no pbxproj edits) in D; everything lives in the existing Bot files (`AidenBotSessionModel.swift`, `AidenBotSessionChatView.swift`, `AidenBotAdvancedView.swift`, `AidenBotSemanticAvatarView.swift`, `AidenBotGeneratedAvatarLifecycle.swift`, `AidenBotsHomeView.swift`, `Models/AidenBot*.swift`).
- **Android strings.** All copy is in `strings.xml` (`bot_activity_*`, `bot_chat_activity_*`, `bot_session_*` status/queued strings). `aidenBotElapsedLabel` and `aidenBotDurationLabel` (`AidenBotActivity.kt`) are deliberately English (JVM-tested helpers); see `.memory/android-localization.md`.
