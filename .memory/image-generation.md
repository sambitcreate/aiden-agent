# Image Generation registry (Task 1 core, 2026-10-12)

Plan: `docs/plans/image-generation-settings-plan.md`.

- Main code: `main/services/image-generation/`. `runtime-main.ts` exports the app singleton `imageGeneration` (an `ImageGenerationRuntime`); `runtime.ts` is the injectable core.
- Consumers use `imageGeneration.models` (`Pick<Models, "getAvailableOfType" | "getModelOfType" | "getModelsOfType" | "generateImages">`). Disabled models are never registered with the Pi registry, so every lookup hides them. `generateImages` dispatches the registered model, never the caller's object. `getModelOfType` is sync: call `await imageGeneration.ready()` (or any async method) first.
- Keys: the credential view (`credential-view.ts`) maps provider `p` to `aiden-internal:image-gen:<p>` and has slots only for `openrouter`, `replicate`, `fal`. The only ambient fallbacks are `AIDEN_IMAGE_OPENROUTER_API_KEY`, `AIDEN_IMAGE_REPLICATE_API_TOKEN` and `AIDEN_IMAGE_FAL_KEY`. Keys are validated locally (trim, 8–512 printable ASCII, no spaces) with no network call.
- Catalog: curated Replicate and fal data plus `inferImageModelMaker` live in `renderer/shared/image-generation/catalog.ts`. OpenRouter's curated list is Pi's bundled `openrouter` image models minus `openrouter/auto*`. Precedence is curated, then custom, then fetched. Fetched models start disabled; curated and custom start enabled. Choosing a default turns that model on.
- Settings file: `image-generation-settings.json` (0600, validated on read, invalid file falls back to defaults with one logged warning). It never holds keys.
- Adapters: `replicate-images.ts` (`Prefer: wait=60`, polling, cancel, uploads refs over 256 KB via `/v1/files`, downloads only from `replicate.delivery`) and `fal-images.ts` (queue submit, status, response; cancel via PUT; follows only `https://queue.fal.run` URLs; downloads only from `fal.media`). Both never reject and scrub the key from echoed provider details. Overall 5-minute limit (message reflects the actual `limitMs`). Replicate uses `POST /v1/models/{o}/{n}/predictions` for official models and `POST /v1/predictions {version}` when the adapter has a `version` (fetched entries keep `latest_version.id`; a 404 by name triggers one model lookup and a version retry). Polls retry 429/5xx/network/unreadable bodies with backoff (`withPollRetries`, 6 failures, 15 s cap). After submission, any non-success exit (error, timeout, abort) cancels the job best-effort. fal references are inline data URIs capped at 8 MiB total (`FAL_INLINE_REFERENCE_BYTES`).
- Runtime: key presence is cached per provider (env read once) and invalidated by setKey/removeKey/clearAll; `snapshot()` → `{available, defaultModel?: {provider,id,name}}` is the per-turn read (name = curated name or the id, prompt-safe). Mutations re-register only the affected provider. `ready()` retries after a failed load. Fetch latest has a 30 s deadline (`IMAGE_CATALOG_FETCH_TIMEOUT_MS`). `aiden-internal:` credential writes skip the Bot inventory fence (`piCredentialChangeFencesBotAuthority`).
- Not verified against live APIs: fal `X-Fal-Store-IO` header and `cursor` query parameter, Replicate collection `latest_version.openapi_schema` presence, and the reference fields of some curated models (only listed where known). `recraft-ai/recraft-v4.1-svg` was left out because it returns SVG, which the output validator rejects.
- IPC: `imageGeneration:*` (state, setKey, removeKey, setModelEnabled, setDefaultModel, addCustomModel, removeCustomModel, fetchModels); parsers in `main/handlers/image-generation-parse.ts`; client `imageGenerationApi` in `renderer/lib/ipc.ts`; shared types in `renderer/shared/image-generation/types.ts`.
- Onboarding reset calls `imageGeneration.clearAll()` (keys plus settings).
- Tests: `npm run test:image-generation`.

## Consumers (Task 2, 2026-10-12)

- Chat: `createPiModelTools` takes `imageModels` (always `imageGeneration.models`) and `classifierModels` (the local-classifier facet over `providerRegistry.models`). The classifier facet no longer forwards `generateImages`. `providerLabel(id, type)` and the `onUsage` record's `operation` say which registry served the call; image usage is accounted with no chat-provider deployment lookup (always hosted).
- `generate_image` refuses a registered model whose provider has no image key (checked against `getAvailableOfType("image", provider)`), and unknown models; both errors end with "Add an image key in Settings → Image Generation." `list_operation_models` adds `imageSetup` when no image model is available. `piModelOperationsSystemPrompt({ defaultImageModel, classifiers })` names only `imageGeneration.snapshot().defaultModel` (cached, prompt-safe name); snapshot failures are logged, never fail the chat.
- Conversation mode (review fixes): `shouldEnableImageGeneration` = chat usage source, not Telegram, not Assistant, not a Bot, and not a workspace chat with permission `none`. `planModelOperationsForChat(scope, { imageGenerationAvailable, stagingAvailable })` in `display-image-extension.ts` decides the wiring: workspace chats get image tools + `classify` + `display_image` (staging unavailable throws the repair message); folderless chats get only the image tools (`createPiModelTools` without `classifierModels`: no `classify`, `list_operation_models` image-only) when `snapshot.available`, a one-line `IMAGE_GENERATION_UNAVAILABLE_PROMPT` extension when not, and nothing (a logged warning) when staging is unavailable. The pending-image recovery error stays per chat. `createDisplayImageExtensionRuntime` takes an optional `workspaceRoot`; without one `extension` is `undefined`.
- Create Images: `createWiredImagePort({ models: imageGeneration.models, ready: () => imageGeneration.ready(), ... })`; the port's `prepare` hook runs before listing and before every request (sync lookups). `listModels` marks `isDefault` from `imageGeneration.snapshot().defaultModel` and sets `maker` from `imageGeneration.imageModelMaker`; `pickDefaultImageModel` prefers `isDefault`, then Nano Banana 2, then the first model, and the picker passes `maker` to `ImageModelLogo`. Run-coordinator's missing-model message points to Settings → Image Generation.
- E2E: `fakeOpenRouter` sets `AIDEN_IMAGE_OPENROUTER_API_KEY` (allowed credential key) instead of `OPENROUTER_API_KEY`.
- CLI: does not wire `pi-model-tools`; only `packages/cli/src/extensions/display-image.ts` consumes the display-image runtime (always with a workspace root).

## Renderer (Task 3, 2026-10-12)

- Settings section `imageGeneration` ("Image Generation", Agent group, `Image` lucide icon) in `renderer/shared/settings-section.ts` and `renderer/main/settings-view.tsx`; deep link `/settings?section=imageGeneration`. Not capability-gated.
- Page: `renderer/components/settings/image-generation-settings.tsx`. Per-action pending keys (`fetch:<p>`, `key:<p>`, `model:<ref>`, `remove:<ref>`, `default`, `add`): only the same action is deduplicated, so a fetch never locks key controls or other providers; `ModelRow` is memoized; search uses the shared `Input type="search"` pattern; "Last fetched" uses `renderer/lib/relative-time.ts` (`formatRelativeTime`, shared with scheduled tasks); every result's `state` replaces local state; a thrown IPC error reloads state, and overlapping actions settle with one fresh `state()` read once all are idle. Groups: privacy Callout, Providers (status badge, Add/Replace key inline password form, Remove with AlertDialog, Fetch latest models with per-provider inline notice, "Last fetched" line), Default model (Select, Automatic = null, unavailable default shown disabled), Models (search, provider filter buttons, Field rows with Switch; fetched models that are off stay hidden until searched or "Show all"; 200-row pages), Add model by ID (provider-specific extras: OpenRouter reference switch, Replicate reference field, fal edit endpoint + field).
- Logos: `renderer/components/image-model-logo.tsx` (`ImageModelLogo`, `ImageProviderLogo`); shared mask/initial pieces in `renderer/components/themed-mark.tsx`, also used by `ProviderIcon` (markup unchanged).
- Create Images picker shows maker marks; empty state "Add an image key in Settings → Image Generation." with an "Open Image Generation" button wired in `GenerateImageNode` via `useNavigate`.
- Onboarding provider step has a one-line note; no gallery tile.
- Tests: `renderer/components/image-model-logo.test.tsx`, `renderer/components/settings/image-generation-settings.test.tsx` (happy-dom + `installBotTestIpc`), both in `npm run test:image-generation` and the renderer-other CI lane.
