# `aiden serve` Remote on by default (2026-10-30)

- `aiden serve` starts Remote unless `--no-remote`; `--remote` is still accepted as a no-op. `serve --daemon` spawns the child with `--no-remote` when chosen and always with `--no-pair`. Flag parsing and the foreground/daemon flow live in `packages/cli/src/serve-command.ts`.
- A foreground `serve` with stdout on a TTY opens one LAN pairing window after startup (`--pair tailscale` picks Tailscale, `--no-pair` skips it) through the daemon's own `remote pair` control-socket path, renders it with `pairing-display.ts`, polls `remote pair-status`, and prints one line when the 5-minute window expires or a device pairs. Non-TTY output (Docker logs, systemd, `--daemon`) never mints or shows a pairing secret.
- `serve status` adds `remote: { on, connectionMode, lanPort, lanEndpoint, tailscaleEndpoint?, tailscaleConnected, pairedDeviceCount }`, read from a `serve status` control-socket command (`{ on: false }` when off or not running).
- The Remote LAN listener binds the dual-stack wildcard `::`; on kernels without IPv6 (EAFNOSUPPORT, including the cloud test container) `aiden-remote-service.ts` now falls back to `0.0.0.0`. Before this, every CLI Remote test failed in such containers.
- Linux Bonjour (avahi-publish-service) is best effort in the CLI: missing or exiting avahi logs a warning and no longer stops or fails Remote. The warning says LAN pairing still needs `<host>.local` to resolve on the phone's network, because the pairing payload seals that endpoint and both native clients require the exact endpoint. A missing utility (another responder may still answer) is worded differently from an exiting publisher (avahi-daemon probably not running).
- `remote pair tailscale` and `serve --pair tailscale` both go through `beginTailscalePairing` (remote.ts). It checks the node (installed, signed in, HTTPS), switches `lan` to `both`, runs the ownership-safe `connectTailscale`, then opens the window. It never takes over a route. If the connect fails, it puts the `lan` mode back. Each failure code maps to a message that names the exact setup command (`tailscaleSetupMessage`). `remote tailscale-reconcile` exposes the service's `reconcileTailscale`.
- Tests: `packages/cli/tests/serve-startup.test.mjs` (the TTY case uses util-linux `script` and skips elsewhere).

# `aiden service install` (2026-10-31, follow-up PR stacked on #675)

- `packages/cli/src/service.ts`: Linux writes `~/.config/systemd/user/aiden.service` (ExecStart `<node> <realpath dist/app/cli.js> serve --no-pair`, `AIDEN_CODING_AGENT_DIR` and `PATH` from the install), runs `systemctl --user daemon-reload/enable/restart`, then `loginctl enable-linger` (warns with the sudo command when refused). macOS writes LaunchAgent `com.sambitcreate.aiden-agent.serve` (logs to `<agentDir>/serve.log`, KeepAlive on failure) and does `launchctl bootout` + `bootstrap gui/<uid>`. A running server is stopped first (`stopDaemon`), then the install waits up to 30 s for the control socket.
- Network choice: `remote network local|tailscale|both` on the running server (`setRemoteNetwork` in remote.ts). Local = mode `lan` (which also disconnects Aiden's own Serve route); tailscale/both go through `connectTailscaleTransport`, the setup half of Tailscale pairing, which restores the previous mode on failure. The install asks 1/2/3 in a terminal, else `--network`, else local; then shows a pairing code (Tailscale when Tailscale is on).
- Tests: `packages/cli/tests/service.test.mjs` uses a fake host (`ServiceHost.run`) for systemctl/loginctl/launchctl; nothing touches the real service manager.

# Tailscale ease of use (2026-10-31, PR stacked on the service PR)

- `packages/cli/src/reachability.ts`: `readTailscaleFacts` (controller status + `tailscale debug prefs` for OperatorUser / ExitNodeID / ExitNodeAllowLANAccess), `looksLikeCloudServer` (TCP connect to 169.254.169.254:80, 300 ms), `recommendNetwork` / `networkQuestion` for the install prompt, `tailscaleChecklist` + `serverChecklist` for `aiden remote check` (handled in commands.ts before the daemon call; exit 1 on a failed step the server uses), `probeAidenHealth` / `waitForTailscaleAddress` / `checkTailscaleAddress`, wrapped by `prepareTailscalePairing`: daemon `remote tailscale-prepare` (connects the route) then the address wait, BEFORE `remote pair tailscale`, because pairing reads the endpoint's TLS pin with a 5 s timeout and the first request to a new Serve name fetches the certificate. Runs in `showStartupPairing` and in `aiden remote pair tailscale` (progress on stderr without a TTY). The wait honours the abort signal mid-request and mid-pause; an older daemon without `tailscale-prepare` is skipped.
- `service uninstall` calls `releaseTailscaleRoute` (daemon `remote tailscale-disconnect` when connected) before removing the unit.
- `cli-runtime.ts` now exits with `process.exitCode` after a dispatched command.
- Tests: `packages/cli/tests/reachability.test.mjs`. In the cloud container, `remote check` correctly reports a cloud server.
