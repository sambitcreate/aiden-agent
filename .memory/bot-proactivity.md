Status: implemented on `feature/bots-memory-soul` (not committed by Track B). Spec: `docs/superpowers/specs/2026-10-09-bot-memory-soul-proactivity-design.md` §11, §14. Plan: `docs/plans/2026-10-09-bot-memory-soul-proactivity.md` Track B.

## Routine notes (`routine_notes`)
- Store: `main/services/bot-routine-notes.ts`, file `<profile>/bots/<botDirectoryName>/routine-notes.json` (`{ [taskId]: { [key]: {value, updatedAt} } }`), caps 16 keys / 64-char key / 2,000-char value / 8,000 bytes per routine; a write over a cap returns `notes_full` and changes nothing. Per-Bot serial writes, `writeJsonAtomic`.
- Render: `Notes you kept from earlier runs of this routine:\n- key: value`, prepended to that routine's own input by `botRoutineMessage(prompt, notes)`; `""` when empty. `botRoutinePromptOf(text)` strips the notes block and the `[SILENT]` rule (Remote routine bubbles use it; desktop rows can too).
- Offer: the candidate is always installed (the registry holds the attended set); `botIngressAllowsTool` allows it only when every request id of the run is `routine:` (empty list → no). Binding is at call time: `routineTaskIdOfCall` (`bot-tool-candidates.ts`) matches the oldest placed submission of the call's own run (`call.submissions()`) against `submissionByRequest` of the newest routine notices in `call.entries()` — never the closure from the last refresh, so a queued second routine cannot steal the first one's notes, and never through the session service, which would deadlock a pause (see `.memory/bot-pause.md`).
- Routine delete clears its key (`BotRoutineServiceDependencies.routineDeleted`); Bot delete removes the file with the session directory.

Any later answer, `list`, or `propose` reconciles to accepted when a routine with that `sourceProposalId` exists (`routines.findBySourceProposal`), so a dismissed card never hides a created routine. ## Catch-up after pause
- A `bot_paused` skip of an automatic fire is recorded with run id = that fire's request id (`routine:<taskId>:<fireTime>`). `createBotRoutineCatchUp` runs, per enabled routine or spent one-time routine of the Bot, the newest run when it is such a skip < 7 days old, via `scheduleService.catchUp(id, {runId, at})` (trigger `{kind:"catch_up", missedRunId, missedAt}`; same gates as automatic except the exact spent one-time fire; never advances the schedule). Request id = the skip's id, so repeats dedupe in the session; label `"{name} (missed while paused)"`. Several misses coalesce (only the newest run is looked at).
- 2026-10-22: A one-time routine is disabled when its fire is claimed. A paused skip of that exact fire may now catch up despite `enabled: false`, after Resume and within the same seven-day window. The scheduler admits it only when the newest stored run has the matching id and `skipped/bot_paused`; it stays disabled afterward. This closes the one-time wake-up gap without letting a disabled recurring routine run.
- Trigger: `createBotRoutineCatchUpTrigger` fires on leaving `interrupted` (or the first non-paused state seen for a Bot); subscribed in `scheduled-bot-routines-main.ts` via `onBotSessionStateChange` (module-load side effect).

## Results reach the person
- One delivery funnel (`bot-delivery/funnel.ts`, wired in `bot-delivery/funnel-main.ts`): a visible routine result or failure is written once to the per-Bot log `<profile>/bots/<dir>/deliveries.json` (`bot-delivery/log.ts`, newest 200 rows, dedupe by botId+dedupeKey) and then sent to the Mac banner and Telegram. The executor passes `deliver` its input (`class: "routine_result"`, dedupeKey = the routine request id); silent, skipped and blocked runs never reach it. Delivery does not need the Bot runtime. Each channel is stamped on the row as it succeeds (`macSentAt`, `telegramSentAt`), so a retry sends only the channels the row still owes and never repeats a banner that already appeared; `sentAt` means every channel went out, and only such a row is a duplicate. The gate is asked once, when the row is created: a stored row keeps the decision it got (suppressed rows stay suppressed, a deferred row is sent once due), so a retry never counts against the daily cap. Bot delete removes the log (`forgetDeliveries` in the `bot-session-main.ts` delete effects). `ALWAYS_NOW_GATE` never defers; Plan B replaces it with quiet hours and the daily cap, and adds the deferred flush (`deliverAfter` holds a row).
- Phones: `bot-routine-notifications.ts` is a view over the delivery log (`createBotNotificationFeed({ log, botName, now })`), not the run store. It serves rows of class `routine_result` whose `deliverAfter` is due and that are not suppressed, newest first by `createdAt`, ≤100, `since` exclusive on `deliverAfter` (so a held row is still served after it becomes due), notification id = the row's `requestId` (the routine fire), `finishedAt` = the row's `createdAt`, preview = redacted first 160 chars of the body or "I couldn't finish this routine." for a failed row. Since revision 42 a reader that also negotiated `bot:issues` gets `class: "issue"` rows too, as `kind: "issue"` items (id = the row id, `routineName` = the card title, no `routineId`/`status`); every other reader still gets routine results alone. A suppressed row stays in the log for the record and never becomes due. Served at `GET /bots/routine-notifications`.
- Telegram: the funnel's telegram port calls `telegramService.deliverBotRoutineResult` (failure text is the fixed line; the Mac banner keeps the redacted detail). `telegramService.deliverBotRoutineResult` → binding's profile → outbox `enqueueRoutineDelivery` (`kind:"routine"` row, starts `pending`, same `sending`/duplicate-label path). `routineTargetEnabled` re-checks binding enabled + same chat before each send; otherwise the row becomes `failed` unsent. Text: `**{name}**\n\n{reply}` through the Markdown→HTML chunker. For non-routine classes the port receives `requestId = "bot-delivery:<row id>"` and `routineName = title`.

## Durable fire reconciliation (2026-10-22)
- A Bot automatic fire is appended to `ScheduledTask.pendingRoutineFires` in the same `schedules.json` update that advances `nextRunAt` (or disables a one-time routine). It stores the fire time, stable Pi request ID, and original prompt/name, so a later edit does not change a claimed fire.
- Startup replays pending fires in order through the scheduler's bounded catch-up queue, including disabled spent one-time routines. An open scheduler scans pending fires every minute and retries with exponential backoff capped at 15 minutes, without overlapping a task's recovery. Recovery uses read-only `submissionForRequest` before it decides whether an interrupted claimed fire can safely run. `send` dedupes by Pi request ID; recovery awaits an admitted submission, or admits it once if the claim preceded the send. Ambiguous admission/wait/mark-silent errors and cancellation after admission leave the fire pending. A send failure whose read-back proves no admission becomes a terminal visible error. Runs use the request ID; an existing run repairs any missing task summary and is delivered again through Telegram's idempotent outbox handoff without model work, then the pending fire is cleared. A saved run is never overwritten when Bot runtime acquisition or delivery fails. An interrupted turn's skipped fire remains eligible for Resume catch-up. A person-paused Bot skips new fires without catch-up; an already admitted automatic fire stays pending until Resume. Desktop notification banners are best effort after run persistence; the Bot chat and run history are durable. Telegram's outbox has an exclusive pending-to-sending claim to prevent concurrent recovery and enqueue sends; it makes one duplicate-labelled retry, then marks failure to avoid unlimited duplicate sends.
- `BotRoutine` projects `pendingFireCount` and `overdueSince` for desktop rows. The CLI `schedule status` reports next, overdue, and pending work. Desktop still needs its process running; the separate CLI daemon can run its own Bot host while detached.

## Bot wake sources step 1 (2026-10-28, feature/bot-wake-sources)
- `routines` tool: `list` adds `eventRoutines` (each `kind: "event"`, label from `formatBotRoutineTriggerLabel`, never a token) and `pendingSuggestions` (`proposals.pending`, label via `botRoutineProposalWhen`). `pause` tries this Bot's event routines first (`eventRoutinesToolSource` in `bot-tool-candidates.ts`, which also re-arms through `botEventRoutinesChanged`). `propose`/`revise` take exactly one of `schedule` or `trigger` (validated with `parseBotRoutineTrigger`; refused at `BOT_EVENT_ROUTINES_MAX` = 16).
- Proposal entries are a union: schedule + timezone, or trigger (label is the trigger label). `revise(botId, proposalId, input)` appends the new card (new id), settles the old one dismissed with `settledBy: "host"` and `supersededBy`, skips `onSettled`, and calls `onRevised` (moves a linked commitment's proposalId). Codes: `not_found`, `not_pending`, `declined_before` (only when renamed into a declined name), `invalid`. A superseded card answers NotFound.
- Accepting a trigger card creates the event routine with `sourceProposalId` (store `create` is idempotent by it; `findBySourceProposal` feeds reconcile). The service returns `token` once; the respond IPC turns it into `link` via `botRoutineWebhookLink` (`sources-main.ts`) and drops the token. Remote respond returns only status/routineId. The card shows Copy link once, or New link (`eventRoutines.rotateLink`) when no link was shown on this Mac.
- Timezone: `botRoutineTimezoneName` (Intl `longGeneric`, UTC-like ids → "UTC"); `botRoutineProposalWhen` = `label · Zone` for schedules. Remote `routine_proposal.label` uses it (fixture labels end "· UTC"); superseded cards are omitted on phones. No wire change, no revision claimed.
- Wake-source list: `main/services/bot-wake-sources.ts` (`botWakeSourceLines`), used by `botRoutineGuidance` and the tool description; steps 2/3 add one line each at the marked slots.
