# Bot proactivity and Remote revision 27 (Track B, 2026-10-09)

Status: implemented on `feature/bots-memory-soul` (not committed by Track B). Spec: `docs/superpowers/specs/2026-10-09-bot-memory-soul-proactivity-design.md` §11, §14. Plan: `docs/plans/2026-10-09-bot-memory-soul-proactivity.md` Track B.

## Routine notes (`routine_notes`)
- Store: `main/services/bot-routine-notes.ts`, file `<profile>/bots/<botDirectoryName>/routine-notes.json` (`{ [taskId]: { [key]: {value, updatedAt} } }`), caps 16 keys / 64-char key / 2,000-char value / 8,000 bytes per routine; a write over a cap returns `notes_full` and changes nothing. Per-Bot serial writes, `writeJsonAtomic`.
- Render: `Notes you kept from earlier runs of this routine:\n- key: value`, prepended to that routine's own input by `botRoutineMessage(prompt, notes)`; `""` when empty. `botRoutinePromptOf(text)` strips the notes block and the `[SILENT]` rule (Remote routine bubbles use it; desktop rows can too).
- Offer: the candidate is always installed (the registry holds the attended set); `botIngressAllowsTool` allows it only when every request id of the run is `routine:` (empty list → no). Binding is at call time: `routineTaskIdOfRun` matches the Bot's running submission (`state().submissionId`, the run's first input) against `submissionByRequest` of the routine notices in the conversation — never the closure from the last refresh, so a queued second routine cannot steal the first one's notes.
- Routine delete clears its key (`BotRoutineServiceDependencies.routineDeleted`); Bot delete removes the file with the session directory.

## Proposals (`routines` tool)
- `schedule-tool.ts` `createBotRoutinesTool`: `list` (id, name, label, enabled), `propose`, `pause`. No create/update/remove path; the old `createBotRoutineTool` and the `bot` branch of `scheduleTaskToolsForContext` are gone. Tool name `routines` (`BOT_ROUTINES_TOOL_NAME` in `renderer/shared/bot-routine-proposals.ts`); policy `ROUTINE_TOOL` follows it and stays withheld on routine and Telegram runs.
- Store/service: `main/services/bot-routine-proposals.ts` (`routine-proposals.json` in the session dir, per-Bot lock, ≤2 pending, reason ≤280, validated with `parseBotRoutineCreate`). `propose` appends `aiden.routine-proposal` through the calling tool's `appendEntry`; `respond` schedules the payload read from the conversation entry the card renders (never the mutable JSON, which only tracks status and the pending cap), creates the routine with `sourceProposalId`, appends `aiden.routine-proposal-status`, then records the decision. Any later answer, `list`, or `propose` reconciles to accepted when a routine with that `sourceProposalId` exists (`routines.findBySourceProposal`), so a dismissed card never hides a created routine. Wiring: `bot-routine-proposals-main.ts`; IPC `bots:routineProposals:respond` in `main/handlers/bot-routines.ts` (strict parser).
- `BotRoutineService.create` returns an existing task with the same `sourceProposalId`; `pause(botId, id)` added.
- `schedule-store-core.ts` persists `sourceProposalId` (set once on accept, never changed by an edit).

## Catch-up after pause
- A `bot_paused` skip of an automatic fire is recorded with run id = that fire's request id (`routine:<taskId>:<fireTime>`). `createBotRoutineCatchUp` runs, per enabled routine of the Bot, the newest run when it is such a skip < 7 days old, via `scheduleService.catchUp(id, {runId, at})` (trigger `{kind:"catch_up", missedRunId, missedAt}`; same gates as automatic; never advances the schedule). Request id = the skip's id, so repeats dedupe in the session; label `"{name} (missed while paused)"`. Several misses coalesce (only the newest run is looked at).
- Trigger: `createBotRoutineCatchUpTrigger` fires on leaving `interrupted` (or the first non-paused state seen for a Bot); subscribed in `scheduled-bot-routines-main.ts` via `onBotSessionStateChange` (module-load side effect).

## Results reach the person
- Phones: `bot-routine-notifications.ts` projects the run store (Bot tasks with `notify`, `success` with visible text or `error`; never silent/skipped/blocked), newest first, ≤100, `since` exclusive, preview = redacted first 160 chars or "I couldn't finish this routine." Served at `GET /bots/routine-notifications`.
- Telegram: executor calls `ports.deliverResult` after a visible reply or failure (failure text is the fixed line). `telegramService.deliverBotRoutineResult` → binding's profile → outbox `enqueueRoutineDelivery` (`kind:"routine"` row, starts `pending`, same `sending`/duplicate-label path). `routineTargetEnabled` re-checks binding enabled + same chat before each send; otherwise the row becomes `failed` unsent. Text: `**{name}**\n\n{reply}` through the Markdown→HTML chunker.
