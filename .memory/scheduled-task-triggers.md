# Chat tasks that run when something happens — 2026-11-22

Proactive Aiden plan, Phase 4 (docs/plans/proactive-aiden-plan.md). Guide: docs/scheduled-task-triggers.md.

## E2 watch triggers (desktop)

- `ScheduledTask.trigger?: ScheduledTaskTrigger` (`renderer/shared/scheduled-task-trigger.ts`, strict `parseScheduledTaskTrigger`). E2 has `{kind:"watch", source:{type:"url"|"script"}, everyMinutes 5–1440}`. `ScheduledTaskInput.trigger`: undefined keeps the saved one, null removes it. A trigger task has `cron: ""`, no `nextRunAt`, no Cron job (`schedule-service-core` `schedule()` returns early) and skips the chat cadence floor. Only llm tasks of the person's own (no Bot); a script watch needs Full. An unreadable stored trigger is dropped and the task gets "Needs attention".
- Each trigger task is one routine on the E1 event core keyed by task id: `scheduled-task-triggers-store.ts` (bookkeeping in `<userData>/scheduled-task-triggers.json`, reconciled lazily against the schedule store on every list/mutate) and `scheduled-task-triggers.ts` (dispatcher + watches + runner). The routine's `updatedAt` is a trigger revision moved only when trigger/prompt/enabled change (fingerprint), never by `recordRun`/`updateRuntime`, so a recorded run doesn't retire a change a watch saw. Source change = fresh baseline; prompt change drops queued work.
- Event core extensions (backwards compatible for Bots): dispatcher `limits(routine)`, `payloadChars`, `mergeHeld` (for E3 batching); watch `reportsOutput(routine)` (script output is the news, no baseline/diff). `runScheduledScript` takes `env`.
- Runs: `scheduleService.runEvent(id, {kind:"event",source:"watch",...}, "event:<taskId>:<eventId>")` (same gates as an automatic run; waits out a running task); `schedule-execution` passes `trigger.payload` as `eventText` to `deliverTaskRunToChat`, which fences it in the origin chat and (new) in the own-chat fallback (`runInOwnChat(..., eventText)` appends it after the prompt). Replay: a recorded run (not blocked) with that id counts as settled. 4 runs at once overall via a slot queue. Skipped runs (chat busy/budget) are re-queued (see `requeue` below). `runOnce`'s catch settles the receipt only for `ScheduledTaskIneligible` (typed error from `schedule-service-core.ts`, `reason: missing|paused|no_trigger`); any other `runEvent` rejection requeues under the same event id (`settles` + `refund`, `notBefore = now + min(1 h, 60 s × 2^retries)`, `maxRetries: TASK_TRIGGER_RETRIES`); a rejected requeue (busy or failed path, via `holdAgain`) is never retried and returns `settled: false`, since the write may have landed. Inside `dispatcher.requeue`, a rejected write starts `reconcileRequeue` (2026-11-22, Pullfrog round 3). It re-reads the routine through the store's per-owner queue and handles each part on its own (round 4): any held event is armed (`armHeld` at gap end), AND a `settles` receipt still running is replayed via `claimAndStart` once `notBefore` (or the gap) has passed. An unrelated newer held event no longer hides the receipt. Saved drop notices are shown. With none of these, the event is settled. Max-retry drops are durable: the same write that drops the payload appends a `BotEventDropNotice` (`{id: "<eventId>:retries", reason, held}`) to the routine's `dropNotices`, which the task store persists (max 8; the Bot store doesn't, since only tasks retry). `showDrops` clears a notice only once `heldDropped` has shown every part (round 5). `heldDropped(routine, held, reason, done)` takes the parts already shown (`card`, `log`) and returns `{done, failed?}`. The task callback posts the card first, then the link log line, and skips parts in `done`. A failure keeps the notice with its `done` and `failures + 1` and retries with the reconcile backoff. It is given up and logged after `BOT_EVENT_DROP_NOTICE_TRIES` (6). An in-memory `shownParts` map keeps progress if the write saving it fails, and `showingNotices` stops two passes running at once. It runs after the requeue, in reconcile, and on `rearm` (start) for leftovers. A restart after the clear landed never shows the card again. If the clear never lands before a restart, the card can be shown once more (at-least-once). A failed read is retried after `REQUEUE_RECONCILE_MS` (5 s), doubling up to 5 min. Its timers are cancelled by `dispose`. So the running process delivers the event without a restart, for Bot routines too. `dispatcher.requeue` is once per event: a no-op when `settles` is no longer running or `held.eventId` is the event's id (shared with Bot routine events). Bot routine events don't share this path: their runner throws and the dispatcher keeps the receipt.
- Three failed checks: the store's mutate sees enabled flip and calls `pauseTask` (updateRuntime enabled:false + lastError), keeping the revision; the watch's `paused` posts one record-only card through `scheduleExecution.recordInLandingChat` (new `chatDelivery.recordInLandingChat`).
- Wiring: `scheduled-task-triggers-main.ts`; started after `scheduleService.start()` in `main/index.ts`, stopped at cleanup, re-armed from the schedule service's broadcast. Never holds keep-awake.
- Phones: `AidenRemoteScheduleService` hides trigger tasks (list/notifications skip, get/update/remove/pause/resume/run/runs say not found) until E6.
- UI: editor **When** select (On a schedule / When something changes) + `WatchTriggerFields` (Check, Address/Script, Check every); list, detail, settings row and search show `formatTaskWhen` / `formatScheduledTaskTriggerLabel`.
- Tests: `scheduled-task-triggers.test.ts` (new, test:scheduled), `schedule-store.test.ts`, `aiden-remote-schedules.test.ts`, `schedule-chat-delivery.test.ts`, `scheduled-tasks-parse.test.ts`, `scheduled-task-view.test.ts`, `scheduled-task-editor.test.tsx`.

## E3 link triggers

- `ScheduledTaskLinkTrigger {kind:"webhook", gapMinutes 1–60, signatureHeader?, filters? (≤5 path=equals), dedupePath?, includeFields? (≤10)}`; dot paths, `__proto__` etc. refused.
- Router `/hooks/tasks/:token` (route label `taskTriggerWebhook`) calls `taskTriggerWebhook.admit` (404/429/415, before reading the body), reads ≤256 KB (413 via `taskTriggerWebhook.tooLarge`, which refunds the slot), passes the task's signature header value to `deliver` (401 HMAC, 400 bad JSON, filters → 202 "filtered", dedupe, emit → 202). Core in `scheduled-task-link-trigger.ts`; wired from `aiden-remote-service-main.ts` to `scheduled-task-triggers-main.ts`. The CLI host doesn't wire it (404).
- Batching: dispatcher `mergeHeld(held, incoming, routine)` (now gets the routine); link batches are a NUL-marked JSON payload (`mergeLinkBatch`, ≤24,000 chars, 20 calls), spelled out by `linkEventText` at run time with "N more calls were dropped". NULs are stripped from call text so a caller can't forge a batch.
- Token by hash in the bookkeeping (`setTokenHash`, `findByToken`), log of 50 (`appendLog`, `linkState`), secret `aiden-internal:task-hook:<taskId>` (deleted when the task is removed, via the schedule service broadcast payload). IPC `schedule:trigger-link:rotate` (needs Aiden On The Go on; returns url+secret once) and `schedule:trigger-link:state` (never the link).
- UI: editor **When its link is called** + `LinkTriggerFields`; task details `ScheduledTaskLinkPanel` (Create/Rotate link, Copy once, Recent calls).
- Tests: router test in `aiden-remote-router.test.ts` (order, signature, filter, 429, no token in logs); batch/redaction/dedupe/log/rotation in `scheduled-task-triggers.test.ts`.

## E4 Aiden can propose triggers

- `schedule_task` create takes `trigger` (standard and Assistant; `SCHEDULE_TRIGGER_PARAMETER`, parsed by `toolTrigger`); refused on update. Assistant refuses script watches; its schema's `cron` is now optional (required unless trigger). Canonical Assistant args carry `trigger` instead of `cron`.
- Approval details (`ScheduledTaskApprovalDetails`, `AssistantAutomationApprovalDetails`) gained optional `whenLabel`; a trigger task has `cron: ""`, `nextRunAt: 0`, and the validators accept an empty cron only with a `whenLabel` (phones that require a cron fail closed until E6). `whenLabel` is in the run-journal allowlists (`run-event-projection.ts`). Card shows it instead of the cadence.
- Results: task summaries carry `trigger` (the label); a link task's create result adds `link: "shown_to_person"` (standard also `status: "saved"`). The agent never sees the link.
- CLI `packages/cli/src/schedules.ts` `saveInput` refuses `trigger`.

## E5 Failure pause and the 12-hour rule (chat tasks only)

- `schedule-service-core.ts`: `chatFireTooLate` in `dispatch` (automatic, not recovery, no `botId`): fire more than `CHAT_TASK_LATE_LIMIT_MS` (12 h) late and no cron time in the last 12 h → `advanceBeforeRun` claim, record `skipped` / reason `too_late` (run id `late:<taskId>:<fireTime>`), no execution. Covers startup catch-up and a Cron timer waking from sleep (both pass through `dispatch` with the stored `nextRunAt` as fire time). Bot routines untouched (7-day window in `scheduled-bot-routines.ts`).
- `pauseAfterRepeatedFailures` after `execution.run` for automatic or event dispatches of chat tasks: newest 3 runs after `task.failurePausedAt`, ignoring `skipped`, `cancelled` and by-hand failures, all failed (error or refused `blocked`) → `updateRuntime({enabled:false, nextRunAt:undefined, failurePausedAt, lastError})` (before `stopJob`, else `isCurrent` turns false and the write is refused) then dependency `pausedAfterFailures` → `scheduleExecution.recordInLandingChat` card (desktop only; CLI has no card).
- `ScheduledTask.failurePausedAt` (main-owned, chat tasks only) kept by save/normalize; `ScheduledRunSkipReason` gained `too_late`. Phones see skips as succeeded runs with the output as summary, so no contract change.
- Tests in `schedule-service-core.test.ts`; old tests' `nextRunAt: 1` overdue values became `Date.now() - 60_000` so they don't depend on the time of day.

## Skipped trigger runs keep their payload (after E5)

- `runOnce` in `scheduled-task-triggers.ts`: a run recorded `skipped` with `chat_busy`/`chat_budget` calls `dispatcher.requeue` (new generic method in `bot-routine-events/dispatcher.ts`) with a fresh event id (`<eventId>~<now base36>`, so the recorded skip's run id doesn't short-circuit `findRun`). It merges into `held` (older first) and arms the held timer at `lastRunAt + gap`.
- `combineHeld`: link → `mergeLinkBatches(older, newer)` (both may be batches; 20 calls, dropped counts summed); watch → newest change, then "An earlier change that wasn't delivered yet:" plus the older one, cut at 24,000 chars. The watch's in-gap `mergeHeld` now uses the same (it was newest-wins), otherwise a requeued change would be dropped by the next change.

## Phase 4 review fixes (E2–E4)

- Token lookup: the store keeps an in-memory `tokenIndex` (hash → task id) rebuilt in every `load()` and `setTokenHash`; `findByToken` only takes the serial `load()` for a hit, so unknown tokens never read tasks or write. `linkState` is read-only. The webhook answers unknown tokens 429 after `UNKNOWN_LINK_CALLS_PER_MINUTE` (120) a minute across links (superseded details: see Phase 4 loop-closing fixes).
- Refused calls (bad signature, invalid JSON, 415 wrong type, 413 oversized) refund their slot in the 60/min (`admit` returns an opaque `admission` id per reservation, which the router passes to `deliver` and `tooLarge({token, admission})`; a refund removes exactly that reservation, or nothing once it aged out; a 415 is refunded inside `admit`; once the refused bucket is full a 415 answers before `findByToken`), count toward `REFUSED_LINK_CALLS_PER_MINUTE` (30) and log with `coalesce` (same outcome within a minute bumps `repeats`). Log broadcasts throttled to one per 2 s per task (trailing).
- One event bound: `SCHEDULED_TASK_TRIGGER_LIMITS.eventTextChars` (24,000) = `TASK_TRIGGER_PAYLOAD_CHARS` = delivery's `EVENT_TEXT_CHARS`; delivery keeps the start (`headText`); `linkEventText(payload, maxChars)` fits heading + calls by shortening the longest.
- `dispatcher.requeue(..., {refund, notBefore})`: skipped chat_busy/chat_budget runs give back their day count; chat_budget waits `CHAT_BUDGET_RETRY_MS` (1 h) by moving `lastRunAt` to `notBefore - gap`. New dispatcher dep `heldDropped` (tasks: `dailyLimit` card + link log `daily_limit`; Bots unchanged).
- Replay: a recorded skipped chat_busy/chat_budget run counts as unsettled (like blocked) and runs again.
- Book `needsNewLink` when a save adds or changes `signatureHeader` on a task with a link; cleared by `setTokenHash`; `linkState.needsNewLink` → panel says Rotate.
- Store dep `released(taskId)` when a link or script-watch task changes away or is deleted → main deletes the link secret and `taskCheckStateFile`.
- `schedule_task` refuses proposed URL watches where `isPrivateWatchAddress` (renderer/shared/scheduled-task-trigger.ts); the label shows the whole host and cuts only the path; link results say `person_creates_in_task_details`.

## Phase 4 review fixes (E5, E7, model)

- Failure streak: `ScheduledRun.byHand` (manual trigger, set by desktop `recordRun` and CLI) and `cancelled` (blocked because the run's controller aborted; normalize keeps it only on `blocked`). `pauseAfterRepeatedFailures` counts error and non-cancelled blocked (refusals) runs, skips `skipped`, `cancelled` and `byHand` failures; a `byHand` success still breaks the streak. Turning a chat task off→on by hand (`changeEnabled`, or a save that enables it) sets `failurePausedAt = now`.
- Connector choices are single-use: `createTaskConnectorTriggers().forgetChoice(id)`. `saveConnectorTask(trigger, existing, {connector, save, bind, needsSource})` in scheduled-task-connector-trigger.ts is what `schedule:save` calls: forgets the choice once the save lands, binds after, and on a bind failure marks the task and throws "The task was saved, but its source couldn't be connected…". Triggers dep `needsSource(task)` runs in `start()` for enabled connector tasks with no `connectorSource` (crash between save and bind). Main `markTaskNeedsSource` sets `lastError = TASK_CONNECTOR_NEEDS_SOURCE`; `bindTaskConnectorSource` clears it. Exports: `taskConnectorChoices`, `bindTaskConnectorSource`, `markTaskNeedsSource`.
- Wording: connector-main `isPaused` throws `BotConnectorWatchError("unavailable", "Scheduled tasks are paused." / "This task is off.")` instead of returning true (the shared hosts would say "This Bot is paused."); the 3-failed-checks card for a connector task says to check the connected app in Settings → Connectors. watch.ts comments why tasks never take the Composio calendar first-check exception (`connector` vs `connectorSource`).
- Tests: CLI parity refuses a `connector` trigger too (message now names connected apps); schedule-execution-tool-policy test runs a task in its origin chat against the real `createChatStore` and checks the stored chat keeps the person's model.

## Phase 4 loop-closing fixes

- Link lookup: store `tokenTask(token)` (in-memory index only) and a read-only `findByToken` (tasks + `persistence.load()` + `reconcileTaskTriggerBook`, no `persistence.update`). Webhook `admit`: index miss counts toward `unknown` (429 past 120/min, else 404); a hit takes the link's 60/min (paused tasks too) before `findByToken`; nothing on the admit path writes. `deliver` re-opens read-only. Refused calls (bad signature, invalid JSON, 415, 413) never 429: they refund the 60/min slot and only the first `REFUSED_LINK_CALLS_PER_MINUTE` (30) a minute are logged.
- `dispatcher.requeue(..., { settles, refund, notBefore, maxRetries })`: drops the run's own receipt in the same mutation as the held copy; held receipts carry `retries` (store `BotEventReceipt.retries`, parsed by the task store, copied by `withRunning`); past `maxRetries` (tasks: `TASK_TRIGGER_RETRIES` = 6) the payload is dropped via `heldDropped(routine, held, "retries")`. `heldDropped` now takes a reason; the triggers dep `dailyLimit` became `dropped(task, {summary, text})`; link log outcome `dropped` ("Chat stayed busy, dropped").
- Store payload checks count code points (`payloadFits`), matching the dispatcher's cut.
- `isPrivateIpAddress` / wider `isPrivateWatchAddress` in renderer/shared/scheduled-task-trigger.ts (v4-compatible/mapped/NAT64 IPv6, site-local, multicast, 198.18/15, 192.0.0/24, docs ranges, 224+/broadcast, dotless names, `.home.arpa`/`.lan`/`.home`/`.corp`/...). Schedule tool saves url watches with `agentProposed: true`; triggers `fetchUrl(url, signal, {publicOnly})`; main uses `publicOnlyFetch` (main/services/public-only-fetch.ts: node http(s) with a `lookup` that refuses any private address and hands the socket the checked address, so no rebinding; IP literals checked directly; `WatchAddressRefused` message surfaces through `fetchBotWatchUrl`). Bot routine proposals refuse private url watches; `watchAddressLabel` (bot-routine-trigger.ts) shows the whole host for both labels.
- `TASK_CONNECTOR_NEEDS_SOURCE` moved to renderer/shared/scheduled-task-trigger.ts; schedule-store-core save clears it when the saved trigger isn't `connector`.
- Chat Stop on a scheduled run: `finishLlm` maps a `chat:done` whose timeline status is `cancelled` to `{result:"blocked", cancelled:true}` (`TaskRunExecution.cancelled`); `run()` records `cancelled`, skips analytics and the notification.

## Final integrated review fixes
- Link bodies: after JSON.parse, `nestsDeeper(json, MAX_JSON_DEPTH=32)` (iterative) throws inside the parse try, so a deep body takes the invalid path (400, refund, coalesced log) instead of overflowing `asText`/`valueAt` (500). `withholdSecrets` uses the same depth.
- main/index.ts imports `start/stopScheduledTaskTriggers` statically (no cycle) and stops them synchronously in cleanup.
- Trigger event text (fenced under `TRIGGER_EVENT_LABEL`) taints the run that reads it and later runs in that chat (see chats-that-run-chats.md, final review).
