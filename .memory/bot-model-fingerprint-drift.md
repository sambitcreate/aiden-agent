# Bot model fingerprint drift (2026-10-21)

Symptom: after 0.58.0, every turn of a Full-access Bot on ChatGPT / Codex GPT-6.1 Sol failed admission with "This Bot's available capabilities changed. Start again after reviewing access." The Bot's last good turn ran on 0.57.0.

Cause: `modelFingerprint` in `main/services/bot-capability-inventory-ports.ts` hashed the whole `ProviderModelMetadata` (name, context window, thinking levels, ...). The pi-ai 1.2.0 → 1.3.0 pin raised GPT-6.1 Sol's `contextWindow` from 272000 to 500000, so the catalog's `modelExactFingerprint` no longer matched the Bot's stored binding, and `assertBoundBotProviderModelCurrent` threw `BotCapabilityBindingDriftError` on every admission. Verified by recomputing the stored fingerprint from Codex metadata with `contextLength: 272000`. The remote Pi catalog refresh (every 4 h) could trigger the same failure without a release.

Fix:
- `modelFingerprint` now hashes only `{ providerId, modelId, supportsImages }`. The provider `connectionFingerprint` (endpoint, credential and resource incarnations) is unchanged and still fences account or credential changes.
- `refreshBoundBotProviderModel` (bindings) plus `BotCapabilityStateEditor.refreshStaleModelBindings` (store core) repair the Full model binding and the companion vision binding at `BotCapabilityStore.admit` when only the model fingerprint is stale. Repair requires the same provider id, provider exact fingerprint, model source id, model public id, availability and image capability; otherwise the existing drift failure stands. It issues a new policy revision but keeps the policy epoch, so no lease is fenced. Selections and chat reductions never change.
- Custom bindings are deliberately not repaired (Pullfrog review on PR #567): every runtime and access-settings catalog read re-verifies a Custom binding's public ids against its exact facts (`assertBoundBotCustomSelectionOpaqueIds`), and legacy v1 ids embed the old fingerprint, so a repaired binding would fail that check and strand the Bot. Custom model drift fails closed as `model_changed` until the model is chosen again.
- Provider/model drift now classifies as `model_changed` ("This Bot's AI model or its connection changed. Choose the Bot's model again in its settings.") instead of the generic `capability_changed`. Remote/native clients only receive the message text; `aiden-remote-bot-files` maps it like any non-unavailable failure.

Not changed: Custom binding drift for MCP toolsets, skills, files and shell still fails closed as `capability_changed`. Observed while debugging but not traced: during the failing admissions `bot-capabilities.json` was rewritten with byte-identical content about 45 times, each leaving a `.previous` predecessor until the next startup. The suspected source is the per-snapshot incarnation reconcile, which runs `persistence.update`.
