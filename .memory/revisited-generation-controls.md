# Revisited generation controls — 2026-09-21

October 5 update (`feature/unified-send-control`): the desktop busy composer's separate Queue button + chevron dropdown became one pill (`renderer/components/busy-send-button.tsx`): mode name + chevron, single accent color, no icon. Clicking the name sends; the chevron or a ~450 ms hold on the name opens a Steer/Queue radio menu, and hold → drag → release on a mode sends in it (Radix items select on pointer-up when the press began elsewhere). Picking a mode with a draft now sends it; with an empty draft it only switches. Desktop Redirect was removed entirely (composer prop, confirm dialog, `ChatPane.redirectMessage`, `ChatMessageQueue.replaceWith`); Stop then send covers it. iOS and Android got the same pill in the same change (Redirect removed there too, `offersRunInput` no longer requires a draft so the dimmed pill shows while a run streams; `canSubmitRunInput` carries the draft check). iOS: `runInputPill` in `AidenChatFeature.swift` uses `Menu(primaryAction:)` so tap sends and touch-and-hold opens the menu. Android: `AidenRunInputPill` in `AidenComposerView.kt`, mode in `AidenChatViewModel.runInputMode`.

October 1 update (`feature/desktop-telegram-steer`): desktop composer Steer and the new queued-row Steer action now go through #251's `chat:admitRunInput` admission (durable transcript append before Pi's steer queue), and the old `chat:steer` IPC / `llmClient.steer` / `steerGeneration` were removed. The harness reuses the committed message id when Pi emits admitted input, and excludes host-committed input from `takeUndeliveredQueuedMessages`, so admitted guidance appears once and stays as history after Stop instead of returning to the draft. The `chat:guidance-returned` path below is no longer fed by desktop Steer. The paragraph below is the earlier design.

September 23 composer audit: the old queued-row “Steer” actually stopped the response and sent the row next, so it was removed. Busy desktop input now selects true Pi Steer, Queue, or confirmed Redirect. Steer uses exact-stream document-owned IPC; when Pi emits queued user guidance, the Mac persists it before the next model step. The accepted queue is still memory-only until emission, so crash-durable admission remains a follow-up. Within a live Mac process accepted guidance is never silently dropped: the queued-user projection runs inside the harness's managed fault boundary (cancellation-aware, a failure is a structured `session` host failure), and after each run `takeUndeliveredQueuedMessages()` reports accepted input that never became visible chat (Stop before emission, a terminal before the next step, a failed projection). Main adds it to the terminal event as `undeliveredGuidance` without ever waiting on host storage: if Stop stopped waiting on an unresolved projection save, the terminal goes out at once, the save stays quarantined as detached durability for the rest of the run even once settled (so the turn always goes through rollback + visible-history resync and the guidance keeps its place before the assistant; the next turn waits for that recovery), and only if it then fails is the text sent to the owning window on `chat:guidance-returned`; the renderer appends it to that chat's composer draft (live composer or device-local store) and never resends it. Once Stop starts, Queue/Steer/Redirect admission is closed until the stream settles. Stop clears the local follow-up queue but preserves the independent composer draft. Device-local text draft records retain an unresolved marker and never automatically resend. See `docs/chat-composer-busy-controls.md` for the desktop/mobile gap table.

Returning to a chat with a route-detached generation now uses the retained stream projection to expose the existing composer Stop and queue/steer controls. Stop targets that exact stream through the same-document `chat:cancel` authority check; the main handler acknowledges whether cancellation was admitted. Queued messages remain document-local and cannot append until the existing main-process idle and authoritative transcript reconciliation gates settle.

The pane's detached Stop state has no local terminal callback. Clear it when the shell removes the detached lifecycle marker after authoritative settlement, otherwise steering leaves the queue disabled behind a stale “Stopping…” state. Keep reconciliation-only markers (no active projection) read-only. The ordinary local stream path is unchanged.

Pullfrog follow-up: terminal cache publication can precede detached-owner cleanup. Once the cached final assistant message is present, the pane masks the retained projection for Stop/queue/steer and stays read-only until reconciliation clears the draining marker. The terminal-sync held-settlement test and pane control contract cover that handoff.

Subsequent review found the inverse race: a chat read begun before append might replace the newly appended user turn with the previous assistant tail, falsely triggering that mask. The append path now cancels exact-chat reads before installing the durable appended snapshot, matching terminal cache publication's read fence. A held old-read regression proves its late result cannot replace the user turn.

Hosted verification also exercised the broader Environment/Subagents source contract, which still expected the pre-guard detached readiness and transcript expression. Updated that contract to assert the guarded handoff; focused contract and type/lint checks pass.

Focused renderer/IPC tests, chat/composer suite, and held-response Electron regressions cover revisit → queue/steer → next turn and revisit → Stop → new turn. E2E held-response sidebar titles reflect the original prompt, not the deterministic completion text. Local native helper scripts discard inherited SDK variables; on this host a direct Xcode 26.5 SDK helper build was used for E2E because the CommandLineTools macOS 27 SDK fails linking.

Review: OpenCode Workers created an isolated checkout at the exact feature commit, but its launcher rejected `--dir` under the configured OpenCode v2 CLI. A direct read-only DeepSeek V4 Flash run in that same worktree reviewed the full diff and surrounding lifecycle/queue contracts, reported no actionable findings, and left the worktree unchanged. The requested “4.1 Flash” name was not listed by OpenCode; V4 Flash was used as the available model.

## October 15: chat-message-queue CI flakes (PR #479)

Two held-response specs flake about once per few dozen hosted runs and never locally: "Stop after revisiting…" (Stop missing after the revisit, line ~617; sibling "revisiting a running chat…" had the same symptom on Oct 9) and "a response finishing while the queue editor is open…" (0 requests with the edited text, line ~511). They predate Bot slice C2 (#478): the editor test flaked on Oct 10 and Stop-after-revisit on Oct 13 (mcp-07 branch, head bcc1845d) — so C2's route memory, Bot panel provider and Bot notification sync are ruled out.

Not reproduced: ~1,300 local runs (macOS, 8 workers, CPU stress, CDP 20x renderer throttle, background QoS, SIGSTOP stalls of main/renderer, slow fs, delayed IPC replies and idle notifications, focus loss, gap sweeps) plus 360 runs in a Linux container under xvfb. Reading the code, both symptoms need the first held response to end (a terminal or error) while the test thinks it is still running: a terminal hides and drops the detached projection (Stop gone), and `onError` pauses the chat queue (edited row never sent). The trigger on hosted runners is unknown.

Fixed along the way: after a revisited chat's detached run ended, the watcher started on revisit mirrored that same run back as an "observed" (phone) run because the only ownership check was the detached marker the terminal had just cleared. The composer re-locked ("Waiting for the response…") right after unlocking, for 10–300 ms (11 of 12 local probe runs; 0 of 12 after). `rememberOwnGenerationStream` in `chat-terminal-sync.ts` (called from `startGeneration` and on detach) now keeps a bounded set of this document's runs that are never mirrored.

Diagnostics for the next hosted failure: the E2E fixture prints, on failure, the on-screen alerts/status/toasts and the dev log's warn/error records to stderr (the reporter truncates the dev-log attachment, and hosted artifacts keep only the sanitized receipt). The editor spec also asserts the first reply saved and the queue is not paused before Save, so an upstream failure no longer reads as an editor bug.

Also found by loading the whole spec (6 workers locally), where the Steer specs failed 8 of 30 before and 0 of 60 after (whole spec, 4 workers, repeat-each 30: 570 of 570):
- Steer during the start window was rejected. Stop and the Steer pill appear as soon as a send begins, but Pi opens its run-input queue only at `agent_start`, so main answered `run_not_active` and the composer said "The current response has ended". `admitRunInputOnceStarted` (`chat-message-queue.ts`) now retries `run_not_active` while the pane's own run is still live (bounded to about 8.5 s; a rejected attempt writes nothing). Detached runs are not retried.
- `handleSend` awaited the `chat:start` acknowledgement. That held the composer's `sending` flag, so the busy pill's `canSubmit` was false while main initialized, and picking Steer or Queue only switched modes. The send now finishes at the durable append; a start rejection still sets the pane error.
- Test race: after picking from the busy pill's menu, Radix returns focus to the chevron a task later, so a keypress sent straight to the composer could land on the trigger and reopen the menu. The rejected-steer spec now waits for that focus first.

Noise seen in every local run: "Could not append Pi session messages for stream …" logged three times at error level on each user Stop.
