# Missing workspace folder notice — 2026-10-29

Adopted from Pi #11511 (deleted working directory) as part of the "six upstream changes" plan, step 1.

- `main/services/workspace-folder-presence.ts`: `workspaceFolderPresence` (`present` / `missing` / `unknown`; ENOENT and ENOTDIR are missing, permission errors are `unknown` and never block), `workspaceFolderMissing` and `assertWorkspaceFolderPresent`. The assert runs before `assertManagedWorktreeAdmission` in `prepareGeneration` (llm-client), both scheduled-task paths, and the terminal drawer's open.
- Scope (`workspaceFolderCheckApplies` in `renderer/shared/workspace-folder-presence.ts`): only workspaces with a folder, not No Access (the folder is never touched), including Aiden-managed worktrees since step 5 (checked at the checkout root, `checkedWorkspaceFolder`).
- Desktop: IPC `workspaces:folderPresence`; ChatPane queries it (10 s stale, refetch on focus), shows `WorkspaceFolderMissingNotice` (full sentence with `~/path`, no path for worktrees, and Check again, which always stays) above the composer, and refuses a send before append with a short toast so the text stays. The check is fenced by `chatVisitRef`: if the person changes chat while it runs, the send is dropped silently (the composer's saved draft keeps the text). If the IPC check itself fails the send goes ahead (main checks again). A send that drains from the queue instead fails at main and pauses the queue.
- Phones and paired Macs: `AidenRemoteChatService` option `workspaceFolderRefusal` (returns the message) refuses a turn before append with `workspace_unavailable` 409 wrapped in `AidenOperationNotExecutedError` (the same idempotency key runs once the folder is back). The message has no path, since Remote errors never carry one. iOS and Android (`AidenDraftSendReconciliation.refusalSettlesSend`) treat a 409 with exactly `workspace_unavailable` as a known refusal: they drop the saved attempt, keep the text and show the Mac's message; any other 409 stays an unknown delivery. No protocol revision.
- Workspace folders stay fixed by design (`workspaces:update` refuses `folderPath`), so there is no "Locate folder" action; workspace memory is keyed by the folder path too.
- CLI: `runCli` checks `process.cwd()` first and prints one line, exit 1. Pi's own fix (#11511) is not in a Pi release yet and Aiden reads the cwd before Pi anyway.
- Tests: `main/services/workspace-folder-presence.test.ts` (test:workspace-intake, core lane in ci-test-registry.json), a phone-turn case in `aiden-remote-chats.test.ts`, `tests/e2e/workspace-folder-missing.spec.ts`, CLI `tests/runtime.test.mjs` (fails with `uv_cwd` without the fix). No direct test of the `prepareGeneration`/scheduled refusal (heavy harness).

## Deleted managed worktree (step 5a, 2026-10-29)

- Owner chose "Restore, or new chat in main". `workspaces:folderPresence` adds `worktree: {branch, restorable, mainWorkspaceId?, mainWorkspaceName?}` from `missingWorktreeOptions` (restorable = branch head exists and no other worktree holds it; a Git error means not restorable).
- Restore: `workspaces:restoreDeletedWorktree` -> `workspaceWorktreeApplicationService.restoreDeleted` -> `gitRestoreDeletedManagedWorktreeCheckout` (token check, deletion-journal check, refuses a `locked` record; never runs `worktree remove`: the stale admin dir is renamed out of `.git/worktrees/` to `aiden-discarding-<uuid>` in the common dir and put back if `worktree add` fails or a folder reappears, then deleted best-effort after add; an empty placeholder holds the old admin name during `worktree add` so Git picks a fresh one and a moved/trashed copy can't alias the new checkout (a kept folder's record is renamed back to the recorded name and its `.git` repointed); `worktree add` same path + branch, a nested workspace subfolder must still exist in the branch, new token, then a `commit` callback saves the record inside Git's lock; any failure after add rolls the new checkout back through `quarantineAndRemoveManagedWorktree` with a strict safe policy: it is moved aside first, then checked, so anything written, new or ignored keeps the folder in place with a `dirty_worktree` "kept the folder" error (if the removal stopped after setting the checkout and Git record aside, `returnSetAsideRestore` moves both back and drops that journal first); a failure before the new token is saved keeps the folder too). Branch never created/deleted. `.worktreeinclude` re-provisioned after (after the same Mac capacity check creation uses), errors only logged. A kept folder re-stamps or clears the recorded Git record (`settleKeptRestoreRecord`) so Restore can be retried after deleting it. Restorable also needs the parent folder, no pending removal, a token, and permission not none; the main workspace is matched by realpath.
- New chat in main: `openNewChatIn(mainId, {gitMode: "checkout", initialText})`; without gitMode the draft inherited the remembered worktree mode.
- Remote: `workspaceFolderRemoteRefusal` gives the worktree-specific path-free message.
- Tests: two in managed-worktree-lifecycle.test.ts, workspace-folder-presence.test.ts, e2e `tests/e2e/worktree-folder-deleted.spec.ts` (navigate back via the sidebar; memory router has no goBack).

## `aiden serve` parity (W1b, 2026-11-11)

- Before this, the server never passed `workspaceFolderRefusal`: a phone turn in a deleted folder was appended, reached the provider, and every tool failed (`spawn ... ENOENT`); a scheduled run leaked a raw `ENOENT ... lstat '/path'`.
- Pi 1.5.2's #11975 (`assertSessionCwdExists` / `MissingSessionCwdError` in `core/session-cwd.ts`) runs only in Pi's interactive mode and `AgentSessionRuntime` resume/import. The daemon calls the SDK `createAgentSession` directly, which never checks the cwd, so #11975 never fires on the server. Aiden's checks are the only ones.
- Remote: `packages/cli/src/remote-chats.ts` passes `workspaceFolderRefusal` -> `workspaceFolderRemoteRefusal(workspace, undefined, "server")`. Same `409 workspace_unavailable` before append, same idempotency behavior; the text says "on the server" instead of "on your Mac" (`SERVER_*_MISSING_REMOTE_REFUSAL` in `renderer/shared/workspace-folder-presence.ts`), and the worktree variant drops "restore it from the chat on your Mac". Phones show the host's message verbatim, so no client change.
- Backstops: `assertCliWorkspaceFolderPresent` (`packages/cli/src/workspaces.ts`) throws `WorkspaceFolderMissingError` (code `workspace_folder_missing`). In `daemon-chats.ts` `perform` it runs for non-Bot chats right after the workspace is resolved, before hooks, provider runtime and the session (chat:error with the path-free server sentence; covers Telegram and a turn that raced the Remote check). In `schedules.ts` it runs before `accessFor` (run error names the workspace, no path).
- Tests: `packages/cli/tests/workspace-folder-missing.test.mjs` (real serve over HTTPS on port 49380; daemon start; scheduled run). All three fail without the fix.
- For W1c (relink / "continue in a new chat here"): attach actions where the refusal is produced. Remote: the `workspaceFolderRefusal` callback returns only a string today; an action would need either `details` on the `workspace_unavailable` error (additive, needs a protocol revision for clients to act on it) or a separate route. The daemon backstop error carries `code: "workspace_folder_missing"` for a future structured chat:error. Workspace folders are still fixed by design (`workspaces:update` refuses `folderPath`), so relink is a new decision.

## Continue in a new chat (W1c, 2026-11-11, Pi #11975 analog)

- Owner decision (made by the orchestrator for the owner): folders stay fixed, no relinking. Continue in a new chat forks the chat's history into a new chat in a workspace the person picks (desktop: an existing workspace or No workspace; `aiden serve`: existing workspaces only). The original keeps its workspace, keeps refusing turns and keeps the notice.
- Reuses `ChatForkService` (`main/services/chat-fork-service.ts`): request `continueIn: {workspaceId}`, exclusive with `forkAt`/`summary`; cut point `continueInNewChatForkPoint` (newest assistant reply that answers a user message). New dep `workspaceFolderMissing` (desktop `chat-fork-service-main.ts`, CLI `daemon-forks.ts`); the service refuses a present source folder, the same workspace, the Assistant, Bot chats, and a destination whose folder is missing too ("unavailable").
- Desktop: `WorkspaceFolderMissingNotice` gets a Continue in a new chat action and workspace menu (`new-chat-workspaces.ts` lists choices); `chatsApi.continueInNewChat` -> `chats:copyVisibleHistory {chatId, continueInWorkspaceId}` (parsed in `chat-session-params.ts`). No register-and-invoke test for that IPC branch yet.
- Remote revision 63 (provisional, re-claimed at merge): opt-in `chat:continue-in-new-chat`, advertised only when `chats.supportsContinueInNewChat && chats.fork` (router `continueInNewChatWired`). `workspace_unavailable` gets `details {reason: folder_missing|worktree_missing, canContinueInNewChat}` only for devices holding the capability (`deviceSupportsContinueInNewChat` option, via `state.snapshot()` devices), because old iPhones refuse unknown detail keys. `workspaceFolderRemoteRefusal` now returns `{message, reason}`. Fork body `{continueIn:{workspaceId}}`: 403 without the capability, 404 when unwired or a Bot chat. Fixture `continueInNewChat` in contract.json, openapi `ChatForkRequest` oneOf and `ErrorEnvelope` details.
- Phones: iOS alert button + workspace sheet (`AidenChatFeature.swift`, `AidenRemoteClient.continueChatInNewChat`); Android `AidenContinueInNewChat.kt` banner action + sheet (Expressive layer), verified on a headless AVD.
- Tests: `aiden-remote-chats.test.ts` (`continueFixture` over the real chat store and fork service), router advertise/negotiate test, protocol fixture test (Ajv), CLI `workspace-folder-missing.test.mjs` continue test (port 49382), iOS 5 XCTests, Android 8 unit + 4 UI tests, desktop notice test and e2e `workspace-folder-missing.spec.ts`.
